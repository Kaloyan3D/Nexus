Branch `feature/linux-arm64-port`. Nothing is committed or pushed. M1–M4, the sandbox, the permission model and the Mac writeback code are unchanged; the Mac side only gained wording.

## 1. What the live run actually did (read from the engine's own records)

Run `run_9cd20c1d…` on `opencode-go-native/muse-spark-1.3-contributor`, prompt *"open this website and improve its quaility"* on project `test 3`. The records were copied read-only from the VM's state disk (run record, activity log, transcript, engine state); no credentials were read.

| Fact | Value |
|---|---|
| Model turns | **36** (the engine's attempt list keeps the last 32, which is where "32" comes from) |
| Tool calls | 30: 7 `browser_inspect`, 1 `fs_write` + 6 `fs_edit` (**7 edits**), 6 `proc_run`, 4 reasoning-state reports, 1 list, 5 reads of `index.html` |
| Browser | 7 inspections, all `launched/loaded`, every screenshot delivered to the model. The last edit was call 21; calls 22, 23, 24 (desktop, mobile, desktop + 4 interactions) came after it. |
| Checks | 6 commands. Calls 25–27, 29 passed but were not *recognised* as verification; call 28 and call 30 are the same script and **failed** (exit 1); call 29/32 is a different, passing check of the same JavaScript. |
| Outcome | `completion = failing-checks`, one unresolved failed check, `verification = unverified`; therefore **no macOS writeback** (correct, fail-closed). |
| Final answer | *"I made **zero file edits** in this entire run … The failure was not caused by my change."* The record shows 7 edits. |

**The failing command.** `…; node --check <(python3 -c "…extract the <script>…")`. Process substitution gives `node` a path like `/proc/5/fd/pipe:[42337]`; `node --check` reads its input with `readFileSync`, which cannot open a pipe, so it died with `ENOENT` before looking at one byte of the project. I reproduced the identical stderr, byte for byte, in the real sandbox.

**Why the run could not recover.** A failure is only cleared by a pass of the *same* command (`check_identity`); the model's equivalent check on a real file is a different command, so it never cleared it. The engine's generic nudges (*"if the failure was already there and is unrelated … say so explicitly in your final answer"*) then invited exactly the explanation the model gave, and it embellished it with a false statement about edits. The engine also read the failed check as a failed project check: its `museReasoning` went to phase `recover` and the effort to **high** from attempt 35, because of a command that examined nothing.

**Browser evidence.** It was intact and visible in the run (7 inspections with delivery recorded). The visual-assessment requirement was **satisfied** on the record (screenshots delivered after the last edit). It was not *reported* as a requirement because the request wording "open **this** website" was not in the broker's phrase list (it knew "open the website"); that is fixed (§3.4).

## 2. Root causes

1. A tool/invocation error was indistinguishable from a project failure (exit 1 and a stderr nobody classified; the existing classifier only knew shell 126/127).
2. A failed check could only be cleared by repeating the identical command, which here also failed identically; nothing could resolve it, and the nudge text told the model to explain it away.
3. The final text was never compared with the receipts.
4. The engine treated the invalid check as a project failure (recovery phase, higher effort).

## 3. What changed

### 3.1 Invalid-invocation checks (`invalid_check.rs`, `inspect.rs`, client)
* **Detection (controller-owned, narrow):** exit ≠ 0, the process's own stderr shows `ENOENT`/"No such file" on `…/fd/pipe:[…]` (or `/dev/fd/…`), the command is a `sh -c` script with exactly one `<( … )`, and the checker in front of it is a file-only checker on a short allow-list (`node --check|-c`, `python -m py_compile`). Anything else (a genuine `SyntaxError`, two substitutions, another program) is untouched and stays an ordinary project failure.
* **The failure is never erased.** The activity entry keeps `verification: fail`, exit 1, and gets `checkClass: invalid-invocation`. It still counts in `checksFailedUnresolved` and in the run's unresolved-check count, so completion stays `failing-checks`, `verification` is not `verified-passed`, and **both** Mac writeback rules (strict and opt-in) stay closed — the Mac code is unchanged and already refuses on exactly those fields. It is also reported apart (`checksInvalidUnresolved`).
* **Independent equivalent coverage.** The *controller* writes the replacement from the original's own producer command (the text inside `<( … )`, verbatim) and the same checker, with the output in a regular temporary file: `set -e; t=$(mktemp --suffix=.js); ( PRODUCER ) > "$t"; node --check "$t" && echo "syntax check passed: …"`. It is put in the failed result (`nexusRecheck`) together with an explanation, and again at the final-answer boundary (up to three times, before any generic nudge). **Only a `proc_run` that is byte-for-byte that command and then passes resolves the original** (`resolvesCheck`, `checkClass: controller-recheck`). A different check the model wrote, a pass of something else, or the model saying the failure is irrelevant resolves nothing. If the replacement fails, that is a genuine project failure with real evidence and stays open.
* **Spoofing gains nothing:** the classification only changes a label and opens that one path to resolution; resolution still requires the controller's command to pass.
* **No effort escalation for a check that examined nothing:** the engine is told "started", not "failed". I did not change any routing or adaptive policy; I corrected an input.
* Runs where the engine has no automated approvals (strict profile) are unchanged: the replacement goes through the same approval path as any command.

### 3.2 Final answer against the record (`claims.rs`, `inspect.rs`, `server.rs`, UI)
At the final boundary the broker compares the answer with receipts it owns: files changed (count and paths), checks run, failed checks unresolved, browser inspections and whether any screenshot was shown to a model. It recognises narrow first-person contradictions: *no files changed / zero edits* vs applied edits; *all checks pass* vs unresolved failures; *I ran the tests* vs none ran; *I opened/looked at the page* vs no browser run or no screenshot shown. On a conflict the model gets **one** restatement request that contains only the controller's facts. If the contradiction survives, the run is flagged (`answerConflicts`) and `intent-result` returns the model's text **unchanged** followed by "Nexus record (authoritative over the text above)" listing the conflict and the recorded counts; the app shows a red banner. The model's words are never rewritten, and a truthful answer passes untouched.

### 3.3 Attempts
See §5. Two evidence-backed, non-policy changes: the browser-run guidance (first message of browser conversations only) now says to batch edits to one file into one `fs_edit` (up to 16, already in the catalog), not to read back a file just written, and to check syntax on a real file; and the invalid-check path above removes three nudge turns and the effort escalation from this failure mode.

### 3.4 Visual request recognition
"open this/my website|site|page" and "look at this/my website|site|page" are now recognised (the live request was missed).

### 3.5 Nexus.app
Timeline: "Check could not run (invalid invocation, nothing was checked) — still unresolved" / "Nexus's replacement check passed · resolves the invalid check of step N". Outcome card: a banner when the answer contradicts the record, and a note for unresolved / resolved invalid checks. Browser evidence rows are unchanged and independent of the check status, so unrelated failing static checks never hide the screenshots, and "visual inspection met" is displayed separately from the verification verdict.

## 5. Why 36 attempts (live run), and what is avoidable

| Turns | What | Avoidable? |
|---|---|---|
| 1–2, 8 | list, read (800 lines), `fs_write` of the whole 34 KB page | no |
| 3, 6, 7, 13 | 4 reasoning-state reports (6 and 7 back to back: design, implement) | model/policy; left alone |
| 4, 5, 14, 18, 22, 23, 24 | 7 browser inspections (2 before, 2 mid-edit, 3 after the last edit; 22 and 24 are both desktop) | ≥4 needed; ~1–2 redundant |
| 9–12 | **4 reads of the file it had just written** (ranges 1–50, 51–450, 238–537, 538–637; overlapping) | yes, ~3 (guidance added) |
| 15–17, 19–21 | **6 separate `fs_edit` calls** to the same file in two bursts | yes, ~4 (`edits[]` takes 16; guidance added) |
| 25–30 | **"changes not verified" ×3**: none of the model's checks (HTML parser one-liner, heredoc extraction, `ls &&…`) contains a word the recogniser counts as verification (`test/build/check/…`; heredoc bodies are data by design) | policy; **not changed** (see below) |
| 31–36 | the invalid check (fail ×2), a different passing check, "failed checks never re-run" nudge, "last verification failed" nudge, final answer | **yes, ~3 turns and the effort escalation** (now fixed) |

So of 36 turns about 11 were avoidable without touching independent verification, visual inspection or determinism: ~3 from the invalid-check loop (fixed in code), ~7 from read-backs and unbatched edits (steered by guidance; model behaviour, not enforced), and ~1 duplicate inspection. 1.31 M input tokens over 36 requests (≈36 K each) and 5 context compactions come from the 34 KB file reads plus up to four screenshots per request against the 440 KB budget; I did not change image limits.

**Not changed, on purpose.** The "changes not verified" rule (muse-v0 rule 2, up to 3 nudges) is working as specified, but on a static HTML project with no tests it can only be satisfied by a command containing a recognised word, which the model discovers by trial. A concrete, evidence-backed improvement would be to let a controller-classified syntax check (e.g. the same `node --check` replacement) count for that rule when the project has no detectable verification kind. That changes an engine policy, so I left it for your decision. Adaptive effort itself behaved as designed: it reacted to a "failed verification", which was a misclassification, not a routing defect.

## 6. Limits (accurate)

1. Not run against the live model. The corrected flow is shown with a scripted model through the real broker, sandbox and Kernel, not by calling the provider; I did not use your key. You can repeat the live test with the rebuilt app.
2. The Mac writeback itself was not exercised by this change; I confirmed by tests that the fields it keys on (`verification`, `checksFailedUnresolved`, `staleAfterEdit`, `completion`) take the right values (open when unresolved, `verified-passed`/`fulfilled` when resolved). The Mac code is unchanged.
3. Detection covers `node --check` and `python -m py_compile` with exactly one `<( … )`. Other file-only checkers or shapes stay ordinary failures (fail closed), and need the model to run a valid check — which then also does not resolve the original (by design); a future allow-list entry would be the fix.
4. Claim detection is phrase-based and narrow: it catches the live contradiction class, not every paraphrase. The recorded facts are shown beside every coding answer so a miss is still checkable.
5. The batching/read-back guidance is advice to the model, not an enforced limit.
6. The full `code_a56` suite was not re-run (focused subset only).
