# M4.4 — Host-execution cancellation hang: root cause and fix; full rebuild and validation of Nexus.app

Branch `feature/linux-arm64-port`, HEAD `8d209f2`, with the M4.2 Phase A, M4.3 and M4.4 work **uncommitted** in the working tree (110 changed tracked paths, 47 untracked files; `sha256(git diff HEAD)[:16] = 5b611d65037244f8`). Nothing was committed or pushed. The benchmark project and its results were not touched.

**What the shipped artifacts were built from:** no file under `native/` changed after the engine image was built, and after the Nexus.app bundle was built only two **test** files changed (`src-tauri/tests/live_m44.rs`, `src/test/visualEvidence.test.tsx`), which are not part of the app. So the installed app and engine image contain exactly the working tree described here.

## 0. Outcome in five lines

* **Root cause found with evidence, fixed, and proven by a test that fails on the old code:** concurrent host executions of one process could be given the **same cgroup leaf name**; the second `mkdir` failed with EEXIST, the error was dropped (`.ok()`), that run silently lost kernel supervision, and a `setsid` descendant escaped and held the output pipe, so the supervisor waited for ever (§2).
* **Fix:** unique leaf names (process-wide monotonic token + never adopt an existing directory), supervision failures are now reported, and output readers can no longer wait indefinitely for a writer Nexus cannot reach (§3).
* **Stress:** the compiled host-execution test binary (10 tests, 8 threads, the formerly intermittent test included) was run **200 times in a row, 200 passed, 0 failed, 0 timed out**, with **0 leaked processes and 0 leaked cgroup leaves** after every run (§5). Before the fix the same test hung in 3 of 60 solo runs.
* **Engine image rebuilt** from the current `Containerfile` and verified from the shipped `rootfs.img` itself (Rust 1.99.1, Cargo, rustfmt, Clippy, GCC 16.2.1, linker): a broken crate fails with E0308 (exit 101), then checks, tests, lints and links (§6).
* **Nexus.app rebuilt, signed (ad-hoc), validated, installed, launched**, connected to the new engine (green "Nexus ready"), and a **real model session** through the rebuilt app's engine compiled, fixed and tested a broken Rust crate; a real policy denial and a missing executable were recorded as different error codes (§8). The old app is backed up.

## 2. Root cause (Phase 2)

Evidence trail (all on the Fedora ARM64 VM, user-manager-launched, real cgroup v2):

1. M4.3 measured the hang: `hostexec_m8::m81_setsid_descendant_cannot_escape_cancellation`, 3/60 solo runs on the current tree and 2/60 on a clean `HEAD` build.
2. A hang was captured **while it was hung**, from inside the same service cgroup: the surviving `sh -c 'while true; do date >> hb.txt; sleep 0.2; done'` was in the *runner's* cgroup, **not in any `nexus-host-*` leaf**, no leaf existed, and it was the only other holder of the test's two pipe write-ends. The test's reader threads were blocked in `anon_pipe_read`.
3. A traced build (temporary prints, VM copy only, removed) showed why. Two executions in the same test binary produced the **identical** leaf name:
   ```
   TRACE[nexus-host-621565-436364-1793694315781711126] base+leaf ready: true
   TRACE[nexus-host-621565-436364-1793694315781711126] leaf create FAILED File exists (os error 17)
   TRACE[nexus-host-621565-436364-1793694315781711126] base+leaf ready: false
   ```
   `run_host` named a leaf `nexus-host-<pid>-<proc start>-<SystemTime nanos>`. All executions of one process share pid and start time, and two threads can read the same clock tick. `std::fs::create_dir(&leaf).ok().map(..)` (`host_exec.rs`, old lines 124-127) turned EEXIST into `None`: the run silently fell back to **process-group-only** supervision.
4. In that fallback a `setsid` descendant leaves the process group, so neither the group kill (`kill_group`) nor anything else reaches it, and it inherits the stdout/stderr pipes. `run_host` then did `t_out.join()` / `t_err.join()` on readers blocked in `read()` until **every** writer closes. The descendant never exits: the supervisor waits for ever. (The old code's own comment said the cgroup kill must happen "BEFORE joining the pipe readers" for this reason; with no cgroup nothing protected it.)

What was ruled out, with the evidence for each: the pre-exec cgroup join works (`member after spawn: true` in every traced run); `cgroup.kill` works (`kill_tree … returned true exists_after=false`, members killed); PID reuse and group-vs-session membership are irrelevant to this failure (the survivor was never in the leaf); `kill_and_remove_cgroup` is correct for a leaf that was created.

Two further defects were found on the way and fixed (§3): a supervision failure was never reported, and a reader could wait for ever on a writer Nexus could not reach.

Not involved: the bubblewrap sandbox path (`sandbox.rs` leaves are named by execution id, and PID-namespace teardown kills everything), seccomp, Landlock, the authorization path.

## 3. Fix (`native/nexus-tools/src/host_exec.rs`)

| Change | Where |
|---|---|
| `unique_leaf_token()`: wall-clock nanoseconds forced strictly above every earlier token with a lock-free CAS on a process-wide `AtomicU64`; `leaf_name()` keeps the exact `nexus-host-<pid>-<start>-<token>` shape that `orphan_host_leaf` reads | `host_exec.rs:133`, `:151` |
| `create_leaf()`: an existing directory is **never adopted** (it would be another live execution's cgroup); on EEXIST take a fresh token and retry (8 attempts); any other failure is returned as a reason | `:163` |
| Supervision failures are reported: the outcome's `cgroup` text now says why supervision is only the process group (`no writable cgroup v2…`, `cannot create …`, `the command could not be moved into …`) instead of silently dropping the guarantee | `run_host_with`, `degraded` |
| Readers cannot wait for ever: `read_tail` polls (50 ms) and honours a `stop` flag; after the command ends and the cgroup is reaped, `finish_readers` gives the pipes a 1 s grace to reach EOF, then tells stragglers to stop (they drain at most 250 ms of already-buffered data). The result says `an output pipe was still held by a descendant Nexus could not reach … output may be incomplete` | `READER_GRACE`, `READER_STOP_DRAIN`, `read_tail` (`:400`), `finish_readers` (`:456`) |
| `Supervision::{Auto, ProcessGroupOnly}` and `run_host_with`: the degraded mode is selectable so it can be tested on a machine that has cgroups; `run_host` is unchanged for callers | `:113`, `:181` |

Requirement check: cancelled executions end their whole tree including `setsid` descendants (cgroup leaf per execution, unique); descendants cannot escape by changing group or session (cgroup membership is set before `exec`); readers cannot hang (bounded, and honest about incompleteness); leaves and processes are reaped (audited per iteration, §5); cancellation only kills the execution's own leaf or its own process group (no process-wide kills); no sandbox, seccomp, Landlock or approval control was touched; no test timeout was added to hide the defect.

**Residual by design:** when a machine truly has no writable cgroup, a command that `setsid`-daemonizes still escapes Nexus's reach (the run is labelled `process-group-polling` and says so). The fix makes that case bounded and visible instead of an indefinite hang; it does not make an unreachable process reachable.

## 5. Stress validation (Phase 3)

**Method.** `systemd-run --user --wait --pipe -p Delegate=yes` (a child of the user manager, as the real daemon is; see M4.3 §11.1), one run of the compiled `hostexec_m8` binary (all 10 tests, `--test-threads=8`, so the formerly intermittent test runs with the other tests as before), each run under an **external 60 s watchdog** (a hang is recorded as `TIMEOUT` and the run is killed; it cannot block the loop). After the binary exits, **still inside the same service cgroup and before systemd can clean up after it**, the wrapper counts the processes still alive in that cgroup tree and the `nexus-host-*` leaves still present. (Auditing from outside would see nothing: the service's cgroup is killed when the unit stops.)

|---|---|---|---|---|---|
| **200** | **200** | 0 | 0 | **0** (in all 200) | **0** (in all 200) |

Wall time 23 min 27 s (about 7 s per run, i.e. each run executes the whole binary including the 16-way simultaneous-start test). The run overlapped in time with the engine-image build on the same VM and with the Mac app build (the VM is hosted on the same Mac), so part of it ran under extra load.

**Baselines for comparison** (M4.3 and this task, the same method): the formerly intermittent test hung in 3 of 60 solo runs on the tree before this fix and in 2 of 60 on a clean `HEAD` build; the new simultaneous-start test hung in **8 of 8** runs against the pre-fix `host_exec.rs` and passed in all 200 runs above.

**Two infrastructure mistakes caught and corrected while setting this up** (the figures above are from the corrected runs only): the first start used a test binary that cargo had not rebuilt after the sources were restored (stale mtimes), so the binary was rebuilt with `touch` and its contents checked for the new tests before restarting; and the first audit counted its own `cat` as a leaked process (`procs_left=1` on every pass) until it was changed to use shell built-ins.

**What this does not show.** A finite number of clean runs bounds the failure probability, it does not prove the absence of other races. The identified cause (duplicate leaf names) is removed rather than made less likely, and the degraded mode that turned it into an indefinite hang is now bounded.

## 9. Remaining risks and open items

1. **Finite stress is not a proof.** See the stress numbers above; the original defect had a 3-5% per-run rate, and a clean 200 runs bounds, but does not eliminate, residual races. The fix removes the identified cause (duplicate leaf names) rather than lowering its probability.
2. **No writable cgroup ⇒ no descendant reach.** The degraded mode is now bounded and honest but cannot kill a `setsid` descendant (§3). The engine VM and the Fedora builder both have delegated cgroup v2.
3. **Guest kernel fault seen in the previous engine.** The engine that was running before the switch (kernel 7.2.13-200.fc44) had crashed with a NULL-pointer oops in the kernel's seccomp filter path (`seccomp_run_filters` → `0x0`, then `bpf_prog_free`), triggered by the guest's own `systemd-network` (uid 192) about 2 h 17 min after boot ("Fixing recursive fault but reboot is needed!"); its log is kept at `scratchpad/old_engine_console_kernel_oops.log`. The rebuilt image carries **7.2.15-200** (Fedora's repository moved on between builds); after the boot and two live runs it showed no fault, but that is hours of uptime not tested. If the fault recurs, the first mitigation to try is outside this work (pin or change the guest kernel, or relax `systemd-networkd`'s seccomp hardening in the image); I did not change either on a guess.
4. **Sandbox suites ran on the Fedora builder's kernel (6.19.10), not on the engine's 7.2.15.** The engine guest was exercised end-to-end (§8) but the sandbox/seccomp/Landlock test suites cannot be run inside the guest; the two live runs are the evidence on that kernel.
5. **Image size and offline builds.** The image grew by about 0.66 GB uncompressed (packaged 353 → 536 MB). Rust projects with crates.io dependencies cannot fetch them in the sandbox.
6. **Ad-hoc signature.** Fine for local use; distribution needs a Developer ID signature and notarization (unchanged since M4).
7. **The previous behaviour of `sandbox_a34::procfs_and_dev_expose_no_writable_host_controls`** depends on the launcher's `oom_score_adj` floor (documented in M4.3); all suites here were launched from the user manager.
8. The `rel2_` 140-turn marathon tests were not run. Nothing was committed or pushed.
