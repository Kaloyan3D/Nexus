# Command-execution investigation (benchmark run) — root cause, reproduction, fix

Branch `feature/linux-arm64-port`. Nothing is committed or pushed. The benchmark project and its results were not touched; the run was read from the engine's own durable records (run record, activity log, transcript) copied read-only from the engine VM's state disk, and everything else was reproduced in a controlled Linux test environment (Fedora 44 ARM64, real sandbox, real Kernel).

## 0. Verdict in one paragraph

**The sandbox, the allowlist, PATH propagation, the macOS→Linux bridge and the seccomp/Landlock rules were not at fault.** The benchmark run (`run_dbdb…`, 127 turns, 57 `proc_run` calls) had exactly **two** commands that did not start — `cargo --version` and `rustc --version` — because **the Linux runtime contained no Rust toolchain** (the engine image is Fedora-minimal + Node + Python + Chromium; no `cargo`, `rustc`, linker). The other **55 commands started and ran** (50 `run-pass`, 4 `run-fail`, 1 `pass`). What the person saw ("`sh -c` / Python commands → command not run") was a **display defect**: the UI worded every executed command that is not a verification check as "Command not run". On top of that the two real failures were reported with the **policy** code `command-refused`, although nothing was refused by policy: the programs simply do not exist. The agent therefore could not compile (a true environment limit) and spent ~12 turns probing the runtime, and the run ended `unexecuted-claims` / `unverified`.

The model then probed (`ls ~/.cargo/bin`, `find / -name cargo`, `curl https://sh.rustup.rs`, `pip install`, `command -v cc gcc …`) and found no Rust, no C compiler, and no network.

Same eight commands, through `prepare → authorize → execute`, under (a) a runtime **with** a toolchain and (b) **without** one (the engine VM's situation).

| Command | with Rust: stop / resolved / exit | without Rust: before the fix | without Rust: after the fix |
|---|---|---|---|
| `pwd` | process · `/usr/bin/pwd` · 0 | same | same |
| `ls` | process · `/usr/bin/ls` · 0 | same | same |
| `echo hello` | process · `/usr/bin/echo` · 0 | same | same |
| `cargo --version` | process · `/toolchain/cargo/bin/cargo` · 0 (`cargo 1.99.1`) | **resolver/authorization · `command-refused`** · never started | resolver/authorization · **`executable-not-found`** · never started |
| `rustc --version` | process · `/toolchain/cargo/bin/rustc` · 0 | **`command-refused`** | **`executable-not-found`** |
| `sh -c 'echo hello'` | process · `/usr/bin/sh` · 0 | same | same |

So: a missing program stops at the resolver (code `command-refused` before; `executable-not-found` now); every program that exists runs; and the shell-wrapped form `sh -c 'cargo --version'` reaches the shell, which exits 127 "not found".

## 5. Root causes

* **RC1 — the Linux runtime had no Rust toolchain.** `engine-image/Containerfile` installed Node, Python, Chromium libraries and tools but no `rust`/`cargo`/`gcc`. With nothing in `/usr/bin` and no `~/.cargo` (the daemon's `Toolchain::discover()` finds only rustup/cargo homes), `cargo`/`rustc` do not exist for the sandbox. This is the reason a Rust project could not be compiled; it is an environment limit, not a security rule.
* **RC2 — absence was reported as a policy decision.** `workbench.rs` (and the strict resolver) used `ToolErrorCode::CommandRefused` for "this program is not installed". The model, the run record, the UI and the controller could not tell it from a real policy denial (`/bin/sh` absolute path, too-long scripts, `cargo --version` under the strict profile, …).
* **RC3 — the UI worded every executed non-check command as "Command not run".** `progress.ts` handled only `verification === "pass" | "fail"`; the broker deliberately records commands that are not checks as `run-pass` / `run-fail`, so 54 of the 57 commands fell through to the "not run" line with a failed tone. This is exactly the reported symptom ("multiple sh -c / Python commands → command not run", "one shell-based verification invocation successfully executed").
* **RC4 (contributing) — the run-end note lumped different things.** `unexecuted-claims` said "refused, failed or never executed" for commands that never started *and* commands that started and exited non-zero.

## 6. Changes

| Area | Change |
|---|---|
| `nexus-tools` | New `ToolErrorCode::ExecutableNotFound` (`executable-not-found`). Used wherever a program is absent: workbench resolver (generic programs, shells, `tsc`/`npx`, `pip`/`python`), the strict resolver's missing `cargo`/`npm`/`python3`/`node`/`tsc`, and the Full-scope host resolver. The message states what was searched, that it is **not a permission decision**, that **nothing was run**, that retrying will not help, adds a Rust-specific line for the Rust family, and keeps the previous wording ("not available inside the authorized runtime", "does not fall back to host execution") so nothing that matched it breaks. Policy refusals keep `command-refused`. |
| `nexus-broker` | Refusal bookkeeping counts `executable-not-found` like other refusals (bounded repeats unchanged); background jobs carry the real code; exit 126/127 of an executed command is classified (`processClass`) and the model-visible result gets a plain note (this is the shell-wrapped form of the same condition); the run-end note separates "refused or not installed, so never executed: nothing ran" from "ran and exited with an error" (it keeps the existing phrase "never executed", see §11.2). |
| `nexus-client` | `ToolActivity.processClass`. |
| Nexus.app | Executed non-check commands read "Ran … · exit N" (never "not run"); exit 127/126 say a program inside is missing/not executable and that it is not a permission decision; refusal table explains `command-refused` (a rule about what may run) vs `executable-not-found` (not installed in the Linux runtime). |
| Engine image | `rust cargo rustfmt clippy gcc` added (`Containerfile`); resolved by the generic `/usr/bin` path, no new bind. Verified in a container: `cargo 1.99.1`, `rustc 1.99.1`, `cc 16.2`, `rustfmt`, `cargo-clippy`; `cargo check` and `cargo test --offline` compile, link and pass. Cost: about **+0.66 GB uncompressed** to the rootfs (1.17 GB → ~1.8 GB of the 3 GB disk). |

## 7. Security impact

* **No sandbox, seccomp, Landlock, mount, cgroup or approval code was changed.** No allowlist was added or widened; the workbench still has no name allowlist and the strict profile keeps its exact-argv table. The new error code only *relabels* an existing refusal; the command is refused exactly as before.
* No fallback to host execution was introduced (the message still says there is none).
* The toolchain added to the image runs inside the same sandbox (offline, read-only system, scratch writes only); `CARGO_NET_OFFLINE=true` stays set except for the explicit dependency-install class. It enlarges the guest's installed software (a larger patch surface and image), which is the price of being able to compile Rust.
* Classifying exit 126/127 is derived from the Kernel receipt (exit code + the process's own stderr) and only adds an explanation; it cannot turn a failure into a pass.
* The UI change only changes wording; it hides nothing (exit codes are shown).

## 9. End-to-end (Phase 6, `e2e_the_agent_compiles_reads_the_error_fixes_it_and_reports_the_real_test_result`)

Real broker, Kernel, approvals and sandbox on Linux with a Rust toolchain; minimal crate whose `add` is declared `-> i64` but returns `i32`. The agent: lists, reads `src/lib.rs`, runs `cargo check --offline` (**real rustc `error[E0308]: mismatched types`, exit 101**), fixes the signature from what the diagnostic says, re-runs `cargo check` (exit 0), runs `cargo test --offline` (exit 0), and its final answer carries the **actual** line the runtime produced (`test result: ok. 1 passed; 0 failed`). ## 11. What the regression run turned up (four items, resolved or explained; none needed a sandbox change)

**11.1 `sandbox_a34::procfs_and_dev_expose_no_writable_host_controls` failed when the suite was started from an ssh-launched `systemd-run --scope`; it passes when started the way the daemon is started. Not caused by this change, no sandbox code touched, test not modified.** A pristine copy of `HEAD` fails the same way, and `sandbox.rs`/`confine.rs`/the test are byte-identical to `HEAD`. The test writes `0` to `/proc/1/oom_score_adj`; inside the sandbox `/proc/1` is the sandbox's **own** `bwrap` (the PID namespace hides every host process, and it is the same uid), so the write is to a sandbox-internal process, never a host control. The kernel lets an unprivileged process set its own `oom_score_adj` anywhere between the *floor it inherited from its launcher* and 1000 (lowering below the floor needs `CAP_SYS_RESOURCE`, which `--cap-drop ALL` removes). An ssh-started scope has floor 0, so the no-op write of `0` succeeds; a process started by the user manager inherits the manager's floor (here 200) and the write is refused. Demonstrated: same binary, same tree, floor 0 → fails; floor 200 → passes; and a plain `bwrap` probe shows `/proc/1` is `bwrap` and writes there stay inside the sandbox. Impact: a sandbox process can make itself *more* likely to be OOM-killed, or put its own value back to its floor; it cannot affect anything outside. The test is launcher-dependent rather than wrong, and was left exactly as it is (weakening a security test to get a green run is not acceptable); the suite is run from the user manager here.

**11.2 A regression of mine, found and fixed: the run-end note no longer contained "never executed".** The existing test `demo_a_a_refused_command_is_never_laundered_into_a_passed_demonstration` asserts that wording. My `unexecuted_note_split` (§6) had dropped it. Restored in the new text ("…refused or does not exist in this runtime, so it was never executed: nothing ran (first: …)") while keeping the refused-vs-ran-and-failed split; my own `nf_…completion_note_separates…` expectation was updated to match. `demo_a`/`demo_b`, the four `nf_` tests, the end-to-end test and the completion unit tests all pass; the full `code_a56` run above is after the fix.

**11.3 `hostexec_m8` hangs intermittently on its own; this predates the change.** `m81_setsid_descendant_cannot_escape_cancellation` (Full Access host execution, M8.1) sometimes blocks forever: after a cancel, the test thread waits on the output pipe because the `setsid` heartbeat loop it started was not killed by the cgroup supervision, and the descendant holds the pipe open. Measured by running the compiled test binary alone, 60 times each: **current tree 3 hangs in 60 runs; a pristine `HEAD` build (separate target directory) 2 hangs in 60 runs**, and the stuck test and thread states (`anon_pipe_read` in the pipe-reader threads) were captured on the `HEAD` build. The only edit in `host_exec.rs` in this change is the error code for an absent program in `resolve_host_program`, which is not on the cancel path. It is not part of this investigation (Full Access host execution is not the sandboxed path the benchmark used), but it is a real supervision defect: see §12. The roughly 10-minute stall seen earlier in a full run was the same binary with the same symptom (the stuck test was not identified at that time).

**11.4 Test-environment note.** `model_only_a51::a51_executor_death_…` asserts that the `nexus` CLI binary (package `nexus-cli`) already exists; `cargo test -p nexus-daemon` does not build it, so it failed after the workspace-member artifacts were cleaned (to make sure no stale build was linked). Built `nexus-cli`, test passes (21/21). Not a code defect. Also learned the hard way: two source trees in one `CARGO_TARGET_DIR` share artifact names (workspace-member hashes are path-independent), so a pristine-`HEAD` comparison must use its own target directory; the `HEAD` baselines above do.

## 12. Remaining risks and limits

1. **The running app is unchanged until the engine image and Nexus.app are rebuilt.** The Rust toolchain only exists in `Containerfile` (verified in a container) and in the tests; the shipped engine image still has no `cargo`/`rustc`, so a Rust benchmark in the *currently installed* app would still stop at `executable-not-found` (now reported accurately, with the next step spelled out). Rebuilding also brings in the M4.2 Phase A work, which was never rebuilt into the app either.
2. **Image size.** `rust cargo rustfmt clippy gcc` add about 0.66 GB uncompressed (1.17 → ~1.8 GB of the 3 GB disk). No network in the sandbox: a crate that needs crates.io dependencies cannot be built in the offline class and needs the explicit dependency-install class.
3. **Capability is not advertised to the model up front.** The model still discovers what the runtime has by trying it; the new error says plainly what is missing and what to do, and the run-end note no longer calls the missing command a permission problem, but a pre-flight "this runtime has: …" line would save the ~12 probing turns seen in the benchmark. Not done (a prompt-surface change was out of scope).
4. **Exit 126/127 are classified after the fact.** `sh -c 'cargo build'` in a runtime without cargo reaches the shell, which exits 127; Nexus classifies it from the receipt (exit code plus the process's own stderr), not before it runs.
5. **The end-to-end test uses a scripted model.** The compiler, sandbox, Kernel, approvals and tool results are real; no provider key was used (standing rule), so the model's own choice to run `cargo check` is scripted.
6. **`hostexec_m8` intermittent hang (§11.3)** — pre-existing Full Access supervision race. A hung cancellation of a `setsid` descendant would leave that process running and the tool call blocked. Worth its own investigation (the suspect is the window between the child's pre-exec cgroup join and the supervisor's membership check/`cgroup.kill`); not fixed here.
7. **`procfs_and_dev_expose_no_writable_host_controls` is launcher-dependent (§11.1)** — it fails when the suite is started from a process whose `oom_score_adj` floor is 0. The production daemon is started by systemd, so it is not exposed, but CI should start the suite the same way.
8. The 140-turn `rel2_` marathons were not run. Nothing was committed or pushed.
