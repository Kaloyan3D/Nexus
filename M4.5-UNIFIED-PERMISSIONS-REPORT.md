## 1. Architecture and authorization model

**Ceiling vs. gate.** Three independent things decide what a command can do:

1. *The ceiling* — the task's frozen standing grant (filesystem scope, network scope `offline`/`install`/…, approval axis), unchanged. A mode never widens it. If a project's grant has no install network, no mode can install anything; the Desktop offers the existing native "allow dependency installs for this project" consent first (`project_allow_installs`) when a run starts.
2. *The gate* — new, in the broker (`nexus-broker/src/permissions.rs`, called from `inspect.rs` right before the daemon approval): the run's mode decides **run** or **ask the person first**.
3. *The daemon's own policy* — unchanged; whatever the gate lets through still passes the frozen-grant check, the sandbox and the journal.

**Classification** (`nexus-tools/src/permission.rs`): `Safe` | `Install(plan)` | `Delete` | `BulkDelete`. Install is decided by the **daemon's own resolver** (`CommandPolicy::resolve(...).install`), the same code that gives a command the install network, so the broker's gate and the daemon's network decision cannot disagree, and a shell wrapper cannot turn an install into a "safe" command or get it the network (tested). Deletions are read from direct programs and from `sh -c` scripts split into commands; scratch space (`/tmp`, `/work/env`, `/work/out`) and regenerable output (`target`, `build`, `dist`, `node_modules`, `__pycache__`, `.cache`, without `..` or globs) are not a decision for the person (found necessary in the live run, §5).

| Class | Ask for Approval | Auto Approve Safe | Full Access |
|---|---|---|---|
| Safe (builds, tests, reads, edits, local commands) | runs | runs | runs |
| Dependency install | **asks** | **asks** | runs, recorded |
| Single-file delete | **asks** | runs | runs |
| Bulk delete (`rm -r`, globs, `find -delete`, `git clean`, `git reset --hard`) | **asks** | **asks** | runs |

**A request** records the exact program, arguments and directory, a plan for installs (manager, operation, packages with constraints, options, whether it comes from the manifest) and a digest of run id + request id + kind + program + args + cwd. The command that runs after approval is the same `params` object the digest was computed from. A decision must repeat request id **and** digest, is single use (replays after consumption or after the run ends are refused), expires after 10 minutes, and is withdrawn on cancellation. An identical installation already approved in the run is covered by that approval ("approved-earlier"); a materially different one (other packages, options, manager, directory) asks again; any mode change ends the coverage.

**Mode changes.** Downgrades apply to the very next command and revoke daemon approvals created but not consumed. Upgrades need a single-use, 120-second token that the engine only issues together with its own confirmation text; the Mac app shows that text natively and only then presents the token. A pending request is released if the person confirms an upgrade to Full Access. A continuation of a run never inherits Full Access.

**Runs with no mode** (CLI, scripts, runs that predate modes) have **no mode gate**: the frozen grant alone decides, exactly as before. The Desktop always sends a mode (default Ask). This keeps every existing non-Desktop client working, and was necessary: defaulting those runs to Ask made 7 existing tests wait for a person who does not exist.

**Controller view.** A denial returns an explicit `permission-denied` result telling the agent nothing was run or installed and not to retry the same operation; expiry and withdrawal have their own codes. When a command fails because the sandbox is offline (cargo "no matching package … offline", npm `ENOTCACHED`, pip "No matching distribution", DNS failures) the result carries a note saying dependencies come from a direct install command that the person approves unless the run is in Full Access. The frozen tool catalog was not touched (guidance travels in results). A repeated refusing loop is bounded by the existing refusal counter. Mode changes never rewrite earlier activity: each command's record keeps the mode and decision in force when it was decided (tested).

## 3. Security impact

* **Unchanged:** sandbox, seccomp, Landlock, mounts, cgroups, the daemon's frozen-grant and approval machinery, the install network class, the frozen tool catalog. Full Access is "do not ask" inside the grant; it does not remove a boundary. Tested in a real sandbox: in Full Access `touch /usr/pwned` is still refused by the sandbox and a Full Access install still goes through the install class only.
* **No hidden host fallback.** Full Access does not select the separate M8 host backend (`fs=full`, `net=full`), which remains its own explicitly granted, separately disclosed capability. General network access (curl, `git clone`, arbitrary sockets) is **not** supported by this work and stays offline; the Controlled-Internet egress proxy and the M8 host network are separate existing capabilities that Full Access does not enable.
* **A design delta to know about.** Until now an `ask` approval was decided by a separate approver terminal holding a credential the broker never sees. The new permission decision is arbitrated by the broker (trusted code) on a decision that arrives from the person's authenticated local client (the Mac app, after a native confirmation). The model has no tool that can reach it, and the daemon's own independent approvals are untouched, but the broker is now the arbiter of this particular gate.
* **Approval binding:** request id + digest over the exact argv/cwd; single use; no replay; digest mismatch and unknown ids refused; renderer-supplied digests are ignored in favour of the engine's.
* **Shell wrapping / command chaining:** an install inside `sh -c` is not an install (no gate bypass, **and** no network). A deletion inside a chain is found per command segment. Both tested.
* **Secrets and host paths:** unchanged isolation (the sandbox has no access to other Mac folders, `$HOME` or credentials); the native dialogs show only the engine's record; no credential was read by any new code or test.
* **Audit:** every request, decision, auto-run, mode change and revocation is an entry with time, mode, request id and digest; every install is a ledger entry with the exact command, decision and exit code; both are on the run record and survive restarts with it.

## 7. Remaining limitations

1. **GUI not observed by a person** (§5). Please try: send a message with each mode, approve/deny a request, switch modes mid-run, and read the dialogs.
2. **"Approve once" covers identical repeats** in the same run (so the agent is not asked 7 times for the same `cargo fetch`); a different installation asks again; a mode change resets it.
3. **Package list on manifest-driven installs** (`cargo fetch`, `npm ci`, `pip -r`) is shown only when the model wrote the manifest with a file write in this run; if it edited it with `fs_edit` (scenario A did) the card says "everything the project's manifest and lockfile declare". The request still shows the exact command.
4. **"Sensitive filesystem operations"** in Ask mode means deletions (direct or in shell scripts, as classified above). Ordinary writes inside the throw-away working copy are not gated (it is disposable; the Mac write-back has its own verified-result policy). Deletion detection is heuristic (words in commands/scripts); a deletion hidden inside an interpreter one-liner (`python -c`, `find -exec` variants) is not recognised, and a bare word `rm` in a script is treated as a deletion.
5. **No general network.** Only the package-manager install class has network. `curl`, `git clone`, arbitrary sockets remain offline; Controlled Internet and M8 host network exist separately and are not enabled by any mode.
6. **Per-run, in memory:** upgrade tokens, approval coverage and the manifest display cache live in the broker process; a broker restart drops them (safe direction: the next install asks again) and does not resurrect a pending request.
7. **Install ceiling is per project.** If the person declines the native "allow dependency installs" consent, installs are refused with the daemon's message in every mode.
8. **The broker is the arbiter of this gate** (§3), unlike daemon approvals, which keep their separate approver.
9. Not run: the 140-turn `rel2_` marathons. Live scenarios used scripted dialogs and one provider.
