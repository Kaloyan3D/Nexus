# M4.7 — Evidence Precision, Prefix Stability & Dynamic Reasoning: Report

Branch `feature/linux-arm64-port`, uncommitted (no authorization to commit or push was given). Companion document: [M4.7-DYNAMIC-REASONING-COMPARISON.md](M4.7-DYNAMIC-REASONING-COMPARISON.md) (the Phase 0 audit).

## 1. Executive summary

- **The benchmark's false `verified-failed` is fixed without creating false positives.**
  - The deterministic replay of `run_faf5…` reproduced the original verdict exactly before any change.
  - After the change, exactly the four `… | grep -i 'warn'` calls differ: they become *unverified obligations*, not failures.
  - Every open obligation now carries a re-check the controller provably accepts.
  - The run is labelled `unattested-checks`: not `verified-failed`, and not passed.
  - A real-sandbox end-to-end test shows the benchmark shape now ends `verified-passed` once the model runs the filter-free re-check.
  - The five masked-failure shapes stay unattested, and writeback still blocks every unverified result.
- **The strategy report got DSH's reasoning wrong.** DSH's adaptive governor was active and its effective effort was **medium**, not xhigh. Native runs the same governor, byte for byte. Native switches effort more often because it *sees* verification failures (foreground checks); DSH never did (background builds).
- **Reasoning replay: the new default is `append-only`, with request-budget hysteresis.** The choice is provisional: one scheduler run per arm.
  - On the M4.7 engine the scheduler cache hit went from **71.4% (`window`) to 89.3%** (default). The benchmark baseline was 76.9%.
  - `none` (DSH's choice for this route) needed **2× the requests, 2× the uncached input and 2× the list cost** of append-only on the scheduler. On the inventory task it used 2.9× the reasoning tokens: without replay the model re-derives its reasoning. Best cache-hit rate is not the best outcome.
  - The live A/B exposed a second prompt-rewrite mechanism: the sealed 440 KB request budget trimmed one replayed item per turn. It is fixed with hysteresis (`REQUEST_BUDGET_VERSION` 2).
- **Effort.** The governor's escalations are kept (provisional).
  - The pinned-low "stable" engine was the cheapest and fastest on **both** tasks: scheduler 7 min, 45 requests, $0.04 list price, verified and applied.
  - Its generated project passed its own tests, as every arm's did; there is no independent quality signal that separates them.
  - Whether low effort holds up on harder work is the main M4.8 experiment (§6).
- **Performance root cause narrowed, not fixed.**
  - Cold `cargo fetch` of the benchmark's lock file: 3.8 s on the Mac host, 58–146 s on the Linux builder VM with no Nexus proxy, 283 s in the engine.
  - Linux-guest networking on this Mac is the dominant factor; the egress proxy adds the rest.
  - The controller's per-request pre-send work is now measured: about 530 ms.
- **New defects found and fixed along the way** (all in the final build):
  - A read-only classifier false positive ("Do not modify anything under `test/`"), confirmed live.
  - Per-turn prompt rewrites from the request budget.
  - An inflated decode-rate metric on short replies.
  - Wall-clock telemetry corrupted by a guest clock jump; durations are now monotonic.
- **Independent acceptance** (13 black-box tests, outside both generated repos): Native 10/13, DSH 10/13. They fail on different defects, plus two shared ones (process-group kill).

## 3. Verification controller: root causes and fixes

**Root causes:**

1. A derived re-check kept a trailing selecting filter (`| grep -i warn`). Under the Kernel's pipefail, a clean build makes it exit 1.
2. A non-zero status of a check pipeline was attributed to the check even when only the trailing filter could have produced it.
3. The re-check named for an unanalysable hazard (a `for` loop) was not one `satisfies` accepts.
4. A failed *compound* check could never clear: re-running it as written attests nothing.
5. The final-boundary guards spent their budget on the false failure, and the model was never told about the two other open failures.

**Fixes:**

- `compose.rs`: per-stage spans; check forms drop trailing pure output filters (`grep egrep fgrep rg head tail wc sort uniq cut tr cat sed`; never `tee`, `awk` or in-place `sed`).
- `filter_status()`: exit 1/2 under applied pipefail, with a check-bearing pipeline ending in a selecting filter, becomes an *unverified obligation* whose re-check is the filter-free command. Never a pass.
- Plain re-checks for unanalysable hazards whose checks are literal. When a check uses expansions, the guard says honestly that no re-check exists.
- `inspect.rs`:
  - A failed compound check is cleared by an attested pass of all its checks (`resolvesFailed` on the activity).
  - A re-check that ran and failed is never repeated.
  - Identical obligations are joined (`*-joined` classes) instead of multiplied.
  - One bounded final-boundary message names **every** open obligation with its exact command: at most 3 per run, each hazard at most 3 times.
- Client outcome, UI wording, and model notes (`nexusRecheck` on filter-status results).

## 6. Dynamic effort experiments

- Adaptive (the governor plus limiter) and the existing pinned engine (`stable`: route `opencode-go-native/muse`, effort **low**) both passed every hidden check on the inventory task.
- Pinned-low cost 56% less (list) with 66% less uncached input there.
- On the hard task (scheduler), see §5.
- On the scheduler, pinned-low was the fastest and cheapest run (7 min, $0.04) and produced a project whose own tests pass. Adaptive with append-only took 14.7 min and $0.09.
- **Decision (provisional):** keep adaptive escalation as the default.
  - One run per arm cannot show that low effort is as reliable on harder tasks.
  - Low effort remains available per run as the "stable" engine.
  - Effort changes now account for most of the remaining uncached input (292 k in the final run), so a cache-aware limiter (longer dwell, under a new `state_schema`) is the M4.8 experiment.

## 8. Token, time and cost comparisons; performance

- **Dependency fetch** (cold, same `Cargo.lock`, 75 crates): Mac host 3.8 s (warm 0.18 s); Linux builder VM (UTM NAT, no proxy) 146 s and 58 s on two runs (index phase about 30 s); engine 283 s (benchmark).
  - The guest showed one 61 s dual-stack request, then 0.07–0.3 s once warm; IPv6 has no route and fails immediately.
  - Most of the cost is the guest network path, not the Nexus proxy. A persistent registry cache would remove it for every warm project (M4.8).
- **Builds on the builder VM** (6 vCPU / 11 GB): clean debug build 16.8 s, tests 11.2 s. On the Mac: release build about 28 s per project.
- **Controller pre-send per request**, live: attempt record 102 ms, intents 160 ms, Engineering Mode consult 15 ms, target 26 ms, bind 20 ms, publish/accept/authorize 208 ms. About 530 ms total, out of about 650 ms of controller time per request in the benchmark.
- **Provider transport:** `connection: close` remains. With pre-send measured, connect and TLS can now be isolated (M4.8).
- **Telemetry fixes found live:**
  - A guest wall-clock jump (+26 min) inflated one run's controller time. Durations now come from a monotonic `runElapsedMs`, and skew is reported.
  - The decode rate needs ≥ 256 visible tokens over a ≥ 1 s window (it showed 873 tok/s on two-line replies).

## 12. Remaining risks

- One scheduler run per arm: the cache difference is clear (deterministic mechanisms, confirmed live), but quality differences between arms are not established. Every project passed its own tests; the black-box suite cannot be applied without per-run CLI adapters.
- The hysteresis trims more replayed reasoning than strictly necessary when a request is over budget (down to 7/8 of the limit). It is quality-neutral in the runs so far, not proven in general.
- `filter_status` treats any exit 1/2 of a check piped into a selecting filter as ambiguous. A genuine failure that exits 1 becomes an open obligation (never a pass) and is confirmed by the re-check.
- Both generated schedulers lack process-group termination and single-instance protection. That is generated-code quality, not harness behaviour.
- The guest network path (DNS or NAT latency) is not yet diagnosed to a single cause.

## 13. Recommended M4.8

1. **Dependency acquisition:** a persistent, shared, content-addressed registry cache on the state disk (warm 0.2 s vs 283 s), plus a guest network-path diagnosis (resolver, NAT, IPv6), keeping the egress policy.
2. **Cache-aware effort:** a limiter `state_schema` that prices re-prefill; A/B over ≥ 5 scheduler runs per arm with the independent acceptance.
3. **Transport:** isolate connect and TLS cost; connection reuse if attestation guarantees hold.
4. **Benchmark methodology:** per-run CLI adapters, so the black-box scheduler suite applies to every generated project.
5. **Sandbox usability:** tell the model the cargo target directory (`/work/env/target`) in exit-127 notes and the tool description. The final run lost 37 requests to `./target/...` paths and a never-exiting `run` command.
6. **Pinned-low vs adaptive** on harder tasks (≥ 5 runs per arm), since pinned-low was the cheapest and fastest on both tasks here.
