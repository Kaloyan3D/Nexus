# Nexus CLI contract · proposed v1

The Nexus CLI is the product's public task client. It uses the same trusted task API as the GUI and the same DSH Agent Loop as any engineering session. Arthur Studio exports Markdown and invokes this interface. The CLI works with a text terminal, a script or a GUI-driven process launcher.

## 2. Commands

| Command | Behavior |
|---|---|
| `nexus host start [--json]` | Explicitly start or join the approved local host. Return only after an authenticated Controller readiness check. Idempotent under parallel starts. |
| `nexus host status [--json]` | Read authenticated host identity, API version and readiness. Does not start anything. |
| `nexus workspace add --path <dir> [--json]` | Explicit local owner operation to register an existing authorized directory for terminal-only setup. It does not submit a task or grant another principal access. |
| `nexus modes [--json]` | Return authorized public mode IDs and readiness for the caller. The host maps IDs to preset, registry resolution and strategy. |
| `nexus submit --workspace <dir> --mode <id> <prompt-source> [--idempotency-key <key>] [--json]` | Return a durable submission receipt after task/session binding and durable queue admission. This is the automation command. |
| `nexus run <same submission flags> [--interactive] [--timeout <duration>] [--json]` | Submit, then follow the authoritative task. Human progress goes to stderr. A TTY may answer advertised approval requests when interactive. JSON mode is non-interactive and returns one final response. |
| `nexus status <task-id> [--json]` | Return current authoritative projection without activating an agent. |
| `nexus wait <task-id> [--timeout <duration>] [--interactive] [--json]` | Follow or reattach to a task, including a task submitted elsewhere. Returns on terminal outcome, actionable hold in non-interactive mode, timeout or disconnect. |
| `nexus result <task-id> [--json]` | Fetch the result or the current non-terminal/held state. No wait and no implicit verification. |
| `nexus cancel <task-id> [--json]` | Request cancellation. Receipt exposes the committed state, usually `cancelling`. Use wait/status to confirm settlement. |
| `nexus respond <task-id> --request <id> --choice <advertised-choice> --revision <revision> [--json]` | Answer one current authorized request. GUI and CLI share first-valid-response arbitration. |

`<prompt-source>` is exactly one of `--prompt <text>`, `--prompt-file <path>` or `--stdin`. No implicit read from a terminal or a pipe. Human prompt flags are convenient for short text. File or stdin is preferred for longer or sensitive content since command-line text can appear in shell history and process listings. `--workspace` and `--mode` are required for submissions in v1. For example, existing mode IDs can be `engineering-v1` and `engineering-v2` after parity. The host may advertise `nova-auto` and explicit strategies later. Unavailable modes are refused with a code. The CLI has no list of valid strategy IDs in its parser. Submissions require an existing authorized workspace. Register it explicitly through the GUI or `nexus workspace add`. Registration and task authorization are distinct. `--timeout` limits waiting, not task runtime or budget.

Commands discover the selected installed root through their launcher, never a project-local executable or an arbitrary environment-provided endpoint. `submit` and `run` require a ready host. The CLI returns `HOST_UNAVAILABLE` with a start hint when necessary. Read commands and `cancel` do not start a host as a side effect. v1 supports same-host operation only.

## 3. Input and provenance

- Resolve relative prompt-file/workspace inputs against the invoker's cwd. The client may read a prompt outside the workspace so Studio can export in its own directory. Reject non-regular files, devices, directories, symlink/reparse-point prompt inputs and unsafe opens. Open the file using a platform-appropriate no-follow check, validate the opened descriptor and read bounded bytes from that descriptor. Define explicit handling for an intentionally resolved trusted input directory, and reject a raced path change. The host receives prompt bytes/text, never a request to open the client's file path. It cannot be tricked into reading privileged server files through the handoff.
- Initial limits are 256 KiB of UTF-8 input, 16,384 prompt tokens and a server-side budget derived from the authorized model window minus prompt/tool/context/output reserve, using the strictest applicable cap. Confirm those defaults on the parity workload. Read at most limit plus one byte from file/stdin and reject oversized input before decoding or JSON allocation. Reject invalid UTF-8, NUL and whitespace-only input. Allow and remove one leading UTF-8 BOM, preserve remaining characters including line endings, and hash the exact UTF-8 bytes of the submitted text as `sha256:<64 lowercase hex>`. Validate host-side byte count and digest again. When exact token counting is unavailable, enforce a validated conservative bound or reject with `PROMPT_BUDGET_UNVERIFIABLE`. Never silently truncate.
- The authenticated request carries a workspace candidate. The Controller re-resolves it against its authorized, existing workspace registry, canonical repository and execution root. Enforce installation/tenant/principal grants and a path containment check after symlink/reparse/volume resolution. Do not create an arbitrary directory or authorize a new project as part of submission. Capture the resulting workspace/repository ID and cwd in the binding and verify again before dispatch and on resume. Case-fold only where the host filesystem requires it.
- Record digest, byte count, source kind `text | file | stdin` and authenticated principal, plus an optional bounded informational label. Omit the original absolute prompt-file path from persisted records. The Controller persists prompt content only in protected intake until it can prove the prompt is in DSH history. The DSH transcript owns the accepted message and obeys existing retention policy. Server logs and status output omit raw prompt text by default.
- Submit Markdown as a single DSH user message. Treat headings, YAML front matter, links, embedded shell text and instructions as user content. They cannot change task scope, mode, permissions, risk floor, provider, budget, approval or credentials. Fetching referenced paths or URLs remains subject to normal tool authorization.

The owner-only workspace setup operation validates the canonical existing execution root under installation policy, resolves the existing Nexus repository/checkout identity and uses DSH's `workspaceRegistry.create` for idempotent registration. Apply the same validation to managed GUI registration. Authenticated owner intent is required, and a task client without workspace administration cannot grant itself access. An already configured Studio/CI integration needs only submit and observation. ## 4. Shared task API and delivery

**Proposed Nexus operations** are `hello`, `listModes`, owner-only `registerWorkspace`, `submit`, `getStatus`, `getResult`, `follow`, `cancel`, and `respond`. Local IPC and admitted Web routes are two adapters to these operations. They construct the principal from authenticated transport identity and share policy. A request cannot specify its principal or the implementation provider. Use one versioned command schema. The UI can retain its existing legacy displays and DSH conversation controls during cutover. For managed tasks, browser prompts, queue edits, model/preset/permission changes and raw DSH turn cancellation must be prevented from bypassing task admission. Gate all exposed mutation routes for those sessions, including browser/API peers, while preserving ordinary legacy behavior.

**Pinned gateway limit.** DSH creates the browser/API launch-token peers as `owner`. The gateway skips `remoteAccess.decide` for that principal and owns the only `/api` interceptor. Registering a second interceptor or configuring non-owner policy therefore does not protect managed sessions. In P0, trace actual unary HTTP and WebSocket paths and prove a supported guard for each mutation. The `connection/request` middleware is a candidate for HTTP, with separate coverage required for other routes. An independent Controller admission check must still guard every model/tool effect. If a supported complete guard is unavailable, carry a narrowly scoped, version-pinned upstream compatibility change or keep managed admission disabled. Do not claim GUI/CLI parity from client control visibility. [Owner peer](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/connection/src/rpc-host.ts#L94) · [Gateway access](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/api/gateway/src/index.ts#L793) · [Interceptor registration](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/connection/src/rpc-host.ts#L285)

**Existing mode completion.** A legacy turn that needs explicit verification projects `awaiting_operator` with a `run-verification` choice. `respond` dispatches the existing Controller verification path for that exact task and attempt, using the same semantics as the legacy `/verify` command. Advertise legacy review or gate actions only where policy and mode allow them. Muse continues to refuse independent review. This makes the legacy CLI usable through completion without GUI input or new legacy auto-review behavior. For managed submissions, typed actions invoke command handlers. Initial Markdown that happens to begin with `/verify` or `/review` remains a task prompt. Existing unmanaged slash commands keep their semantics. It allocates an opaque external `taskId`, a DSH `sessionId` and a prompt submission ID. Reuse the key only for identical canonical workspace, requested mode and content digest. ## 5. Wire and JSON output

Recommended v1 wire uses bounded HTTP JSON over the private IPC channel. Path `/v1/commands/<operation>` uses POST for commands. Host hello negotiates major 1 and advertises capabilities. All operations except hello use a strict `{ "schemaVersion": 1, "requestId": "<opaque UUID>", "input": { ... } }` envelope. The idempotency key is independent of the transport request ID and is a 1–128 character printable identifier. Enforce a separate bounded request envelope before parsing, initially 2 MiB to allow worst-case JSON escaping of the 256 KiB prompt. Reject unsupported major versions and unknown write fields. Consumers tolerate additive optional response fields and unknown error codes while honoring the v1 exit class. UTC timestamps use RFC 3339. Task and session IDs are opaque case-sensitive strings.

```json
{
  "schemaVersion": 1,
  "requestId": "43c70446-b2cb-4338-b56d-eab6f64e8bfb",
  "input": {
    "idempotencyKey": "studio-export-613-r2",
    "workspace": "/projects/example",
    "mode": "engineering-v2",
    "prompt": {
      "kind": "file",
      "text": "# Exported idea\n\nImplement the documented acceptance criteria.\n",
      "digest": "sha256:23302796318566b1a166555f85ae388ce649230d9b88a7194d07d81ced9f8f88"
    }
  }
}
```

| Operation | Input shape | Success data |
|---|---|---|
| `hello` | Supported schema majors and a request ID, after local peer authentication | Negotiated major, install and host generation IDs, pinned build, readiness and supported operations |
| `registerWorkspace` | Existing directory `path` | Authorized `workspaceId` and registration disposition |
| `listModes` | Empty object | `modes[]` with opaque ID, label, readiness and safe blocked reason when applicable |
| `submit` | See example. Required mode, workspace, idempotency key and prompt object | Acceptance receipt below |
| `getStatus`, `getResult` | `taskId` | Task view or Result below |
| `follow` | `taskId`, optional decimal `afterRevision`, bounded `waitMs` | Current Task view, or `unchanged` with current revision. Return full view when a cursor is older than retained history |
| `cancel` | `taskId` | `taskId`, `revision`, current status and disposition `requested`, `already_requested` or `already_terminal` |
| `respond` | `taskId`, `actionId`, decimal `expectedRevision`, `choiceId` | `taskId`, `actionId`, resulting revision and disposition. First valid decision wins, duplicate same decision can return its prior receipt |

A successful `submit --json` returns one envelope. A retry returns the original acceptance receipt, even if the task later completed. Query status for current state.

```json
{
  "schemaVersion": 1,
  "ok": true,
  "requestId": "43c70446-b2cb-4338-b56d-eab6f64e8bfb",
  "data": {
    "taskId": "nt_257aed7b",
    "sessionId": "session-3ac1bd11",
    "status": "accepted",
    "mode": "engineering-v2",
    "revision": "1",
    "idempotencyKey": "studio-export-613-r2"
  }
}
```

`status` and `result` use a shared view. The result adds bounded summary, evidence/artifact references and outcome. Operator actions are a separate array keyed by exact request ID and revision. Required checks, review and disposition are explicit, including when a legacy mode has no review policy. A nonzero task-outcome exit can still carry an `ok: true` result envelope if the query succeeded. An operation failure uses `ok: false`.

| Type | Required v1 fields |
|---|---|
| Task view | `taskId`, `sessionId`, `workspaceId`, `mode`, `strategyId` (nullable), `revision` (decimal string scoped to task), `status`, `attemptId` (nullable), `updatedAt`, `verification`, `review`, `operatorActions`. `displayId` is optional and is never an API lookup key. |
| Status enum | `accepted`, `queued`, `running`, `verifying`, `reviewing`, `awaiting_operator`, `blocked`, `cancelling`, `completed`, `failed`, `cancelled`, `interrupted`. The final four are terminal. Blocked/awaiting operator are holds and can have advertised transitions. |
| Verification | `state: pending \| running \| passed \| failed \| unavailable \| not_required`, `required`, `snapshotDigest` (nullable), bounded check summary and evidence references. For Nova, completion requires actual required check receipts. |
| Review | `state: pending \| running \| passed \| findings \| inconclusive \| unavailable \| timeout \| budget_exhausted \| cancelled \| error \| not_required`, `required`, `snapshotDigest` (nullable), bounded severity/count summary, findings references and provider when present. An exemption carries a policy reason. |
| Operator action | `id`, `kind`, `revision`, safe label, deadline, and `choices[]` with IDs and labels. Status redacts anything the principal cannot observe. `respond` sends task ID, request ID, expected revision and chosen ID. |
| Result | Task view plus `outcome: completed \| failed \| cancelled \| interrupted \| pending`, bounded summary, `snapshotDigest` (nullable), authorized artifact/evidence reference IDs and typed failure reason when present. Paths outside the requested workspace and reviewer internals are private. |

Error envelope example follows. `retryable` means retry using the same idempotency key when relevant. `taskId` is included only when allocated and authorized to disclose. `details` is an optional allowlisted object, never a stack trace or provider response.

```json
{
  "schemaVersion": 1,
  "ok": false,
  "requestId": "43c70446-b2cb-4338-b56d-eab6f64e8bfb",
  "error": {
    "code": "HOST_UNAVAILABLE",
    "message": "Start the Nexus host with nexus host start.",
    "retryable": true
  }
}
```

| Exit | Meaning and example error codes |
|---:|---|
| 0 | Command succeeded as a command. For `submit`, durable acceptance. For `status`, a successful read at any task status. For `cancel` and `respond`, committed request disposition. For `run/wait/result`, only Controller-confirmed `completed`. |
| 2 | Invalid request or local input. `USAGE`, `PROMPT_UNREADABLE`, `PROMPT_INVALID_UTF8`, `PROMPT_LIMIT`, `PROMPT_BUDGET_UNVERIFIABLE`, `WORKSPACE_INVALID`, `MODE_UNKNOWN`. |
| 3 | Connection or compatibility failure. `HOST_UNAVAILABLE`, `HOST_NOT_READY`, `HOST_IDENTITY_MISMATCH`, `PROTOCOL_UNSUPPORTED`. |
| 4 | Refused operation. `AUTH_REQUIRED`, `FORBIDDEN`, `NOT_FOUND` (also conceal foreign task IDs), `MODE_UNAVAILABLE`, `REQUIRED_CAPABILITY_UNAVAILABLE`, `IDEMPOTENCY_CONFLICT`, `STALE_ACTION`. |
| 5 | Authoritative task failure. The structured result identifies failed verification, failed repair budget, execution error or other recorded reason. |
| 6 | Authoritative task `cancelled` or `interrupted`. |
| 7 | Current `pending`, `awaiting_operator` or `blocked` result, or wait deadline reached. Distinguish by envelope and status. |
| 8 | `INTERNAL`, `STORAGE_UNAVAILABLE` or `SUBMISSION_UNCERTAIN` after an unconfirmed commit/response. Use the original key for reconciliation. |
| 130 | Client interrupted or detached by SIGINT. Does not cancel work. If acceptance is known, include task/session IDs in the final response when the output stream is still usable. |

With `--json`, stdout contains one UTF-8 JSON document and a newline, including expected errors, and stderr carries optional diagnostics. `run --json` and `wait --json` suppress human progress. Interactive mode requires a TTY and is mutually exclusive with JSON and piped stdin. Abrupt process or pipe loss may prevent a response, so the caller must handle transport interruption separately. Future explicit event output can be a separate documented NDJSON mode. Terminal output strips control sequences from model, tool and reviewer text.

## 6. Host ownership, transport and operator interaction

**Discovery and startup.** The host publishes an atomic, owner-protected descriptor under the canonical installation data root only after Controller readiness. Include installation identity, protocol, endpoint, generation nonce, PID/start identity, approved profile/build and readiness. Validate root ownership, directory/file type, path traversal and ACLs before connecting. Require an authenticated handshake binding the same installation, protocol, nonce and build. A stale PID, ordinary HTTP success or browser token in a log does not establish ownership. Existing `aih-state.json` is a hint. An older host without the task API returns an upgrade-required diagnostic, and is neither stopped nor competed with automatically.

**Single host.** Route GUI launcher and `nexus host start` through the same startup election. Reuse tracked-process diagnostics, with a cross-process startup mutex and a separate lifetime exclusive writer guard bound to canonical installation and session store identity. Both launch paths use the pinned DSH binary and identical product composition. Acquire the lifetime guard before DSH opens stores and keep it through shutdown. A supervisor owns it or the host proves it has inherited the guard. The guard must survive launcher exit and exclude a second approved launcher. Refuse a still-running old host or uncertain ownership. Verify the platform's non-expiring kernel ownership mechanism and process teardown in real-host tests. If the supervisor dies before the writer, the guard must remain held by the writer or a successor must prove that it is gone before opening stores. No TTL, lock-file deletion or PID guessing as failover. DSH's per-session write handle remains a separate protection. HMR of the engineering composition stays disabled. Manual handoffs and upgrades drain or park and preserve readers. The current stop path can force-kill a tracked process. For a managed host, have stop/update request drain through a separate authenticated local owner lifecycle operation and verify process death before releasing ownership. Forced recovery is a distinct operator action with uncertain work reconciled on restart. [Current stop path](../../scripts/Stop.ps1#L43) · [Force fallback](../../scripts/Startup.ps1#L198)

**Transport and authentication.** Use a private local socket on POSIX, in an owner-only directory with an owner-only socket. Use a local named pipe on Windows with an explicitly verified owner/service ACL and remote access rejected. If the packaged runtime cannot establish and test that ACL, Windows stays unavailable for this feature until a secure implementation is available. Use a random per-host-generation capability in separate owner-readable metadata, never argv, logs, browser URL or project configuration. Authenticate both endpoints before sending prompt bytes, by a reviewed mutual challenge-response binding fresh nonces, both roles, the installation and the host generation to the same connection. Expire each challenge, use constant-time proof checks and close on auth failure. Rotate the capability on restart and revocation. Bind the authenticated connection to a server-resolved local principal, task operations and installation. Close and reauthenticate on host generation change. Keep the browser transport behind existing `ctx.connection.admit` and enforce the same task authorizer above both transports. DSH `/connect` exchanges its launch token for an API Peer, so scraping that token would grant broad browser/runtime access. The Nexus task client uses its own scoped boundary. [DSH connect exchange](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/connection/src/browser-auth.ts#L308) · [DSH admission](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/connection/src/rpc-host.ts#L122)

v1 targets an authorized local installation account. Studio and local CI can run the client under that account, subject to the installation's workspace and mode grants. Cross-user or remote delegated automation requires a separate scoped credential and identity design. Same-user file permissions alone cannot protect credentials from unconstrained worker processes. The worker and verification sandbox must deny the IPC endpoint, descriptor, protected ledger and credentials. The launch environment must avoid exposing private capability material to children. Test denied arbitrary paths, parent cwd changes, endpoint impersonation, browser-origin requests, log leakage and credential replay.

**Detach and recovery.** The long-lived host owns agents and subprocesses. A CLI exiting after submit, terminal hangup or Ctrl-C releases the client subscription. It does not release ownership of a task. The host continues under normal budgets or waits for an operator. There is no promise of execution while the host is down. On explicit host restart, reconcile journal/intake, task binding and DSH durable state under the same identity before reopening work. Only continue safe queued operations under a matching pin. Classify interrupted active tools, verification, Sentry or uncertain publish/merge instead of replaying side effects. Report resumable holds through status. A crashed host cannot leave an accepted task invisible.

**Cancellation.** First persist `cancelling` and revoke new effect and provider admission. Withdraw pending approvals and task-owned inbox work, abort active verification/review and children, and cancel and await the exact owned agent and process tree. DSH's browser `session.cancel` retains the inbox, so it cannot implement task cancellation on its own. Use the Controller's scoped Agent APIs and job/worker disposers, flush session and task state, then record `cancelled`. A stubborn process or unknown mutation holds/quarantines the task. Duplicate cancellation is idempotent. A concurrent completion and cancel race resolves in the Controller's conditional transition. [DSH cancel contract](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/api/session-controller/src/index.ts#L511)

**Approvals.** Tool approvals, user questions and Controller review/operator gates are different requests. For managed sessions bridge the documented DSH `approval/request` and `user-questions/request` waterfalls through one trusted scoped interaction broker. Keep DSH policy evaluation and audit events. The broker offers a task-bound request with opaque ID, deadline, choices and revision, to authorized GUI/terminal humans. An answer resolves the original live request once. Refuse stale, foreign, replayed and altered action IDs. A disconnected terminal does not grant approval. The host may offer the request to another authorized client until the bounded deadline. Missing or expired approval fails closed, and any interrupted question is reconciled after restart rather than replayed as an approval. Non-interactive submissions cannot prompt on stdin or authorize themselves. Existing unmanaged browser approval behavior stays on the DSH path. If the bridge cannot safely arbitrate both clients or the required user question cannot be serviced, the task stays held or denied. A gate decision cannot substitute for a required verification or Sentry receipt. ## 7. Arthur Studio usage and support gates

Studio resolves the installed Nexus invocation, runs it with an argument array and no shell interpolation, saves its export's idempotency key, and uses one of the server-advertised modes. The operator registers and grants the workspace once before configuring this integration. For a local legacy-compatible smoke flow after P2:

```sh
nexus host start --json
nexus modes --json
nexus submit --workspace /projects/example --mode engineering-v2 \
  --prompt-file ./idea.md --idempotency-key studio-export-613-r2 --json
nexus status nt_257aed7b --json
nexus result nt_257aed7b --json
```

Use the actual returned task ID and follow advertised operator actions, including explicit verification for a legacy task when required. Choose an advertised Nova mode when available to obtain the Nova verification/Sentry contract. In an automation client, treat exit 0 from `submit` as acceptance and poll status or use `wait`. Inspect operator actions and final outcome instead of reading DSH transcripts. A retry after a lost response uses the original key and exact payload. Store the IDs locally as references. Nexus never calls back into Studio or queries its data store for the MVP.

Release by tested OS and installer channel. Native macOS arm64 and Linux aarch64 have historical Web-host evidence only. This audit proves no CLI OS cell. Linux x86_64 and Windows require fresh end-to-end evidence, including executable quoting, Unicode/CRLF/BOM, path aliases, pipe ACLs, process/session ownership, launch without a desktop, disconnection, wake/restart and install/uninstall. Use synthetic credentials, disposable installations and an egress-blocked model transport. Keep existing pinned installer paths until each platform meets the roadmap gates.
