## 2. Why DSH never escalated: an evidence gap, not a better policy

`Muse-ReasoningActivity.cjs` classifies verification only from **foreground** shell results. A background job is recorded as `started` (lines 393–402). DSH ran every `cargo build` and `cargo test` as a background job and read the output through `job_output`. The governor therefore never saw a failure, never entered `recover`, and the effort never moved. DSH's prompt stayed byte-stable for a different reason: replay is off and no switches happened. Its effort policy did no better in this run; it simply had no failures to react to.

## 3. Native: same governor, different evidence

- Native evaluates the **same historical modules, byte for byte**. `governor_bridge.rs:24–28` uses `include_str!` on the repo `config/Muse-Reasoning*.cjs` and runs them in a sandboxed Node bridge.
- On top of that, Native adds `effort_limiter.rs` (Policy V2): dwell of 2 consecutive lower decisions before moving down, and re-arm tokens. The host re-derives every transition.
- Native's verification runs in the **foreground** under the Kernel, so failures are trusted evidence, and every fail/fix cycle moves recover (high) → implement (medium).

**The 11 switches in `run_faf5`:**

| Request | Switch | Trigger |
|---|---|---|
| 5, 7 | medium → high → medium | Model signal (design) in the early planning burst |
| 28, 44, 86 | medium → high | Real failed verifications: offline build, lock-contention test failure, integration failure |
| 35, 83, 95 | high → medium | After the fix or the next pass |
| 114, 119 | medium → high | Escalations caused by the **false** grep failure |
| 116 | high → medium | After the next action |

**Cache cost per switch.** 294,889 uncached tokens over 11 switches, about 26,800 per switch. That is a re-prefill of everything since the target effort was last used. A switch back re-uses that effort's older prefix: request 7 reused request 4's 6,257-token medium prefix.

**Did high effort help?**
- Recovery requests (9) consumed 5,584 reasoning tokens.
- The two longest high-effort recoveries (requests 44 and 45: 2,383 and 616 reasoning tokens) diagnosed the real SQLite lock-contention bug.
- Requests 114 and 119 were spent on the false failure.
- Reasoning per request was similar at both levels: high 250 average (16,498 over 66), medium 260 (15,356 over 59). Effort did not inflate reasoning volume on routine steps.
- **One run cannot show whether high effort improved the outcome.** It is an A/B question.

## 4. Capability, policy, behaviour, results

| | DSH | Native |
|---|---|---|
| Supported efforts | medium / high / xhigh / max, clamped to the registry entry | Registry-sealed `authorized_efforts` of the binding (this route: medium, high) |

| Evidence feeding it | Model signals; foreground mutations and verification only | Model signals (`muse_update_reasoning_state`, 3 calls); Kernel receipts (all verification is foreground) |

| Reasoning replay | `none` for this route | Window of 12 (`REASONING_REPLAY_ITEMS`) |
| Prompt cache key hints | `prompt_cache_key = sessionId`, `x-client-request-id`, `x-opencode-session` | `x-opencode-session` only |
| Observed cache | 95.98%; one unexplained full miss in 64 | 76.9%; misses fully explained by replay-window drops (78.8%) and switches (18.3%) |

## 5. Unknowns that need experiments

1. Does replayed encrypted reasoning improve Native's quality on this pooled OpenCode route? DSH's projector records that the Meta count endpoint cannot decrypt OpenCode-issued `encrypted_content` and that no-replay continuation works. Whether the serving model *uses* replayed items is not observable.
2. Does recover → high improve fix rates enough to pay for about 27k uncached tokens per switch?
3. Is DSH's step-27 full miss a provider eviction or routing effect, and does `prompt_cache_key` reduce such misses?

## 6. Consequences for M4.7

- Native's effort *policy* is not inferior to DSH's: it is the same policy with better evidence. M4.7 does **not** replace it with a pinned effort.
- The changes justified by evidence are:
  - Remove the controller false failures that caused 2 of the 11 escalations (Phase 2).
  - Make reasoning replay a per-route policy with an append-only option, so a stable prefix no longer depends on whether effort switches happen (Phase 3).
  - Expose effort pinning only as an *experiment arm*. The existing fixed-effort engine provides it without new code.
- Effort-policy changes stay provisional until the A/B in Phase 4.
