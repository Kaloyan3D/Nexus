# M4.2 Phase A — Compound-command verification hardening

Branch `feature/linux-arm64-port`. Nothing is committed or pushed. Only Phase A was implemented (no ledger, typed-intent or turn-optimisation work). M1–M4 infrastructure, the sandbox, the adaptive routing and the frozen catalogs are unchanged.

## 1. The problem and the rule

For `sh -c "<script>"` the Kernel's exit status is the **last** command's. In the real sandbox `node --check broken.js; echo done`, `… || true` and `… && echo ok; echo end` all exit 0 and were recorded `verification: pass`; the broker's legacy path treated that as a passing check, so a failed check followed by any successful trailing command could end `verified-passed` and be applied to the Mac folder. A non-zero status was always a real signal.

**Rule now:** an exit 0 of a verification command counts as a pass only if the script's structure *attests* every check in it. Otherwise the Core's separate assessment is `unverified`, an unresolved **hazard** is recorded, and it blocks writeback under every policy until an attested command re-establishes the check.

## 2. What changed (exact behaviour)

### 2.1 New analyzer (`nexus-broker/src/compose.rs`, ~700 lines, no execution)
A real shell lexer (quotes, escapes, `$()`, `${}`, backticks, process substitution, heredocs incl. `<<-`, comments, redirections incl. `2>&1` and `&>`), not string splitting. It classifies a command:

| Trust | Shapes | Exit 0 means |
|---|---|---|
| **Attested** | a direct (non-shell) invocation; a single `&&` chain of pipelines (the Kernel adds `pipefail` to pipelines); a leading `set -e` followed only by simple `;`/newline-separated commands | every member succeeded |
| **Unattested** | `;`/newline lists, `\|\|`, a check inside `$()`/backticks/`<()`, a check inside a nested `sh -c` that is itself unattested, a status-swallowing wrapper (`find -exec`, `xargs`, `eval`, `parallel`, `watch`) around a check, `set -e` with `&&`/`\|\|` lists | only the last command's status |
| **Unanalyzable** (fail closed) | `if/for/while/until/case/select`, `{ }`, `( )` subshells, functions, `!`, `[[ ]]`, background `&`, `;;`, unbalanced quotes/substitutions/heredocs | not trusted |

Quoted separators, heredoc bodies, comments and substitution contents are data (tested: `"a;b.js"`, `'a && b'`, a heredoc containing `;`, `# ; echo`). The lexer is total (tested on odd inputs) and never executes anything.

### 2.2 Kernel record preserved; separate assessment
`ToolActivity` keeps `exitCode`, `verification` (the Kernel's verdict, verbatim: still `pass` for the three masked shapes), the output and `argsDigest`; the Kernel's own journal/approval record still holds the exact argv. New, additive fields: `assessment` (`unverified`), `composition` (`unattested:or-list`, `…:command-list`, `unanalyzable:control-flow`, …), `checkClass` (`unattested-composition` on the hazard, `attested-recheck` on the command that resolves it) and `resolvesHazards` (call indices). Every consumer reads `assessed()` (the assessment, else the Kernel verdict): the broker's `last_test`/`failed_checks`, the engine's observation (an unattested check is "started", never "failed", so it cannot open the recovery effort), `CodingOutcome`, completion, the UI. Old records have no assessment and read exactly as before.

### 2.3 Hazards, resolution, no textual dismissal
* A hazard needs three facts together: a recognised verification command (legacy recogniser, unchanged), the Kernel verdict `pass`, and a non-attested composition.
* The analyzer names the **required members**: every non-inspector member from the start of the script through the last check-bearing unit (so state-changing prefixes such as `cd sub`, and producers such as `cp new.js a.js`, are required), without `||` fallbacks and without the masking tail. Pure printing commands (`ls`, `echo`, `test`, …, with no redirect and no substitution) are not required.
* **Resolution** is only by a later command whose exit status IS attested, whose exit is 0 with Kernel verdict pass, that contains every required member in order (member-for-member, quotes removed) in the same working directory. A different check, a masked repeat, another directory, a model statement, or "the failure is unrelated" resolves nothing. For analysable scripts Nexus derives the exact command from the required members' own source text joined with `&&` (no rewriting, no additions) and gives it to the model in the tool result (`nexusRecheck`) and at the final-answer boundary (up to three times per hazard). It is **never run automatically**: the model runs it through the normal approval path, so side effects (`cp`, producers) stay under approval and in the throw-away copy.
* No derived command exists for heredoc members, control flow or substitution-hidden checks; the model is told to run each check as its own plain command. For an unanalyzable script the required set is the checks found by a lenient scan of the whole text (an over-approximation); if none can be named, any later attested verification pass stands in (documented limit, §5).
* Controller-authored M4.1.1 invalid-invocation rechecks are attested by construction (matched byte-for-byte), so that mechanism still works.

### 2.4 Outcome, completion and writeback
* `CodingOutcome`: `checksUnattestedUnresolved` / `checksUnattestedResolved`; `verification` becomes **`unattested-checks`** while a hazard is open (a real `verified-failed` or `uncertain` keeps its stronger value); hazards are *not* counted as failures (`checksFailedUnresolved` unchanged).
* Run: `unresolvedUnattestedChecks`; `completion` = **`unattested-checks`** (new value, plain-words note) instead of `fulfilled`.
* **Mac writeback (`qualifies_with`), audited and hardened.** Before: the `applyUnverified` branch refused only `verification == verified-failed`, `completion == failing-checks`, `checksFailedUnresolved ≠ 0` and the basic gate; it ignored uncertain outcomes. Now, under **both** policies, an open hazard (`checksUnattestedUnresolved`, `unresolvedUnattestedChecks`, `verification` or `completion` equal to `unattested-checks`) blocks with the reason "a verification check ran inside a compound command that cannot show it passed", and the opt-in additionally refuses `verification == uncertain` and `uncertainOperations ≠ 0`. Left as is on purpose: opt-in still applies `no-test-executed`, a stale-after-edit pass and `unexecuted-claims` (its purpose is "no check could run"); those are not masked checks.
* The answer-vs-record guard counts hazards: "all checks pass" with an open hazard is now a contradiction.
* UI: timeline wording, a red banner for unresolved hazards ("even with apply unverified on"), a note when resolved, outcome/label text for `unattested-checks`.

## 3. Replay of the recorded commands (old rule vs new)
The exact argv of all 12 `proc_run`s of the live runs (from the Kernel's approval records; `tests/fixtures/recorded_checks.json`) were replayed (`replay_of_the_recorded_commands_changes_exactly_the_intended_outcomes`). The historical receipts are untouched.

| Run / call | Command shape | Old | New |
|---|---|---|---|
| live-1 #7 | `ls -la; echo; if [ -f package.json ]; then … npm test …; elif …` (no package.json: nothing ran) | credited **pass** | `unverified` hazard (unanalyzable; names `npm test`; no derived command) |
| live-4 #18 (the accepted run's first check) | `python3 extract.py && node --check /tmp/…js && echo JS_OK; python3 -c "…"` | **pass** | `unverified` hazard; derived command `python3 extract.py && node --check /tmp/…js && python3 -c "…"` exists, is attested and resolves it |
| live-4 #19, live-2 #12, live-3 #29 | plain `&&` chains | pass | **unchanged** (attested) |
| live-3 #28/#30 | `ls; test … \|\| echo …; node --check <(…)` (exit 1) | fail | unchanged (a non-zero status is never touched) |
| all non-check commands (`cat`, `ls &&`, heredoc scripts) | — | unchanged | unchanged |

**Intentional compatibility impact.** The accepted live run's call #18 would have become a hazard. Its later call #19 is an attested chain with the *same* `node --check` but a *different producer* (`python3 -c` instead of `python3 extract.py`), so it does not re-establish #18 (a different producer could check different bytes; the analyzer cannot prove equivalence). That run would have needed one extra command (the derived one) before it counted as verified — with `test 3`'s "apply unverified" opt-in it would still not have been applied until then. This is the intended trade ("one extra turn only when a model puts `;` after a check").

## 5. Limits and compatibility notes
1. Phase A trusts the exit status only structurally. A script file (`sh run-checks.sh`) is a direct invocation: its inside is not analysed (as before).
2. The analyzer is deliberately conservative; some legitimate patterns (`if …; then check; fi`, `[[ … ]] && check`) become unanalyzable hazards and need the check run on its own.
3. A project with no tests where the model runs a guarded compound (`test -f package.json && npm test || …`) now has an unresolvable hazard (the guarded check cannot pass): it blocks writeback even with "apply unverified". Avoided by not attempting a compound check; the guidance already says to run checks individually.
4. For an unanalyzable hazard whose checks cannot be named, any later attested verification pass resolves it; this is the weakest rule in the design and applies only to exotic scripts.
5. A new Mac with an older engine sees no hazard fields (treated as none) and the older engine still has the masking bug; the engine and app are built together in the shipped bundle.
6. The Kernel contract, catalogs and the typed ledger are unchanged (Phase A did not touch them); the ledger already marked every composed check `Indeterminate`.
7. Not run: the 140-turn `rel2_` marathon tests.
8. **Nexus.app and the engine image were not rebuilt** for Phase A (tests and replay only); the shipped build still has the old behaviour until it is rebuilt.
