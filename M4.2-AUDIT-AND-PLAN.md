# M4.2 — Evidence-Aware Verification & Reliability: audit and phased plan

Status: audit. **Phase A has since been implemented (see `M4.2-PHASE-A-REPORT.md`); Phases B–F are not started.** Original status line: audit only. The working tree still holds the uncommitted M1–M4.1.1 work and nothing else. A temporary probe test was added to measure the compound-command behaviour and then removed.

## 0. How this was measured

* Real sandbox, real Kernel, Fedora 44 ARM64, one throw-away probe (below).
* The engine's own durable records of the **two live runs** that exist on the embedded VM's state disk (read-only copy, no credentials): run B (36 turns, the M4.1.1 failure) and run C (20 turns, the successful acceptance run). Per-call activity log, verification ledger (`verification/<run>.jsonl`), engine state.
* Code reading of `nexus-tools/src/process.rs`, `nexus-broker/src/inspect.rs`, `completion.rs`, `verification/*`.

## 1. Findings

### F1. Compound shell commands can report a pass for a failed check (confirmed)

`proc_run` derives `verification` from the process's **overall** exit status (`nexus-tools`: `verdict()`), with one correction: a pipeline gets `set -o pipefail` (D5). Nothing handles command *lists*. Probe in the real sandbox, `broken.js` containing a syntax error:

| command | exit | `verification` |
|---|---|---|
| `node --check broken.js; echo done` | 0 | **pass** |
| `node --check broken.js \|\| true` | 0 | **pass** |
| `node --check broken.js && echo ok; echo end` | 0 | **pass** |
| `node --check broken.js \| tail -1` | 1 | fail (pipefail works) |
| `node --check broken.js` | 1 | fail |

`is_verification_command` calls each of the first three a check (it sees the word `check`), `record_receipts` stores `last_test = pass` and clears `failed_checks`, and `CodingOutcome` (the object the Mac writeback keys on) reads `verified-passed`. **A failed syntax check followed by any successful trailing command can therefore produce an applied result.** Nothing in the sandbox is weakened by this; it is a verdict-attribution gap in the legacy path. Exit status ≠ 0 is always a real signal; only **exit 0 of a list** is untrustworthy.

The verification ledger already knows this: its classifier marks any `;`, `||`, `&`, pipe-with-non-truncator or redirection as `Indeterminate { shell-composition }`. But the ledger is reporting-only (F2).

### F2. Two verification truths; the authoritative one is the weaker

| | Legacy path (`is_verification_command` + Kernel exit verdict) | Verification ledger (`verification/*`, typed) |
|---|---|---|
| Drives | engine nudges, `last_test`, `failed_checks`, `completion`, `CodingOutcome`, **Mac writeback** | run record's `verification` summary only; "never decides, blocks, schedules, continues the model" (feedback policy `Observe` by default) |
| Recognition | keywords in any shell segment (`test`, `build`, `check`, `tsc`, `lint`, …), inspectors excluded, heredoc bodies ignored | allow-list of direct invocations (`cargo test`, `npm run test`, `pytest`, `go vet`, `node --test`, …), weakening flags, `Invocation::{Direct, Shell, ShellPipeline}` |
| Freshness | `dirty_since_test` / call-index ordering | receipt-delta source identity, 8-rule freshness (`Current/Stale/Indeterminate`), scope, run-end attestation |

Live evidence of the split (ledger `shadow` field, run B): of the six `proc_run`s, the ledger recognized **none** as a check (3 `not-recognized`, 3 `indeterminate: shell-composition`), the legacy recognizer counted **three** (`legacy-broader`). Run C: ledger `opaque-check-commands-not-trusted:2`, run summary `verdict: unverified`, while the run was `completion: fulfilled` and was written back. Both are honest about different things, but the run record shows "unverified" next to a green outcome, and the stricter one cannot stop anything.

### F3. Browser evidence is outside the ledger

`ObservationKind` = `Command | FileMutation | BackgroundJob | RunBoundary`. `browser_inspect` produces no record, so the ledger has no screenshot digests, no observation time, no freshness against edits, and its summary is silent about the visual requirement. Browser evidence lives only in `ToolActivity.browser` / `CodingOutcome.evidence` (derived on read). That evidence is correct (M4.1/M4.1.1 tests) but is not durable-ledger-grade: it is a derived view of the activity log, it has no content-addressed record id, and the ledger's target/freshness machinery (`VerificationTargetV1`, `SourceTracker`) is not applied to it. In Direct workspaces the ledger's freshness is `Indeterminate` by design (shared writers); the call-index rule used today is stricter about order but blind to outside writers.

### F4. Recognition is vocabulary luck, and measurably costly

* `node --check`, `python -m py_compile`, `tsc --noEmit` and HTML/CSS checks are **not** in the ledger's typed table. In the legacy path they count only if the command line happens to contain a listed word.
* Run B: three "changes not verified" nudges (turns 25, 28, 30) because the model's HTML-parser one-liner, heredoc extraction and `ls &&…` contained no listed word; the model found a recognized command by trial at turn 31. Run C: **zero** verification nudges, only because its command line contained `--check`. Same model, same kind of task, 0 vs 3 nudge turns, decided by wording.
* The invalid-invocation handling added in M4.1.1 already works on a typed, allow-listed shape (`node --check`, `python -m py_compile`); it is the first typed check intent in the legacy path.

### F5. Where the turns and tokens go (profile of the two live runs)

A turn costs the *whole context*: run C averaged 31 K input tokens per request (627 K over 20), run B 36 K (1.31 M over 36).

| | run B (36 turns) | run C (20 turns) |
|---|---|---|
| `fs_read` calls / share of carried tool-result bytes (bytes × later turns) | 5 / **72 %** | 6 / **85 %** |
| of which read-back of the file the model had just written | turns 9–12 (4 reads) | turns 10–13 (4 reads of 30–250-line ranges of its own 1000-line `fs_write`) |
| `browser_inspect` | 7 / 24 % | 5 / 13 % |
| reasoning-state calls (each a full request) | 4 (turns 3, 6, 7, 13) | 4 (turns 4, 7, 8, 14) |
| verification-related continuation turns (nudges + their check turns) | **11** (turns 25–35) | **0** |
| `fs_edit` calls to one file | 6 (two bursts of 3; one `fs_edit` takes 16 edits) | 0 |
| context compactions | 5 | 1 |

* **Read-back is the single largest cost** and the guidance I added in M4.1.1 ("don't read back what you just wrote") did **not** change it in run C (the run was made on the build that contained it). Guidance alone is not enough.
* **Reasoning-state turns are not pure waste:** they move effort (run C: `medium → high` at attempts 8–9 for the design/implement turns that write the 34 KB file, back to `medium` at 10). They cost ~20 % of input tokens (4 of 20 turns at average context) for ~1 KB of output. Changing that touches adaptive policy; **no evidence of a defect, so no change proposed** until a replay harness exists.
* **Verification continuation turns** are fully explained by F4 (+ the invalid-invocation loop fixed in M4.1.1).
* Browser bytes are modest; images are not counted in these tool-result bytes but dominate the 440 KB request budget (the cause of compaction).

## 2. Proposed phases (smallest and safest first)

Each phase is independently shippable, additive, fail-closed, and keeps the frozen catalogs, CCv2 contracts, M1–M4 infrastructure and the adaptive routing untouched unless stated.

### Phase A — Compound-command verdict hardening (broker only; ~1 focused change)
* New pure classifier `shell_composition(script)` for `sh|bash -c` scripts: `AndChain` (only `&&` and pipelines, no `;`/newline lists, no `||`, no `&`, no `!`, no groups, no `if/for/while/case`, no functions), `ErrExit` (leading `set -e` + only simple `;`-separated commands), or `Unsafe`.
* In `record_receipts`: when the command is a verification command, the Kernel verdict is `pass`, and the composition is `Unsafe`, the activity's `verification` becomes **`unverified`** (it keeps `exitCode`, `argsDigest`, and gains `kernelVerdict: pass` and `composition: unsafe` so the Kernel's statement is preserved verbatim, never overwritten). `unverified` already flows through every consumer (`checks_unverified`, `observe → Started`, ledger `Inconclusive`), and never counts as pass or as failure, so a masked failure can no longer produce `verified-passed`, and no new nudge text is needed beyond one controller sentence in the tool result: *"exit 0 is the last command's; this does not show the check passed; run it on its own."* Non-zero statuses are untouched (always real).
* Exact evidence: add a bounded `commandText` (≤ 4 KB) to the **durable activity log only** (not the run record), next to the existing `argsDigest`; the ledger keeps digests.
* No Kernel/tool contract change, no catalog change. Reversible by one flag.
* **Regression tests (real sandbox):** the five probe shapes above (first three ⇒ `unverified`, last two ⇒ `fail`), `set -e; a; b`, `a && b` pass stays `pass`, quoted `;` inside an argument is not a separator, `node --check` direct pass stays `pass`, and the end-state assertion that a masked failure followed by nothing else yields `verification ≠ verified-passed` and completion not `fulfilled`.
* **Replay of the 12 recorded `proc_run`s (done, by hand, from the activity logs).** Run B calls 28 and 30 (`ls -la; test -f … && (…) || echo …`) already ended in the failing command and were `fail`. **Run C call 18 and run B call 29 would be downgraded**: `python3 extract.py && node --check /tmp/hiiii-check.js && echo JS_OK; python3 -c "…"` has a `;` list after the check, so its exit 0 is the *last* command's. Run C's decisive check is call 18, so under the rule as first stated **run C would have ended without a verified check** (it was still applied only because `test 3` has the "apply unverified" opt-in; a strict project would not have applied it). That is the rule doing its job on a real, previously accepted result, and it is also a regression for a legitimate pattern, so the rule needs the following refinement before it ships:
* **Refinement: attest the check unit, do not just downgrade.** Split the script at top-level `;`/newline; each `&&`-chain is a *unit* whose own exit status would be attested if it ran last. For an `Unsafe` composition with exit 0, the controller derives the check-bearing unit (`python3 extract.py && node --check /tmp/hiiii-check.js && echo JS_OK`) **verbatim, with no rewriting**, and gives it to the model as the exact command to run on its own (same mechanism and same exact-match resolution rule as the M4.1.1 invalid-invocation recheck, generalized). Until that exact command passes, the check is `unverified` (never `pass`, never `fail`) and the original receipt stays untouched. Cost: one extra turn only when a model puts `;` after a check; the one-line guidance already given to browser conversations is extended ("do not put `;` or `||` after a check"). A model that already runs checks as plain and-chains is unaffected.
* **Risk:** the extra turn for models that habitually write `check; echo OK`, and the units are parsed from shell text, so unparseable shapes (`if/for/while/case`, functions, here-docs spanning units) fall to "unverified, no derived command" (fail closed; the model must run the check on its own). Mitigated by the replay above (2 of 12 affected, both explained) and by running the full recorded-activity replay as a test before any switch.

### Phase B — Browser evidence in the verification ledger (additive record kind; reporting-only)
* New `ObservationKind::BrowserInspection` (schema v3, readers of v1/v2 untouched) with **four separate sub-records, never one flag**: `execution` (launched / loaded / step outcomes / page-error counts, run id, call index, evidence id), `delivery` (per screenshot: sha256, bytes, viewport, `takenAt`, delivered or not, the sealed model id and the vision decision `yes/no/unknown`), `observation` (derived: delivered ∧ vision-capable), and `assessment` (the model's judgement referenced by `visualBasis` digests; always `model-stated`, never "verified").
* Freshness against the last edit via the existing `SourceTracker` target (receipt-delta), with the existing indeterminate rules (shared writers) *and* the current call-index rule as the lower bound; a screenshot record is `Current` only if both agree.
* Ledger summary gains `visual: { requested, execution, delivery, observation, assessment, freshness }`; the UI and writeback keep reading what they read today (no behaviour change, like Phase 01–04).
* **Tests:** stale screenshot (edit after the last inspection ⇒ `Stale`, requirement unmet), screenshot at the right target but not delivered (text-only / unknown model ⇒ observation absent), delivered-but-oversize, inspections in a Direct workspace ⇒ `Indeterminate`, durable replay (restart mid-run), ledger/`CodingOutcome` agreement (both must say the same about the same run).

### Phase C — One typed check-intent table for both recognizers (measured, still no new tool)
* Replace the two vocabularies with one table of typed intents: `{program, leading args} → intent {js-syntax, py-syntax, ts-typecheck, test, build, lint, vet, html-structure?}` including `node --check FILE`, `python -m py_compile FILE`, `tsc --noEmit`, with weakening flags. `is_verification_command` and `classify_command` both delegate to it; keyword matching survives only as a *demotion-safe fallback*: a keyword-only command is counted as "ran" (can fail the run when it fails, **cannot** clear a failure or establish a pass) until Phase D.
* **Gate:** shadow-compare over every recorded run (3 live + the whole test suite's activity) with a zero-unexplained-difference rule before the switch; `CLASSIFIER_VERSION` bump so old records are never re-read under new rules.
* **Tests:** the live commands from runs B and C classified identically/stricter; heredoc and quoted-word cases; the "grep check" regression that the legacy rule already guards.
* **Risk:** this is the phase that changes engine nudging (rule 2 sees fewer/different checks), so it needs the replay evidence above and is not started without your go-ahead.

### Phase D — Typed `verify` tool (optional; new catalog, new frozen digest, structured receipts)
* A broker-handled `verify_project { intents: [...] }` with a closed intent enum chosen from the project kinds (static HTML: `js-syntax` over each inline/linked script as real files, `html-structure`, `css-parse`; Node/Rust/Python: the project's own test/build/lint). The **controller** maps intents to fixed argv and runs them through the same approved `proc.run` path; the receipt records intent, exact argv, target file digests, exit status and a typed result. This is the structural answer to F4 (no vocabulary dependence) and removes the motive for read-backs and ad-hoc parser one-liners on static sites.
* New profile (like `RepoCodeAdaptiveBrowserV1`), existing catalogs and conversations unchanged; legacy `proc_run` stays.

### Phase E — Measured turn reductions (no policy change)
Only things that the data supports, each behind an A/B on recorded runs before it ships:
1. **Read-back:** the controller already holds `postSha256`/line count for the model's own `fs_write`/`fs_edit`. Candidate: add a controller-authored, bounded *write receipt summary* to the write result (line/byte counts, script/style block counts, first syntax diagnostics from the Phase-D checker) so there is nothing to read back for assurance. Measure: read-back turns and carried bytes (target: −3 turns / −50 % carried bytes on runs like B and C). Explicitly **not** proposed: suppressing or rewriting an `fs_read` the model asks for.
2. **Batched edits:** already allowed (16 edits); measure after Phase D whether bursts disappear before enforcing anything.
3. **Reasoning-state calls:** leave alone. If you want it pursued: build a replay of recorded attempt traces to show which signals changed the effort and whether the phases could be derived from receipts (controller-owned) with identical effort decisions; adaptive policy only changes with that evidence.
4. **A profiling tool** (the analysis in F5 as a committed script over activity logs + engine state) so these numbers are reproducible, not hand-collected.

### Phase F — Promote the ledger (later, separate decision)
Make the writeback gate require **both** the legacy outcome and the ledger verdict (intersection, fail-closed), after A–C have removed the known disagreements. Not proposed for this milestone.
