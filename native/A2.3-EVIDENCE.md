## 1. Architecture (built on A2.1/A2.2, nothing replaced)

Authority chain for one mock attempt:
Controller ledger files (tasks.json + attempts.jsonl, written by
begin-attempt) -> JS resolveShadowIntent (derives commandId, proves
generation) -> JS native-issuer (sealed V1 resolution from the real
Registry) -> JS native-target-v2 (authoritative extension from effective
snapshot records + Controller session; fail-closed on any gap) -> daemon
acquire (lease) -> daemon seal (V1 HMAC) -> daemon seal-extension (V2 HMAC,
same issuance key, separate table) -> Rust prepare (exact bytes, no
network) -> JS buildDispatchIntent (canonical bundle incl. requestDigest)
-> daemon intent-publish (kernel seals + persists published intent) ->
daemon accept (receipt, existing A2.0 semantics untouched) -> daemon
dispatch-authorize (9 revalidation checks, marks intent executed
atomically, mock-e2e scope only) -> nexus-model attest + dispatch to the
loopback mock provider -> terminal bound to the Controller attempt.

Trust boundaries: the kernel trusts only its sealed store rows (V1, V2
extension, intent) plus live generation/witness state - never caller
bytes. The daemon trusts only issuer-HMAC requests from allowlisted UIDs.
The transport trusts only attested preparations for its bound origin.
Credentials never enter the kernel, store, snapshots, errors, or logs:
only opaque credential:// references cross boundaries, and the secret
value is injected into exactly one header at the transport boundary (mock credential in A2.3).

## 4. Durable Controller intent evidence

Publication ordering enforced by the kernel: referenced V1 issuance and V2
extension seals must pre-exist (forged-issuer otherwise); bundle digests
must agree with the sealed records (binding-mismatch); the lease must
equal the live generation (stale-lease); scope must be mock-e2e
(scope-refused); the sealed extension must agree with the sealed core on
model, reasoning, and connection. The bundle is sealed with the issuance
key and persisted published; byte-identical republication is idempotent
while any conflict or post-terminal republication fails closed. Fencing is
terminal (intent-fenced). NativeDispatchIntent.Tests.cjs 6/6 pins the
bundle contract (happy path, missing lease/request/session, live scope,
generation mismatch).

## 8. Transport notes (Phase 4)

No transport replacement was needed. from_extension_json consumes genuine
Registry JSON strictly (unknown keys refused, full executable validation).
HttpSseTransport now refuses https explicitly: with no TLS stack, sending
plaintext (including the credential header) to a TLS port would leak
secrets, so https fails closed pre-connect (pinned by test) and TLS
termination belongs to the live gate. Session and billing verified
against opencode.ai Zen documentation: Zen serves Responses with
console-credit billing plus API key, and documents no x-opencode-session
semantics, so our session header is Nexus-originated attempt binding
metadata (opaque to the provider) while billing tier stays a descriptive
Registry classification, never a live balance check. No proxy path, no
redirects, no retries, and no tool execution anywhere on this path.

## 11. Final security audit and commit record

Reviewed baseline 02cb320a plus the full A2.3 tree above. Adversarial
conclusions per task check: (1) Controller keeps sole task/completion
authority (kernel creates no attempts; terminal acceptance stays
Controller-side); (2) Registry keeps sole routing (no second router;
model code takes targets as given); (3) kernel revalidates seals, lease,
witness, receipt, scope, endpoint, and credentialRef at the boundary;
(4) stale/forged intent is refused at publish and authorize alike;
(5) receipts alone authorize nothing and grants are exactly-once
(8-thread race pinned); (6) fencing is terminal and cancellation never
resolves to a committable state; (7) credential values never enter the
kernel, store, snapshots, errors, or logs (refs only; E2E asserts
absence end to end); (8) same-UID fabrication stays out of scope per
A2.1: file-ledger forgery alone authorizes nothing without the daemon
capability key, but a same-UID peer holding the key is indistinguishable
by design, so live deployment on shared-UID machines remains BLOCKED;
(9) Transport::send is public and cannot verify kernel grants itself:
the grant binds the harness control flow, and any future out-of-process
caller must present a fresh grant per attempt (a sealed grant token is
the recommended A2.4 hardening); (10) dispatch_enabled stays false,
pinned by test.

Audit fixes in this pass: v1-to-v2 store migration had no coverage -
added a preservation test (seals survive, version advances once); grant
race semantics had no pin - added the 8-thread exactly-once test. No
open security findings remain in the mock scope.
