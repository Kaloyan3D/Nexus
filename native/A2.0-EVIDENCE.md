## 0. Step-0 inspection and design plan (executed as written)

Read before changing code: `native/A1.1-EVIDENCE.md`, `native/A1.2-EVIDENCE.md`,
`native/A1.3-EVIDENCE.md`, `native/nexus-kernel/src/{lib,accept}.rs`,
`native/nexus-store/src/{store,witness,schema,journal}.rs`,
`native/nexus-contracts/src/{errors,types}.rs`,
`native/nexus-daemon/src/{server,auth,protocol}.rs`,
`config/registry/native-*.cjs`, the A1.2 shadow adapter and A1.3 daemon
transport, and the current recovery/bridge tests. Branch/HEAD verified:
`feature/rust-native-core` at `0e1fdcb`, clean except three pre-existing
untracked A0.3 docs (preserved untouched).

Transaction boundaries (unchanged primitives, new ordering):

- Main store: one SQLite file, WAL + FULL + IMMEDIATE, `flock` + mutex.
  `accept` commits command row + journal event + receipt row atomically.
- Witness: a SECOND SQLite file (separate failure domain), its own
  IMMEDIATE transactions. Acknowledgement + accepted-map update commit
  together in one witness transaction.
- The two files NEVER commit atomically (stated, not solved — 2PC would
  require a distributed coordinator this milestone does not build).
  Safety comes from ORDERING plus fail-closed reconciliation at every
  crash point, never from claimed atomicity.
- New order: `prepare` (witness) -> `accept` (store) -> `acknowledge`
  (witness). Reservation binds commandId, attemptId, generation key, lease
  epoch, store incarnation, immutable command digest, issuanceId.

Trust principals: Controller (attempt authority), JS Registry (routing
Authority), trusted issuer bridge (delivery channel), `nexusd` (acceptance
authority), untrusted model/tool processes (no privileged access). The
kernel never resolves models; schema validation never confers trust.

## Gate 1 — Receipt/witness crash safety (IMPLEMENTED, proven)

State machine implemented in `nexus-store/src/witness.rs` (+ `schema.rs` v2
migration) and enforced in `nexus-kernel/src/accept.rs`:

`unseen -> prepared -> accepted -> acknowledged`
(`abandoned` is the safe terminal non-success state for expired `prepared`
reservations; it invents no execution and is never replayable without
re-preparation.)

Crash matrix (each row is a named regression test):

| Crash / rollback point | Test | Resolution (proven) |
|---|---|---|
| P1: prepared, store commit never ran | `p1_prepare_without_commit_heals_on_identical_replay` | No receipt, dispatch refused, readiness NOT_READY; identical replay heals to exactly one acknowledged receipt |
| P1 + conflicting binding | `p1_conflicting_binding_is_never_reaccepted` | `command-conflict`; prepared authority preserved |
| P2: committed, acknowledgement lost | `p2_commit_without_ack_heals_on_identical_replay` | Identical replay returns the receipt as a replay (`created=false`), heals the witness, still exactly one receipt; conflicting bytes fail |
| Full main-store restore, witness intact | `full_restore_with_intact_witness_never_silently_reauthorizes` | `reconciliation-required`; 0 receipts; acknowledged reservation retained; readiness NOT_READY; `authorize_dispatch` refuses |
| Expired reservation | `abandoned_reservations_never_invent_success` | `prepared -> abandoned` via explicit reap; `acknowledge` on abandoned refuses `reservation-expired`; identical re-preparation re-arms and commits exactly once |
| Retention / pruning | `retention_never_erases_replay_protection` | `delete_abandoned` removes ONLY abandoned rows; acknowledged reservations + accepted-map entries survive; conflicting reuse still `command-conflict` |
| Live daemon restore (real processes) | A2.0 JS R1 | Stop, restore pre-delivery main store, restart, replay -> refused `reconciliation-required`, 0 receipts, lost receipt stays lost |
| Live daemon replay | A2.0 JS R2 | `delivered` then `replayed`, exactly 1 receipt, status stays `accepted-reserved-dispatch-disabled` |

Unknown outcomes resolve to suspension (`reconciliation-required`) or
healing with a byte-identical binding — never blind redispatch. Reacceptance
after a pre-acceptance restore is refused, not retried. Migration: witness
v1 state preserved (additive `dispatch_reservations` table + version row);
unknown future witness versions refuse `store-incompatible`. New wire codes:
`reservation-conflict`, `reservation-expired` (additive only).

NOT claimed: cross-file atomicity, power-loss safety, independent failure
domains on one disk (same-disk witness restored together with the DB is
still undetected by construction — deployment must separate them).

## Gate 2 — Issuer trust-boundary design (DESIGNED + demonstrated limit)

Production boundary design (recorded here; enforcement needs OS identities
this environment cannot create without modifying host users/services, which
is out of scope and was not attempted):

- Controller -> bridge -> daemon over a Unix socket owned by a dedicated
  `nexusd` UID/GID; store/witness directories `0700` to that identity;
  socket file `0600` in a `0700` directory; capability file eliminated (or
  held `0600` by the issuer UID, never group/other-readable).
- `SO_PEERCRED` gates the TRANSPORT (only the issuer UID may connect) but
  never authenticates the JS module: peer uid/gid/pid are process facts.
  Module-level proof requires the issuer to sign resolution bytes with a
  key the daemon verifies against a pinned issuer identity (A2.1 design).
- The kernel must keep verifying seals against an issuer-pinned key it does
  not itself hold for writing; arbitrary caller-supplied executable targets
  must never become trusted by passing schema validation (no such fields
  exist in the contract vocabulary by construction).
- A second HMAC/capability file is explicitly NOT a same-UID solution.

Demonstrated in this environment (feasible, isolated, no host changes):

- Rust `server::peer_tests::peer_credentials_report_uid_not_module_identity`:
  `SO_PEERCRED` on a live socketpair returns our OWN uid — the exact
  property that makes same-UID peers indistinguishable. The daemon now logs
  peer uid/gid/pid per connection as forensic observation, never as auth.
- JS R4: the same-UID test process reads the `0600` cap file and its forged
  authenticated `acquire` is ACCEPTED (`theft.ok === true`). File mode does
  not stop same-UID theft; socket permissions cannot either.
- JS R7: readonly mode creates no cap, serves `readiness`, and refuses
  privilege with `privileged-disabled` even with a dummy credential.
- Existing A1.3 A4 + Rust `same_uid_cap_theft_is_possible_and_documented`
  re-verified by suite retention (A1.3 44/44 still green).

HARD A2 BLOCKER (recorded, not waived): meaningful process isolation
(separate Linux service identities + protected store) cannot be implemented
or demonstrated in this environment, and same-UID theft provably succeeds.
First model-only execution (A2.1) MUST NOT proceed on a shared-UID machine.
Existing shadow-test protection was not weakened; its adversarial tests are
retained and green.

No production scheduling or DSH routing changed (one-line JS allowlist

  daemon 8-way concurrent-accept proof retained from A1.3).

  re-resolve path; kernel has no resolver).
- Durable Controller intent publication before execution is DEFINED as an

## Gate 4 — Recovery and operator attestation (IMPLEMENTED + bounded)

`fence_for_recovery` now treats the operator string as an assertion to be
checked, never as a guarantee:

- Attestations under 8 non-blank characters are refused (`delivery-invalid`)
  instead of being recorded as assurance.
- An attested maximum BELOW the witness maximum is refused
  (`reconciliation-required`) instead of silently taking the max — a wrong
  number can no longer bless a forgotten issuance.
- Fenced epochs strictly advance (witness max becomes the fenced epoch, so
  re-attesting it is refused; only fresh evidence covering the new maximum
  fences onward). Proven: `recovery_attestation_is_verified_not_trusted`.
- Every decision appends a durable audit record: witness baseline
  (attestedMax, previous store/witness epochs, fenced epoch, attestation
  text, reason) + `recovery-fenced` journal event, readable via the new
  read-only `recovery_audit(task, backend)` (Gate 5's `recovery-attestation`
  dimension points at it).
- Unknown prior outcomes stay unknown: fencing opens the future, it never
  declares the past safe; witness corruption/missing authority still fails
  closed with no automatic continuation.

Proven locally vs requiring independent trust (stated): epoch monotonicity,
refusal of low attestations, and the audit trail are proven locally. The
TRUTH of an attestation (did the operator really review every issuance?)
requires an independent trust/storage service and is NOT claimed — the
dimension stays NOT_READY and A2.1 needs a verified attestation source.

## Gate 5 — Read-only dispatch readiness (IMPLEMENTED, proven)

`Kernel::dispatch_readiness(command_id)` + daemon `readiness` IPC command
(read-only surface, no auth required, no token issued, no state mutated —
read-only proven by R5 status-invariance probing). Nine individually
evaluated dimensions: `trusted-issuer-identity`, `controller-durable-
authority`, `pinned-target`, `generation-lease`, `witness-health`,
`dispatch-reservation`, `reconciliation-state`, `recovery-attestation`,
`dispatch-disabled`. Verdict is ALWAYS `NOT_READY` in A2.0 (`ready: false`,
`dispatch_enabled: false`); per-command assessment pins target/lease/
acknowledged-reservation without ever authorizing (R5: even a fully
acknowledged command reports NOT_READY). `dispatch_enabled() == false` and
`authorize_dispatch()` refuses are preserved and asserted in every suite
(Rust `dispatch_is_never_authorized` + R5 + R7; no `dispatch` command exists
on the daemon: `unknown-command`).

## Known limitations (NOT claimed)

- No cross-file atomicity; no power-loss safety; no same-disk failure-domain
  independence; no exactly-once external effects (dispatch is disabled).
- Same-UID hostile peer defeats the shadow-test capability (BLOCKER).
- Witness accepted-map + acknowledged reservations grow unboundedly; only
  abandoned rows are prunable (documented retention rule, enforced).
- Nonce cache bounds (H-06) retained; ts window needs ~synchronized clocks.
- Linux + SQLite WAL + Unix sockets only. No Windows/macOS/NFS/SLO claims.
- Recovery attestation truth requires an independent trust source (A2.1).
- Controller durable publication and issuer module authentication are A2.1
  design items, reported NOT_READY here.

## Outstanding blockers (all must clear before A2.1 execution work)

1. Separate Linux service identities (distinct UIDs, `0700` store, pinned
   issuer key, SO_PEERCRED transport gating) — cannot be demonstrated here.
2. Independent-failure-domain witness deployment proof.
3. Verified attestation source for recovery.
4. Durable Controller intent publication before execution.
5. Module-level issuer authentication binding resolution bytes to Registry
   identity (replacing the file capability).
6. Only then: any external-effect authorization path (A2.1 runtime scope).

## Final decision

**BLOCKED** — for A2.1 execution work. A2.0 itself passes: the defensible
path toward the first Muse model call exists, with every remaining security
and durability gate explicitly enforced (readiness NOT_READY) rather than
assumed. A2 execution is NOT authorized by this milestone.
