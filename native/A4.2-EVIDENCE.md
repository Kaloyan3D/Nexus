## 1. Principals and UIDs

| Principal | Linux identity | Holds | Can |
|---|---|---|---|
| Daemon `nexusd` | `nexusd` | DataRoot, both credentials (writes them) | enforce |
| Controller / issuer bridge | issuer UID (`--allowed-uids`) | issuer credential (A4.1 dir) | `approval-request`, `approval-revoke`, `tool-execute`, list |
| Approver (human at a terminal) | approver UID (`--approver-uids`) | approver credential (A4.1 dir) | `approval-get`, `approval-decide`, list |
| Nexus Desktop (GUI/Tauri) | the logged-in user | **no credential** | read-only `list_approvals` status |
| AI/model execution | none (disabled) | none | nothing |
| Untrusted | any other UID | none | EACCES at connect |

In a single-user dev setup the GUI, Controller and issuer commonly share one UID; therefore a GUI "Approve"
button would not be independent proof of consent (any same-UID process could call the same IPC). Hence the GUI
is status-only by construction.

## 2. Trust model

Approval = (approver HMAC capability) ∧ (SO_PEERCRED UID ∈ approver UIDs) ∧ (prior authenticated `approval-get`
of the exact request) ∧ (review code echo) ∧ (request digest echo) ∧ (live Kernel authority: lease, generation,
witness, not revoked). The issuer holds none of the approver factors (A4.1). The daemon, not the submitter,
authors the reviewed operation, pre/post-image identity and diff from the live workspace.

## 3. Trusted confirmation mechanism (what is and is not proven)

Mechanism label recorded in the audit: `approver-uid-terminal-review-code`.

`nexus-approver review <id>` runs as the approver UID, refuses unless stdin and stdout are TTYs, reads the answer
from `/dev/tty`, displays the daemon-authored review (operation, digests, diff or "UNAVAILABLE"), and requires the
operator to type the displayed review code (or `deny`). The daemon records as **verified**: approver HMAC, peer
UID, prior authenticated review, code/digest echo. It records as **not verified**: human presence and TTY origin
(client attestation only).

Limitation: a script running as the approver UID could drive a pty. Linux file modes/UIDs cannot distinguish a
human from automation under one UID. A genuinely stronger factor (polkit/PAM re-authentication, FIDO/WebAuthn
presence, a separate trusted display) was evaluated and is **not** available in this environment; it is the
blocker for verdict #2 = PASS.

## 4. ApprovalRequestV1 (immutable, sealed)

`schemaVersion 1`, `domain nexus-approval-request/v1`, `approvalId`, `commandId`, `commandDigest`,
`controllerIntentDigest`, `taskInstanceId`, `attemptId`, `leaseEpoch`, `storeIncarnation`, `workspaceRootDigest`,
`toolId`, `toolVersion`, `scope` (write|process), `argsDigest`, `budgetDigest`, `paths[]`, `operation{}`
(write: path, op, pre/post-image sha256+bytes, mode; process: program, resolved program, exact argv, argvDigest,
cwd, sandbox {network none, snapshot read-only, writeBack none, no shell}), `limits{}`, `preview{}`
(unified diff + digest, or `unavailable` with reason — never a summary), `createdMs`, `expiresMs`.
Row is sealed by HMAC(issuance key) over id|command|sha256(request); `approval_fetch` re-verifies, so DB edits
fail closed. TTL default 5 min, max 10 min.

Scope rules: writes require a non-empty explicit path list (`.`/empty rejected); no workspace-wide inference.
Binding to execution is by `argsDigest` (covers path/content/argv/cwd) + `budgetDigest` + workspace digest +
task/attempt/lease/incarnation + tool id. Any change refuses.

## 5. Lifecycle and recovery

`requested → pending → approved | denied | expired | revoked`; `approved → consumed | expired | revoked`.
Terminal states never transition (compare-and-set under the Kernel critical section + SQLite tx).

- Denial final; expiry lazy-enforced on every read/decide/consume; consumption single-use, immediately before the
  tool grant is minted; decision requires prior review in the same daemon incarnation.
- New generation/lease, `tool-revoke`, or lost authority → open approvals `revoked`.
- Restart: approved-unconsumed → `expired` (`recovered-expired`); reviewed-pending → review voided
  (`recovered-rearmed`). No consent is fabricated or carried over.
- Legacy `write-scope-approve`/`process-scope-approve` refused in this mode (`approval-required`).
- The coarse per-command Kernel scope is bound at the tool ceiling on first approval (idempotent); the
  per-operation approval + budget digest is the fine authority. Documented trade-off.

## 6. Audit trail

`approval_events`: append-only, hash-chained, HMAC-sealed. Events: requested, pending, reviewed, review-armed,
approved|denied, consumed (with grant request id), expired, revoked (reason), recovered-*. Payloads carry request
digest, workspace digest, task/attempt/lease, tool/scope, approver id (`uid:N`), peer uid/gid/pid, mechanism,
`independent`, expiry. Never: capabilities, review code, file content, passwords. Limitation: same-host witness —
tail truncation of the event table is not externally witnessed (same as the tool journal).

## 10. Limitations and production blockers

1. Human presence unverifiable under one UID (§3) — needs PAM/polkit/FIDO or trusted display.
2. Superseded by §12: a store that has run in human-approval mode can no longer be restarted into writes/processes under a weaker policy. Legacy mode remains only on a store that never ran human mode.
3. Same-host witness: event-table tail truncation undetected; no external anchor.
4. Same-UID hostile module inside issuer/approver process (A4.1 limitation persists).
5. No online credential rotation; review code and credentials live in DataRoot 0700.
6. Real systemd provisioning, rootful Docker/VM not exercised.
7. Diff limited to ≤1500 lines UTF-8; else `unavailable` (no summary).
8. Process approvals show exact argv but "filesystem effects" are descriptive (read-only snapshot, no write-back).

## 11. Prerequisites for A4.3 / live integration

Stronger human-presence factor; supervised enforcement of human-approval mode; external witness for approval
events; rootful/systemd verification; online rotation; explicit tool policy for AI-initiated proposals (still
disabled).

## 12. Approval-downgrade closure (final security pass)

Finding: with the original opt-in flag, a restart (operator error or compromised launcher) without
`--require-human-approval` re-enabled A3.3 scope approval on the same store, and a coarse per-command scope bound
by an earlier approval would then have authorized unapproved writes.

Fix: persistent, raise-only **approval-policy latch** in `store_meta`
(`human-required:test-only` < `human-required:independent`).

- Evaluated right after the store opens, before any socket or credential is published.
- Requested policy below the stored level + `--enable-writes`/`--enable-process` → fatal
  `approval-downgrade-refused`, no socket, no credentials.
- Same store, no mutation classes enabled → starts read-only (latch noted in the log); reads keep working,
  every write/process/legacy-approve path is disabled.
- Test-only self-approval (`--allow-nonindependent-approver-test-only`) cannot start on an `independent` store
  and decisions made under a non-independent topology are not consumable by an independent daemon.
- Legacy A3.3 behaviour is available only on a DataRoot that never ran human mode. The documented way back for
  an operator is a **fresh DataRoot** (no pending/approved requests carry over). There is no in-band release flag.
- Human mode still refuses to start without writes/process, approver credentials, independence declaration or
  (outside test-only) the A4.1 role-separated credential directories.

Residual: someone with write access as the daemon UID can edit `store_meta` or the argv-level environment; that
is the daemon-UID compromise already out of scope. An external supervisor/launcher policy remains advisable.

Regression tests: `restart_without_human_approval_cannot_enable_writes_or_processes`,
`previously_approved_request_cannot_execute_through_another_path`,
`human_mode_with_incomplete_configuration_refuses_to_start` (single-UID), and
`multuid_independent_human_approval_store_cannot_be_downgraded_by_restart` (dropped flag, test-only substitution,
process enable; compliant restart still republishes 0640 approver credential).

## 13. Programmatic approval by the approver identity (reviewed, accepted limitation)

Any process that holds the approver capability **and** runs as the approver UID can call `approval-get` followed by
`approval-decide` over IPC without `nexus-approver`; the daemon cannot tell the interactive CLI from a script.
The daemon does enforce: prior authenticated review of the exact request, digest and review-code echo, expiry,
single use, and that the approver channel is unreachable from the issuer/GUI/AI identities. The `tty` field is
client-attested and recorded as `notVerified`. Terminal interaction and code echo are friction, **not**
cryptographic proof of human presence. Verdict #2 therefore stays **PARTIAL** and privileged GUI approval stays
disabled until a trusted confirmation mechanism (PAM/polkit/FIDO or a trusted display) exists.
