## 3. DNS and SSRF audit

**Why the Registry rejected opencode.ai.** opencode.ai resolves to 4 A (172.65.90.20–23) and 4 AAAA (2606:4700:78::90:0:140–143) records, all genuine public Cloudflare addresses. The JS Registry policy (`provider-config.cjs`) deliberately treats *every* IPv6 literal as restricted (it "cannot be proven public" offline) and refuses the host if *any* answer is restricted. So this was a conservative by-design rule, **not a misclassification**. The Rust classifier (`nexus-contracts/src/destination.rs`) classifies those AAAA addresses as public.

**The workaround.** For the Go profile only, the probe resolves with `family: 4`. Assessment:
* Every address the probe may dial is still validated by the unchanged `checkRequestTarget` (any restricted address → whole host refused). AAAA records are simply never dialed, so the dial set is a subset of what was previously (not) permitted — no rule is relaxed.
* An AAAA-only host yields an empty answer → refused (fail closed). Tested.
* Pinning, SNI/hostname verification, `redirect: manual` with redirect refusal and per-request revalidation are untouched (`RegistryR4TransportBinding` 19/19, `RegistryR4ProbeSecurity` 16/16; new redirect test).
* Other providers keep the unchanged lookup (tested).
* The Rust production transport is the stricter-or-equal party for the *executed* request: it resolves once, classifies every address, connects only to the approved IPs, verifies the peer address, refuses redirects, uses no proxy (A5.2 suites + new `dns_policy_a54`). It permits public IPv6; JS is stricter. Registry verification is therefore not more permissive than execution.

**Inconsistencies found and closed (all by tightening):**
* JS `isSpecialV4` did not reject 198.18.0.0/15, 192.0.0.0/24, 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, all of which the Rust classifier refuses → aligned.
* Rust IPv6 classifier now also refuses 100::/64, 2001:2::/48 and 3fff::/20 (previously public by omission).

**New regression tests.** Rust `dns_policy_a54` (4): dual-stack public accepted with all four addresses pinned; 29 restricted addresses (v4 loopback/RFC1918/link-local+metadata/CGNAT/benchmarking/doc/multicast/reserved; v6 loopback/unspecified/link-local/ULA/multicast/doc/NAT64/6to4/Teredo/discard/benchmarking; v4-mapped 127/10/169.254) each refused alone and when mixed *before*, *after* and *among* public A+AAAA answers; empty answers; obfuscated literals (`2130706433`, `0x7f.1`, `0177.0.0.1`, `127.1`, `[::1]`, `[::ffff:7f00:1]`, `*.corp`, `*.internal`); production policy never admits loopback. JS (`NativeOpenCodeGoRoute`, +2): same matrix through the real probe path with a mocked resolver (A/AAAA only, mixed, private in either order, mapped-in-A), redirect refusal, shared-checker IPv6/mapped/literal cases.

## 4. Stale-broker prevention
* Cause: see §1.5. The single-instance lock worked (new broker refused) — the failure was that nothing surfaced it.
* `nexus-broker` records `instance.json` (pid, exe, start time) under its lock. Identity = (device, inode) of the executable: a rebuild always yields a new inode while `/proc/<pid>/exe` keeps the old one. No hashing, clock or file-name trust.
* Enforcement points: (a) the live gate refuses with `broker-stale` **before** consuming the authorization (the record survives); (b) `nexus-broker authorize-live` refuses to write a record while the recorded running broker is an older build; (c) `nexus-broker identity --state-dir D` (exit 0 current / 3 stale / 4 none); (d) `a54-dev-instance.sh check`, `start` (refuses over a live instance and verifies the new broker is current), `stop` (signals only a pid whose command line names this instance's state paths; mismatched pid files are not signalled; unrelated processes are never touched).
* Verified end to end with a real process: start → second start refused → rebuild simulated by replacing the binary → `check` reports STALE (exit 3) → `authorize-live` refused with no record written → stop leaves nothing running. Unit tests cover replacement, hard links, missing files, dead/recycled pids, garbage records.
* Single-instance and single-use guarantees unchanged.

## 5. Streaming correctness and tool isolation
Local verified-TLS fixtures only (no provider calls). `opencode_go_a54` now has 23 tests, including: chunk boundaries split across separate TLS writes (3-byte writes) and mid-UTF-8; many chunks per read; extensions (including quoted `;`) and trailers; zero-length final chunk; SSE events spanning chunks delivered once and in order; premature EOF (missing terminal chunk with an otherwise complete stream — **mutation-checked**: disabling the new guard fails the test; EOF inside a chunk, inside a size line, headers-only); malformed sizes (non-hex, `0x`, negative, empty, padded, overflowing, 16 MiB+ declared, bare-LF framing, missing CRLF after data); Content-Length + Transfer-Encoding, stacked/duplicate/unknown transfer codings and any non-identity content-encoding refused; 4 MiB flood bounded by the transport cap; cancellation mid-chunk yields `Cancelled`, never data. A chunked body that never reaches its terminal chunk is reported truncated and cannot complete a run.

**Tool isolation.** Registry *route verification* sends a synthetic `probe_echo` tool and a tool-result continuation, because the Registry role `muse_main` requires `toolCalling` capability; that is a Registry capability claim about the route and is entirely separate from the model-only executor. The executor's Go request body never contains `tools` (the adapter refuses them), and model output cannot invoke tools or touch the workspace (A5.3 fixtures, unchanged and green; stream tool-call events are not executed). The acceptance request was sent with no tools.

## 7. Limitations and why production is NOT READY
* One successful live sample; no soak, rate-limit, error-rate or long-stream evidence. The provider docs were read through a summarizing tool; only this one call confirms the contract.
* No provider request id header was observed; billing/charge verification is unavailable. Failed attempts' usage is unknown.
* Dev pilot is single-UID with `shadow-test` trust; production-v1 profile was neither used nor modified. Same-UID applications remain indistinguishable; the single-process broker, spend enforcement, systemd hardening and external-witness gaps from A5.3 stand.
* The Desktop was not exercised against the live broker; it polls (~1.5 s) and re-verifies transcripts per call.
* The JS Registry probe policy is stricter than the Rust transport (all IPv6 refused); the two are consistent in direction but not identical.
* Registry route verification costs 1 GET + 4 POST and an operator authorization per run; route re-verification on provider changes is manual.
* `.env` in the repo root is world-readable (0644) — operator should `chmod 600 .env`.
