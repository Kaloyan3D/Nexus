## 1. Architecture review (ten questions, answered)

1. **Source of truth.** Task/attempt/completion: TaskController JSONL
   ledger (sole writer: Task.ps1 lifecycle). Model resolution: JS Registry
   (sole compiler). Shadow durability: Rust SQLite receipts (sole writer:
   kernel accept transaction). Each datum has exactly one owner; every
   other copy (shadow intent, outbox pin, diagnostics) is re-derivable.
2. **Ownership.** Only the Controller creates attempts — the shadow adapter
   has no code path that invokes begin-attempt (proven by C5/B5 ledger-byte
   invariance tests). Only the kernel writes receipts. The bridge writes
   only shadow-outbox.jsonl + shadow-diagnostics.jsonl (new files the
   Controller never reads).
3. **Dependency direction.** Volatile -> stable: shadow JS -> kernel CLI ->
   store. Rust never imports JS; the kernel never calls back. No cycles.
4. **Service boundaries.** The boundary contract is bridge protocol v1
   (section 3): typed JSON requests/responses, kebab-case codes, 1 MiB
   request cap. Forbidden from crossing: live objects, credentials, raw
   prompts, executable paths (the vocabulary cannot name them).
5. **Failure semantics.** Kernel down -> explicit error/uncertain
   diagnostics, zero Controller mutation (C5). Lost ACK -> receipt reuse by
   commandId (C1/B2). Concurrent duplicates -> one receipt + replay/conflict
   (C2). Changed identity -> command-conflict preserving prior authority
   (C3). Stale lease -> refusal, no generation replacement. Missing witness
   on protected generation -> witness-required (C6). Unsupported outcome ->
   explicit status, never guessed success.
6. **State lifecycle.** Shadow pin: created on delivery/replay, immutable
   afterwards; registry change after pin -> refuse (registry-changed-after-
   pin). Generations: kernel-owned monotonic epochs (A1.1). Outbox lines:
   append-only under runs/<taskId>/, same retention as the task ledger.
7. **Test seams.** Reader injection (Controller files), service injection
   (Registry), invokeBridge injection + real-CLI default, temp workspaces +
   temp kernel stores everywhere. No sleeps; pwsh section awaits process
   exit deterministically.
8. **Migration/compatibility.** No contract version change (schema stays 1);
   canonical test vectors untouched and re-proven cross-language
   (bridge_digest_oracle_matches_canonical_vectors + A2). Existing suites
   all pass unchanged. Rollback = delete the four new modules + bridge
   subcommands; the kernel binary keeps init/status behavior identical.
9. **Observability.** shadow-diagnostics.jsonl per task (delivered /
   replayed / refused / error / uncertain / skipped-* with codes);
   journal subcommand reconstructs generation state; status still reports
   dispatch_enabled=false.
10. **Security implications.** No new privilege: shadow runs with the same
    OS user, reads task ledgers + trusted config, writes task-scoped shadow
    files + its own SQLite stores. No secrets cross the bridge (ids/digests
    only; secret-shaped values redacted even in logs). Same-UID hostile-peer
    and cross-domain rollback limits from A1.1 are retained and restated
    (section 7), not widened.

## 3. JS -> Rust bridge transport (protocol v1)

- Request: `{ protocol: 1, ... }` from a file named by argv
  (`--db PATH [--witness PATH] --input REQUEST.json`); 1 MiB cap enforced
  pre-parse; non-object/invalid JSON/oversize -> stderr + exit 2 (process
  failure, never a kernel verdict).
- Response on stdout: `{ protocol: 1, ok: true, ... }` or
  `{ protocol: 1, ok: false, code, message }`; exit 0 whenever a
  versioned verdict was produced (including refusals).
- Strict schema validation per subcommand (typed fields, length caps,
  protocol==1, intent must NOT carry its own lease — the lease comes only
  from acquire_generation). Unknown subcommand -> bad-request envelope.
- accept = seal-check + digest verification + A1.1 accept_command;
  response `{ receipt, replayed }` with receipt.status always
  accepted-reserved-dispatch-disabled. journal = generation events +
  receipt reconstruction (bounded 5000, truncated flag). digest = canonical
  oracle proving JS<->Rust byte agreement.
- Trust: local-subprocess only — explicitly NOT production IPC auth. The
  prototype operates in an isolated trusted test boundary; real deployment
  stays shadow-only (blocker B3).

## 4. Rust kernel integration (existing A1.1 APIs, unchanged semantics)

acquire_generation -> seal_issuance (bridge-verified, forged-issuer
otherwise) -> accept_command (immutable command, durable receipt) ->
read_receipt by commandId -> journal reconstruction. Raw callers cannot
manufacture trust: unsealed/tampered resolutions fail forged-issuer/
delivery-invalid before any write (bridge tests + C3). Stale-lease checks,
receipt-conflict rules and rollback-witness requirements are untouched
(A1.1 suite still 43/43-equivalent: full workspace 52/52 incl. 9 new).

## 5. Controller shadow integration (flag OFF default)

NEXUS_NATIVE_SHADOW env-only, default OFF. OFF = flag check then return:
no reads, no writes, no subprocesses (D1 proves no shadow files and — via
a bogus kernel path — no invocation). ON = observe committed attempts,
resolve real bindings, submit immutable shadow commands, record
diagnostics; routing/attempts/verification/completion untouched (B5/D2
prove ledger byte-invariance with the flag ON).

## 6. Shadow reconciliation (deterministic)

Receipt-first: existing receipt with matching issuance identity -> replayed
(ACK recovery). Else acquire->seal->accept under a per-commandId lock.
Conflict on accept -> receipt re-read, prior authority reported. Stale lease
-> refusal, never replaced. Changed registry after pin ->
registry-changed-after-pin. Unreadable outbox/receipt -> uncertain (never
success). Bounded scope (64 attempts/scope, 10000 outbox lines), retention
= task ledger retention. Kernel receipts NEVER imply Controller completion.

## 7. Security and durability gates (explicitly retained)

Still unsupported, restated (not hidden): real external dispatch (binary
has no such subcommand; dispatch_enabled=false; authorize_dispatch always
refuses); exactly-once inference / tool effects; same-UID hostile-peer
protection; full independent-failure-domain rollback safety; arbitrary
automatic recovery after lost witness. The A1.1 cross-store crash window
(SQLite acceptance vs external witness note) persists: the bridge narrows
its blast radius (receipt-first reads, conflict surfacing) but does not
close it. A genuine Controller outbox would need transactionality the
TaskController JSONL ledger cannot provide — the adapter is therefore
documented NON-authoritative and reconciliation-based (no atomicity
claimed anywhere).

## 10. A1.3/A2 blockers and rollout controls

- B1 (carried): cross-store crash window (SQLite accept vs witness note) —
  needs a witnessed-transaction design before any authoritative use.
- B2 (carried): no Controller+shadow atomicity — TaskController JSONL
  cannot join a SQLite transaction; shadow stays non-authoritative until a
  real Controller outbox exists.
- B3 (new): bridge transport is trusted-local-subprocess only; any network
  or multi-user deployment needs authenticated, replay-resistant IPC before
  A1.3 enables anything beyond shadow observation.
- B4 (new): immutable-pin preservation across Registry change is refusal
  today; A1.3 must design verified-pin retention if history must survive
  config evolution.
- B5 (new): scope is muse_main/engineering-v2; other modes/roles need per-
  mode authorization review, never silent mapping.
- Rollout: keep NEXUS_NATIVE_SHADOW default OFF; enable per-machine for
  observation only; gate A1.3 on closing B1-B3; A2 dispatch gates stay
  closed (dispatch_enabled=false proven in-suite).
