# A7.1 — Persistent conversations and multi-task sessions: design

Status: implemented, **uncommitted**. Evidence: `native/A7.1-EVIDENCE.md`. Builds on A6.1.4/A7.0 (interactive profile, autonomous workspace policy, project registry, continuation). Nothing here adds authority; every run is still a normal `repo-code` run with its own isolated copy, limits, provider consent and durable receipts.

## 1. The problem

Before A7.1 a task was a single run: after it finished the only action was "+ New task". Follow-ups ("Fix F1", "now explain F2") had no way to refer to the earlier report, the earlier changes or the earlier test results, and the Desktop had no notion of a discussion.

## 2. Vocabulary (one meaning each)

| Term | What it is | Where it lives |
|---|---|---|
| **Conversation** (`thread`, id `thr_…`) | Durable discussion about **one project**. Many per project. | broker state `threads/<id>.json` |
| **Message** | `user` request, `assistant` answer, or `system` note, ordered by `seq`. | `threads/<id>.log` (append-only JSONL, fsync'd) |
| **Run** | One autonomous execution started by one request (or one automatic continuation). Has its own record, working copy, receipts. | broker `runs/<id>.json` (unchanged) + `ThreadRun` entry |
| **Workspace** | The conversation's isolated project state: each run's working copy is seeded from the previous run's. | daemon worktrees (unchanged) |
| **Context** | The bounded reconstruction of the above that the model receives. | built per run, never stored |

The word *conversation* in older code (`model_<hex>`, the transcript id) still means the per-run model transcript; the UI and API of A7.1 call the durable discussion `thread`/"conversation" and never mix the two ids.

## 3. Storage

* `threads/<id>.json` (atomic rewrite): title, project, archived flag, `legacy` flag, `runs[]` (each with mode, read-only flag + reason, state, `ended`, a **run digest**), `findings[]`, counters.
* `threads/<id>.log`: messages, append-only. A torn last line (crash mid-append) is ignored; the sequence counter is repaired from the log on reconcile.
* **Run digest** (from receipts, never from model text): files edited by the run, files that differ from the project in its copy, every executed edit/command with its `pass`/`fail` verdict (up to 120), runtime-verified outcome (`verified-passed`…), turns/tool calls/recoveries/compactions, stop reason and error. It outlives the run record's bounded 64-entry activity list.
* Per-conversation mutex (`ThreadStore::mutex`): two conversations never contend; within one conversation every read-modify-write is serialized. A conversation accepts **one active run at a time** (`thread-busy` otherwise).
* The strict profile does not use conversations (it must not persist task text in broker state); `thread-*` verbs answer `not-available` there.

## 4. Context reconstruction (what the model receives)

The provider conversation is stateless, so continuity is a property of the first model turn of each run, not of the UI. `threads::context_for_run` builds, deterministically and with no model call:

```
## Conversation context (Nexus's durable record)        # "this is NOT the first request; treat it as your memory…"
### Findings index                                       # F1…Fn: title, status (open / addressed in run N + runtime-verified outcome), detail
### Working copy for this run                            # continued / rebased / fresh / fresh-by-choice, files that differ
### Run 1 (read-only)  User request … Your answer then … Runtime record: this run changed … ; `cargo test` -> pass ; outcome
### Run 2 …
## The user's new request
<the text the user typed>
```

* The latest answers are kept whole (a review report with its F-numbers), older ones shortened (head + tail), then one line per run.
* **Budget**: a quarter of the broker's context budget, capped at 48 KiB. Levels L0…L5 shrink request/answer caps; then the *oldest runs are dropped one by one*; the findings index and the working-copy section are rendered **first** so they are the last thing any cut can reach. Property tests assert: output ≤ budget; findings, verified results and the newest request survive at every budget from 48 KiB down to 6 KiB.
* Findings (`F\d+`) are extracted from answers by structure (headings, bold, list numbers, table rows). A newer *review* with several findings replaces the numbering; follow-ups never rewrite a known finding. When a run that may edit finishes with ≥1 applied edit, findings named in its request are marked *addressed in run N* with that run's verified outcome.
* The in-run compaction of A6.1.4 (`context::compact`) is unchanged and still protects the first message, which carries this block.
* Raw transcripts are never replayed.

## 5. Read-only requests (no implicit write permission)

`threads::classify_mode(text, requested)` decides per request: *Auto* | *Review only* | *Make changes*.

* Text can only **restrict**: "don't change any files", "read-only", "no edits", "without modifying anything" … make the request read-only even if *Make changes* is selected. Ordinary constraints ("don't change the public API", "make the field read-only", "don't change any file except …") do not. Unit-tested on 18 phrasings.
* *Auto*: a question or review verb with no change verb → read-only; anything else → may change files in the isolated copy.
* Enforcement is in the broker's proposal gate, not in the prompt: `policy.read_only` makes every `fs_edit`/`fs_write` proposal a refusal (`budget-exhausted`, with the reason) before any approval/policy grant is requested; `max_edits` is 0; auto-adopt never runs for a read-only run. The preamble also tells the model, so it normally does not try.
* The UI shows the mode and the reason on every run ("Read-only" / "Can change files") and, for read-only runs, "Read-only · N edit attempts refused · no file changed" computed from the receipts.

## 6. Workspace continuity

Each follow-up run starts from **the working copy of the newest run of the conversation that has one** (`seed_from`), whatever that run's outcome (completed, failed, cancelled, recovered). The daemon seeds the new copy:

* same project snapshot → copy exactly the earlier run's changes (`worktree-seed`, existing);
* project snapshot moved on (the folder changed, or the earlier patch was applied) → `seed_rebase`, per file the earlier run touched:
  * the new snapshot already has the same content → *already in your folder* (nothing to do);
  * the project did not change the file → carried;
  * both changed it → **conflict: nothing is written**, the run ends `rejected` with code `workspace-conflict` and the file list, **before** provider authorization is spent. The conversation offers one explicit choice, *Continue from my project's current files instead* (`workspace: "fresh"` → relation `fresh-by-choice`); the earlier copy is kept for review.
* earlier copy removed: if it held changes → `workspace-missing` (explicit); if it held none → starts fresh with a note.
* The user's original folder is never written by a run. Adoption is the existing explicit, fingerprint-guarded action (or the trusted-workspace auto-adopt, which skips read-only runs).
* The run records `workspace_relation` / `workspace_note` / `seed_from`; the UI shows them per run.

## 7. Reliability

* **Crash recovery**: runs are recorded in `runs/` first; `thread-send` appends the request only after the run exists. `startup()` (a) adds back runs that point at a conversation which does not list them (request text from the run record), (b) migrates legacy records, (c) folds every finished-but-unfolded run (answer from the transcript, digest from the record), (d) repairs the sequence counter. All idempotent. Folding is done by the executor with the complete activity list and final text; readers only fold runs whose executor is gone.
* **No duplicated local operations**: a follow-up starts from the previous copy and is told, from the runtime's receipts, what was already done; provider failures inside a run keep the A7.0 recovery (new attempt, no re-execution). Tested: an earlier run's write is executed exactly once across a stop + a follow-up that suffers lost provider answers.
* **Interrupted runs continued by Nexus** (`resume_run`/auto-continuation) join the same conversation; a newer user message supersedes an interrupted run (it is no longer continued).
* **Isolation**: a conversation is bound to its project (`project-mismatch` otherwise) and owner; context is built only from that conversation; separate working copies per run. Tested with two simultaneous conversations on one project and a second project.
* **Legacy single-run records** (and continuation chains) become one-run conversations with deterministic ids on first start; the original run records are only annotated with their `thread_id`.

## 8. Broker verbs, Tauri commands, CLI

`thread-send`, `thread-list`, `thread-get`, `thread-create`, `thread-update` (rename/archive; nothing is deleted). Tauri: `thread_list|get|send|create|update` (allowlist, capability file and build manifest updated; the renderer sends text + project identity + mode/workspace choice + idempotency key — no path, tool, limit, model or approval). CLI: `nexus intent thread list|show|send`.

## 9. Desktop

* Workspace shows the open conversation: chronological turns (your message → run block → Nexus's answer → runtime notes). The run block carries the run's own status, mode chip, workspace note, steps, and its **verified** outcome/evidence buttons (diff, test output, execution evidence, apply) — separate from the conversation's state ("Working" / "Ready for your next message") in the header.
* The composer is always at the bottom: Send after any run (completed, failed, cancelled, recovered), Stop while a run is active. *Auto / Review only / Make changes*. After a workspace conflict it offers the explicit "current files" choice.
* Idle view and History list conversations (project filter, search, "Runs" tab for the per-run view). *New conversation* starts empty with fresh context. The last open conversation is restored when the app reopens; routes are `#/workspace/c/<id>`.
* A findings bar lists the remembered findings and which runs addressed them.

## 10. Limits and non-goals

* One active run per conversation; no branching/forking of a conversation.
* Findings extraction is structural (best effort); if a report uses no F-numbers the answer text itself is still carried.
* The context is deterministic and lossy by design (budgeted); the stored record is complete.
* Not started: Nexus Nova, Engineering Mode v3.
