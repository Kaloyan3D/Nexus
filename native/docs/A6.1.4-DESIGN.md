# A6.1.4 — Zero-configuration autonomous engineering harness: design

Status: design + implementation log. Everything runs offline unless stated; provider experiments are real OpenCode Go (`opencode-go-native` / `muse-spark-1.3-contributor`) under the operator's standing development-test authorization. Nothing is pushed, merged or deployed.

## 0. What the user must do (target)
Install, connect OpenCode Go once (API key), open a project with the OS folder picker, type a request, press Run. Everything else is orchestration.

## 1. Which ceremonies disappear, and what replaces them

| Ceremony today | Replacement | Boundary that stays |
|---|---|---|
| `nexus-broker authorize-live-session` (prompt hash, single use) | **Provider consent** (one-time, native confirmation dialog, stored by the broker) + **internally issued run-scoped authorization**: at submit the broker writes the same single-use record (`live_auth`) bound to the run's prompt SHA-256, project, limits, expiry, plus an append-only audit line | the model cannot call broker verbs; the record is per run, consumed once; strict mode (manual record) remains for restricted operation |
| per-operation human approval | **Automated workspace policy grants** (kernel-recorded, `humanAuth.kind = automated-policy`, never labelled human) for operations that pass a deterministic policy | Kernel still creates/validates/consumes approvals; daemon evaluates policy from daemon-held facts only; out-of-policy operations are refused, not queued |
| `A613_*` env vars, dev-instance script | **Runtime supervisor** inside the Tauri backend: finds/starts `nexusd` + `nexus-broker` as the user's own child processes, readiness, reconnection, diagnostics | OS peer-uid checks unchanged; renderer never spawns anything |
| `nexus project add`, pin, scope | **Project onboarding**: native folder picker → backend validation → managed snapshot repo + registry entry | renderer never supplies a path; registry written by the broker identity that owns it; same trust checks as the CLI |
| working-copy cleanup | automatic retention policy (keep last N inactive copies/size cap), manual controls under Diagnostics | active/leased copies never removed |
| per-task limits | built-in interactive defaults (see §6) | broker caps still the ceiling |

Two profiles, chosen at daemon start and latched in the Kernel store: **strict** (today: independent human approver, manual session record; for restricted/security-sensitive use) and **interactive** (new: automated workspace policy, consent-derived authorization; single OS user). A store that ever ran strict cannot be restarted interactive (no-downgrade latch ranks: none < automated < test-only < independent).

## 2. Autonomous Workspace policy (P3)
* Daemon flag `--autonomous-workspace-policy`; refused by the production-v1 profile; implies approval mode (approvals are still created, journaled, consumed once) but has **no human approver channel**: `approval-get/decide` are refused, no approver credential is generated.
* On `approval-request` the daemon evaluates policy `autonomous-workspace/v1` over facts it holds, never over model/renderer claims:
  1. the task has a daemon-created isolated copy (identity record exists) and the approval's workspace-root digest equals that copy's;
  2. tool class ∈ {`fs.write`, `fs.edit`, `proc.run`}; writes: relative path inside the copy, not protected (lock/build/CI/hidden/credential-shaped paths, `.git`), inside the project's frozen write scope, size caps; process: argv accepted by the sandbox command allowlist **and** the project's detected execution profile, network off;
  3. per-task budgets (edits, commands, bytes) not exhausted.
  Passing → `Kernel::decide_approval_by_policy` (pending → approved, `approverId = automated-policy:autonomous-workspace/v1`, `independent=false`, `humanAuth = {kind: automated-policy, human: false, policyDigest}`); failing → refusal with a reason. The Kernel additionally requires the store latch to be the automated level and re-derives authority (lease, receipt, binding, digests) — the policy cannot approve anything the Kernel would not otherwise authorize.
* Outside this authority, always: host paths, original repositories, secrets, Git remotes/pushes, deployments, network.
* UI/receipts record "Automated workspace policy" for these grants; nothing says "approved by you".

## 3. Provider authorization (P1)
* `provider-consent-grant/revoke/status` broker verbs (client uid gated). The Tauri backend calls grant only after a **native** confirmation dialog it owns (the renderer cannot synthesize the click), naming provider, model, what leaves the machine, and the autonomy level. Consent is a durable record with a text digest and timestamp; revocable in Settings.
* At `intent-submit` for `repo-code` in interactive mode the broker, if consent exists, issues the per-run record by calling the existing `write_session_record_for` path with `issuer = interactive-consent:<id>` and appends `live-auth-audit.jsonl`. All existing checks (prompt-bytes digest, limits, expiry, single use) apply unchanged. Strict mode keeps requiring the operator's manual record.

## 4. Project onboarding (P2)
* Tauri command `project_open()` shows the OS folder picker; the **backend** receives the path. Validation: canonicalize, directory, not a symlink-escape, not inside Nexus's own data or well-known sensitive roots (`~/.ssh`, `~/.gnupg`, `/etc`, `/proc`, …), size/file-count caps, ownership = current user.
* Detect: Git (branch, HEAD, dirty), project kinds and execution profiles (§7), test/build commands.
* **Managed snapshot**: a Nexus-owned git repo under the data root holding a commit of the current tree (respecting ignore rules + built-in excludes). The registry pin is that commit. Dirty trees and non-Git folders work; the user's directory is only ever read. `project_refresh` re-snapshots (new commit, new pin); new tasks auto-refresh when the folder fingerprint changed; running tasks keep their copy and base.
* The broker owns the registry write (`project-register` verb; same `registry` module, same checks). Registry persists across restarts; `project-list` restores the list.
* Adoption: the patch is relative to the snapshot commit; the Desktop shows whether the original changed since the snapshot; applying to the original is an explicit, confirmed action (never automatic).

## 5. Runtime lifecycle (P5)
Supervisor (Rust, in the Tauri backend, same user): data dir `~/.local/share/nexus` (`NEXUS_HOME` override) → bootstrap (Registry config via the existing setup script, credentials file 0600 from the Settings flow, daemon data root) → start `nexusd` then `nexus-broker` as child processes in their own process groups, wait for readiness (daemon health, broker `intent-models`), detect an existing healthy instance (identity file + socket), reconnect with backoff, clean shutdown on exit, crash recovery by the daemon/broker startup recovery already present. Diagnostics panel shows logs/paths/versions. No privileged installer is needed for the interactive profile because daemon, broker and Desktop are the same unprivileged user; the strict profile keeps its multi-UID deployment and needs a real installer (out of scope here, documented).

## 6. Limits, context, recovery (P4)
* Empirical finding (P0): `max_output_tokens` includes **reasoning tokens** (738–1793 of 1024–2048 at effort `low`); 1024 truncates tool calls. 16/16 requests at ≥4096 completed (max 2492 output). Interactive defaults: **16384** output tokens per turn, ceiling 32768, 60 model turns, 200 tool calls, 40 edits, 30 commands, 45 min, 512 KiB of tool results.
* Truncation is a **turn outcome**, not a run failure: when a turn ends `incomplete:max_output_tokens` nothing from that turn executes; the next turn (a fresh Kernel authorization and provider request, recorded as such) runs with a larger cap, at most twice consecutively. Never re-sent silently: every provider request has its own attempt/digest.
* Context management: history is stateless (re-sent per turn); old tool results are compacted to stubs (path/command + digest + size) once the estimated input passes a budget, keeping the latest results and all edit receipts.
* Uncertain outcomes (crash between effect and receipt) stay `uncertain` and are never replayed; resumption starts a **new** run that reads current copy state.

## 7. Execution profiles (P6)
A profile = detection rule + allowed argv set + sandbox env + read-only toolchain mounts. Selected automatically from the project; no shell. Implemented incrementally with sandbox verification: Rust (existing), Node/TypeScript (`npm test`, `node --test`, `npm run build`, `tsc --noEmit`), Python (`python3 -m unittest`, `python3 -m pytest` when installed, `python3 -m compileall`), then Go and .NET behind their own verification (toolchains/caches not available on every host; roadmap in the evidence doc).

## 8. Reuse of A6.1
Kept as is: Kernel approvals/journals/grants, daemon worktree/diff/lifecycle, registry (+ ownership rules), broker inspect/code loop, `derive_coding_outcome`, receipts, Desktop task view/evidence panel, strict mode and its multi-UID tests. Changed: Kernel gains automated decisions + latch rank; daemon gains the policy flag; broker gains consent/onboarding/limits; Tauri gains supervisor + native dialogs; Desktop gains onboarding and one-click Run.

## 9. Acceptance (P7)
`dev-acceptance` runner starts the real stack through the supervisor entry point, opens a fresh project through the same backend call the folder picker uses, submits a multi-file task to real OpenCode Go, and checks: no manual setup, source inspection, automated grants (not human), sandboxed tests, failure analysis + correction, receipts/diff visible, persistence after restart, original unchanged. Fixture runs (scripted model) are labelled `fixture`; provider runs `provider` in the report.
