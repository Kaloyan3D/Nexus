# Diagnosis — R-NATIVE-1 self-development: planning loop, false completion, re-reading loop

Evidence: durable run records, hash-chained transcripts and thread logs of the live dev instance. Observed facts are separated from hypotheses.

## A. First report: conversation `thr_e8f71b6d7f15c90b6713bd55ecf4e95e`
**Run 1 was read-only by mistake (Nexus defect).** The request ("Implement checkpoint R-NATIVE-1 …  Do not modify the original repository, commit, push or deploy.") matched the A7.1 read-only phrase detector (`do not modify … repository`), mode reason "you asked not to change any files". The sentence restates where changes go; it is not an instruction to change nothing. Fixed: a negated change followed by a protected *target* (original, upstream, remote, production, live, main, …) no longer counts (`threads.rs`, `PROTECTED_TARGET`).

**Run 2** (`run_df746c9ae1bc117aa30cd163188ad5e7`, edit mode, 41 turns, 40 tool calls, 0 edits, 0 tests, 8 provider recoveries, 0 compactions, 1.79 M input tokens):
* Observed: 40 distinct, progressive read-only exploration calls (reads of the Registry, bridge, broker, tests). Every turn the model wrote one progress sentence ("Exploration is done — now I'll implement …", identical up to five turns in a row) and made another read. No edit was ever proposed. Tool schemas/dispatch worked (40 structured calls, executed).
* Observed: the last turn (provider finish `stop`, 71,651 in / 8,733 out tokens) contained **no structured tool call**; its 40,035-character text was a degenerating monologue: pseudo tool syntax (`absoluto=default.fs_search_close...`), "I keep deliberating; just fire", "Firing now for real", invented harness rules ("orchestrator will re-invoke you" — grep finds this text neither in the repository nor in Nexus code), the garble `Zsorry`. The model itself called part of it a "drafting glitch".
* Observed: Nexus accepted it as `completed`. Mechanism, reproduced by `a_planning_ramble_is_no_longer_accepted_as_the_finished_task`: the `premature_stop` heuristics only rejected short mid-flight messages, and for long ones `looks_like_report` (≥1500 chars with any bullet/heading line) treats a ramble as a finished report. Nothing compared the request ("implement") with the evidence (0 edits, 0 tests).
* Verdict: **interaction**. The degenerate final turn and the exploration-without-action habit are model behaviour (provider-level SSE bytes are not recorded, so "plain text instead of a function_call" is established from the transcript: no tool-call event exists for that turn). Accepting it as success is a Nexus defect. Excluded with evidence: malformed schemas (same tools worked for 40 calls), parser/dispatch failure, compaction (0), provider-recovery corruption (recoveries re-ask the same items; no divergence), role/message boundaries, contamination from repository text (the "instructions" are not in the repo).

## B. Second report (my acceptance reruns): the re-reading loop — a Nexus defect
Attempt 1 (fixes for A in place): 58 turns, 5 edits in 2 files, one passing test run, then a one-line announcement ("Selection issuance is wired — now the bridge commands …") was accepted as completion (28 output tokens, finish `stop`; edits existed, so the plan rules did not apply). → new rule: a short forward-looking message with edits but no passing check is nudged, and recorded as incomplete if it persists (`completion::announcement`).

Attempt 2 (`thr_b86c95b5fc8d024f5e3a68941a9c047c`, cancelled by me at turn 281; **you were right, it was looping**): 277 tool calls, **4 edits, all in turns 30–46, none in the following 231 turns**, 226 context compactions, 34 recoveries, 9.2 M input tokens. Of 121 `fs_read`s, 106 re-read a path already read; `native-intent-bridge.cjs` was read 24 times, `native-catalog.cjs` — a file the model had written itself — 17 times, the task file 15 times. The model's own words after turn 55: "Missed the task spec — reading it now", "Resuming R-NATIVE-1: verifying …", "Checking current state and remaining gaps", repeated.

Root cause (observed in the code and the counters): `context::COMPACT_ITEMS = 160` is an **item count** (≈ 53 tool turns), unrelated to any byte or token limit — the model's window is 1,048,576 tokens and the conversation held ≈ 100 K. From turn ≈ 53 on, *every* turn compaction (1) stubbed **all** tool results older than the last 36 items (12 turns) at once, and (2) dropped the oldest step. The model's working memory was therefore twelve turns; a task whose working set (bridge, issuer, target, catalog, server.rs, task spec, tests ≈ 100 KB) does not fit in twelve turns thrashes: read file A, forget it, read B, forget A, … while the stub text itself says "call the tool again if you need it". 226 compactions in 281 turns = one per turn. Not a model fault: the same model made 4 edits in turns 30–46 while its history was intact.

## Corrections (all with regression tests that drive the real decision paths)
1. Mode classification: protected-target phrases are not read-only (`threads.rs`; unit + end-to-end `completion_an_implementation_task_that_forbids_touching_the_original_is_not_read_only`).
2. Completion classification from request + receipts (`completion.rs`): `fulfilled` | `no-change-verified` | `no-change-reported` | `incomplete`. An implementation request with zero executed edits and no passing check that ends on a plan, on tool calls written as text, or on an announcement is nudged (bounded: 5) and then recorded `incomplete` (`limit-reached`, stop reason `no-implementation`) with a visible reason; valid no-ops (a passing check, or a plain statement) and non-implementation requests (reviews, "how would I implement …") are untouched. Follow-ups/continuations that already carry changes may verify without editing.
3. Exploration steer: after 24 tool calls with no change (or the same progress sentence three turns running) one reminder per block (max 3) tells the model to start editing. No side effects, no limits.
4. Compaction no longer driven by item count: item cap 440 (transport max 480); stubbing is oldest-first and only as far as the byte budget requires; whole steps are dropped only after that.
5. Working memory: at 330 items / 800 KB (or ⅔ of a configured budget) the model is asked to write its own working memory (facts, paths, changes, decisions, next steps); it replaces the old steps (`context::fold_into_memory`). A reply that calls tools instead is handled as a normal turn and the request is repeated once.
6. A plan/ramble that changed nothing is not fed back to the model in the next run of the conversation (shortened, labelled).
7. Desktop: runs show "Incomplete · nothing changed" / "Completed · no change was made" / "No change needed · checks passed" with the reason as a conversation note.
8. (Earlier in this investigation) Controller attempt bound 96 → 5000 and clean `limit-reached`; the real failure reason is kept in `errorMessage`; context fits the 32 KiB message bound.

Regression tests added: `completion::*` (6 unit), `inspect::a_planning_ramble_…`, `context::*` (oldest-first stubbing, memory fold), end-to-end `completion_*` (plan loop → incomplete → conversation continues; text tool calls; valid no-ops/read-only/how-to; narration and silent exploration steer; announcement stop; working memory; 80-read exploration untouched), plus the earlier A7.1 suites.

## C. Final live acceptance (R-NATIVE-1, conversation `thr_cf992d42d064cd909b6576ac73629a34`)
* **Run 1** (`run_a9b9bf20…`, 120 turns, 20 edits in 7 files, 4 test runs, 0 re-reads, 0 loops): ended `incomplete`. ### C.2 Further false completions found while driving R-NATIVE-1 to the end (all fixed, each with a regression test)
1. **A `grep` counted as a passing check** (`sh -c "grep … check … Tests.cjs"`): the verification classifier matched words anywhere in the command line. Now it judges each command of a script (quote-aware), and read-only programs verify nothing.
2. **Announcement after an earlier passing check** ("Contract tests pass — now the broker test … attempting it", "Confirmed — running the full suite…") was accepted. Now judged by how the message ends (closing sentences, action gerunds), regardless of earlier results.
3. **A bare "continue" had no completion check** (no implementation verb ⇒ `expects_change=false`): it now inherits the intent of the request it continues (`completion::is_continuation`, `threads::continued_request_expects_change`). A degenerate answer (leaked reasoning, an invented "translate to Spanish" instruction) had ended such a run as `fulfilled`.
4. Known flake: `a71_records_from_before_conversations…` fails occasionally in the full parallel workspace run (2 of 6 runs) and passes alone every time; not caused by these changes.
