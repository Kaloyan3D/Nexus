## What is different from the CLI run

* The Desktop sends **fixed backend limits** (shown in the Composer before you submit): **12 model turns · 30 tool calls · 5 edits · 5 commands · 1024 output tokens per call · 128 KiB of tool results · 30 min**. The renderer cannot change them. The live authorization record must allow *at least* turns 12, tool calls 30, output tokens 1024 and 131072 result bytes (below).
* The task text is bound into the single-use record by SHA-256. What you type in the Desktop must be **byte-identical** to the prompt file used to create the record (one line, no trailing newline, no leading/trailing spaces).
* Submitting requires ticking the disclosure acknowledgement ("selected text … will be sent to the model provider …").
* The Desktop **cannot approve**. Pending approvals appear in a banner above the Composer with the model's proposed change/command, the restrictions and the expiry; you approve only in the separate approver terminal.
* Same-UID development instance: the approver terminal runs as your own user, with the daemon's test-only non-independent-approver flag. The human-in-the-loop property rests on you personally reviewing each request. Human presence and TTY origin are recorded by the daemon as `notVerified`.

## Single-use live session authorization (the point of no return — create it only when you intend the run)

The prompt file and the text you will paste into the Desktop are the same one line:

```fish
printf '%s' 'The test in tests/add.rs fails. Work efficiently: list the repository root once, read src/lib.rs and tests/add.rs, and do not repeat a listing, search or read you have already done. Find the cause of the failure, propose ONE minimal fs_edit to src/lib.rs, then propose ONE `cargo test --offline` to verify it. Every edit and command needs a separate human approval, so propose them one at a time and wait. Do not touch any other file (no Cargo files, no build scripts). If the test passes, STOP: answer with a short summary of the cause, the change and the test result, without further tool calls. If it fails, read the failure output once and make at most one more corrective edit and one more test run.' > $A54_HOME/gui-task.txt
native/target/debug/nexus-broker authorize-live-session --state-dir $A54_HOME/broker \
  --intent-type repo-code --provider opencode-go-native --model muse-spark-1.3-contributor --workspace synthetic-test \
  --prompt-file $A54_HOME/gui-task.txt --max-turns 12 --max-tool-calls 30 \
  --max-output-tokens 1024 --max-tool-result-bytes 131072 --expires-in-secs 1800 --acknowledge-billable
cat $A54_HOME/gui-task.txt | pbcopy 2>/dev/null; or cat $A54_HOME/gui-task.txt | wl-copy 2>/dev/null; or echo "copy $A54_HOME/gui-task.txt manually"
```

The record is consumed by the first submission, even a refused one (for example if the pasted text differs by one byte). Run limits above equal the Desktop's fixed values, which is the largest the record allows.

## Exact prompt bytes — check before you press Start

The record is bound to the SHA-256 of the prompt's exact UTF-8 bytes; the broker compares raw bytes (no trimming). In **Code in copy** mode the Composer shows, under the limits, `Prompt as it will be sent: N bytes · sha256 <hex>` for the text currently in the box. Before **Start coding**:

```fish
wc -c < $A54_HOME/gui-task.txt                  # bytes in the prompt file (must equal N shown in the Desktop)
sha256sum < $A54_HOME/gui-task.txt | cut -d' ' -f1   # must equal the sha256 shown in the Desktop AND the promptSha256 printed by authorize-live-session
```

If they differ, do not submit: a trailing newline, a trailing space, smart quotes or a changed line break each change the hash, and a mismatching submission **consumes** the single-use record and sends nothing (you would need a new record). The file is written with `printf '%s'`, so it has no trailing newline; the textarea adds none either — do not press Enter after pasting.

| # | Step | Expected in the Desktop |
|---|---|---|
| 1 | Open the Desktop; choose **Code in copy**. | The source list contains only `synthetic-test`. The Composer shows the source identity, the fixed limits, and a disabled **Start coding** until the acknowledgement is ticked and the prompt is non-empty. |
| 2 | Paste the task text; tick the acknowledgement; **Start coding**. | The run appears (Recent runs) and moves to executing. A failed submission shows the broker's code/message and keeps your text. |
| 3 | Watch the timeline. | A real `fs_list`, then `fs_read` calls from OpenCode Go appear as tool rows with their results (Conversation tab) and in the Activity table. |
| 4 | Wait for the first approval. | A **Pending approval** panel above the Composer: *Edit file · src/lib.rs*, the model's `- a - b` / `+ a + b`, the restrictions, an expiry countdown and the `nexus-approver … review <id>` command. State **approval-pending**. Nothing has changed in the copy yet. |
| 5 | Terminal B: `list`, then `review <id>`; compare the daemon's diff with what the panel shows; approve only if it is the one-line fix. | After approval the panel disappears, the edit row shows *approved · executed* with a pre→post hash. |
| 6 | Wait for the second approval. | Panel: *Run command · cargo*, `cargo test --offline`, restrictions "network access is disabled", "read-only snapshot…". |
| 7 | Terminal B: review the argv and sandbox policy; approve. | The command row shows *tests passed (exit 0)* and **Last test: passed**; the test output is in the Conversation tab's `proc_run` result. |
| 8 | Wait for the final answer. | State **Completed**; the final summary appears; **Show diff** loads the unified diff (`src/lib.rs` `-    a - b` / `+    a + b`) and the changed-file list. |
| 9 | Quit the Desktop completely and start it again (same command). | The run is in the history; selecting it restores the status, tool table, receipts (pre/post hashes), test result and the diff. |
| 10 | Terminal A: `git -C $A54_HOME/code-base/repo status --porcelain` and compare HEAD with `head-before.txt`. | Empty status, same HEAD. The change exists only under `$A54_HOME/code-base/worktrees/`. |

Do **not** approve anything that is not exactly the expected edit or command; there is no auto-approve. If the model proposes something else, deny/ignore it (approvals expire on their own) and record it as a finding. To abort at any point use the Desktop's **Cancel run**.

## Optional offline look at real history and a pending approval (no provider, no network)

`a61_gui_fixture_hold` runs the real daemon, broker, bridge and sandbox with a scripted model and leaves REAL durable history behind it for the Desktop: five named scenarios (A6.1.1) plus one run held at a pending approval.

| scenario | what happens | verified outcome the Desktop must show |
|---|---|---|
| `approved` | edit and test approved by the fixture, test genuinely passes | Tests passed · exit 0, change applied |
| `expired` | nobody answers; both approvals expire (3 s lifetime in this fixture); the model reports honestly | Blocked · approval expired · not executed |
| `denied` | both operations explicitly denied | Blocked · approval denied · not executed |
| `liar` | approvals expire but the model **claims** "cargo test passes" | Blocked · approval expired · not executed (the claim stays in the Conversation tab as a claim) |
| `pending` | held at the edit approval until you create `approve-1`, then the command until `approve-2` | pending banner, Not yet verified |

```fish
set -x H (mktemp -d)
cd ~/Projects/Nexus/native
env NEXUS_A61_HOLD_DIR=$H cargo test --offline -p nexus-broker --test code_a56 -- --ignored a61_gui_fixture_hold --nocapture &
# wait for "FIXTURE READY" (the four scenarios take ~30 s), then in another terminal:
cd ~/Projects/Nexus/apps/nexus-desktop; env NEXUS_BROKER_SOCKET=(cat $H/socket) npm run tauri -- dev
touch $H/approve-1     # approves the pending edit -> the command proposal appears
touch $H/approve-2     # approves the command -> completes
touch $H/release       # shuts the fixture down
```

Everything here is a **fixture** (endpoint badge "Loopback fixture"). Approvals are granted only by files you create; there is no automatic approval in the fixture, the broker, the daemon or the Desktop.
