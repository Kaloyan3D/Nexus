Verified facts about the current code (check them yourself in the files, then act on them):
A. Coding runs (inspect.rs) issue only the DEFAULT target. A submit naming another model fails there with "the Registry target differs from the requested provider/model". R-NATIVE-1's selection therefore reaches only the model-only path. Coding runs are the main product path.
B. `thread-send` / `ThreadSend` carries no model; a conversation is not bound to any target.
C. Context and output limits are global constants (context::COMPACT_BYTES = 1_200_000, SUMMARY_AT_*, DEFAULT_MAX_OUTPUT_TOKENS, `turn_cap`), not the resolved target's contextLimitTokens / outputLimitTokens, which the sealed extension already carries.
D. `catalogIssuability` in native-target-v2.cjs partly re-states the issuance rules; nothing proves the catalog's `issuable` equals what `issue` really accepts.
E. The selection is resolved from (providerId, remoteModelId); a route identity is more precise.

Goal: one resolved Registry target per run, bound for the whole run, used by coding runs as well as model-only runs, remembered by the conversation, with limits taken from the target.

1. Shared resolution. One function in the broker resolves "which target does this run use" (explicit selection, else the conversation's target, else the default) into a ResolvedTarget: providerId, logicalModelId, remoteModelId, routeId, connectionId, contextLimitTokens, outputLimitTokens, billingTier. pipeline.rs and inspect.rs both use it, and both pass the selection to `issue`. Resolution happens once, before the run exists; a non-issuable or unknown target is refused before any run (same error codes as today, with the catalog reason). No silent fallback to the default model, ever.
2. Optional route identity. `ModelSelection` gets optional `logicalModelId` and `routeId` (serde default, skipped when absent; existing clients unchanged). When given they must match a catalog entry exactly; when only (providerId, remoteModelId) is given and more than one issuable route matches, refuse with `ambiguous-target` listing the routeIds (no guessing).
3. Run binding. IntentRun records the resolved identity (optional fields: routeId, logicalModelId, connectionId, contextLimitTokens, outputLimitTokens; no credential reference, no path). Every turn of a coding run uses the same issued target; `ExpectedTarget` is checked against it each turn; a run never changes target mid-run.
4. Conversation binding. `thread-send` accepts the optional selection; the conversation stores the target identity only. A follow-up without a selection uses the conversation's target. A follow-up with a different selection is allowed, recorded as a system note ("model changed to ..."), and shown in the thread record. If the conversation's target is no longer issuable, the follow-up is refused before a run exists with the catalog reason (no fallback). The deterministic context block is model-agnostic and must stay byte-identical for the same history (add a test).
5. Limits from the target. The context budget for compaction and working-memory is min(configured budget, a documented bytes-per-token fraction of the target's contextLimitTokens); the per-turn output cap never exceeds the target's outputLimitTokens. For the default OpenCode Go target (very large window) the resulting numbers must equal today's constants (golden test), so default behaviour does not change.
6. Credentials by connection. Each target uses only its own connection's credential reference. Prove it with two fixture connections: the scripted provider records the Authorization header and the test shows target B's request carries B's credential and never A's. Credential values and references must not appear in run records, thread files, logs or `intent-models` output. Do not change credential storage or the Kernel seal / sealed-extension formats.
7. Catalog parity. Add a test (JS fixture registry and, read-only, the real registry shape if available) proving that for every catalog target, `issuable` is true exactly when `issue` with that selection succeeds, and that the reason matches the refusal code. If the test finds a mismatch, fix the catalog by reusing the issuance rule, not by adding a second copy.
8. CLI for acceptance without UI: `nexus intent thread send ... --model <providerId>/<remoteModelId>` (optionally `--route <routeId>`) and `nexus intent models --targets`. No Desktop/Tauri/React change (that is checkpoint 3).
