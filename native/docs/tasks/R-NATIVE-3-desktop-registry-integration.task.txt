Checkpoints 1 and 2 are done and committed: the Registry catalog and selection (R-NATIVE-1), and one resolved target per run and per conversation with limits and credentials taken from the target (R-NATIVE-2). Verified facts about the current code (check them yourself, then act on them):
A. The Tauri command `intent_models` returns only `AllowedModel` (the one default); the catalog (`RegistryTarget`) is not reachable from the renderer.
B. The Tauri command `thread_send` sends no model/route (it passes `model: None, route: None`); `intent_submit` sends provider+remote only. The Desktop therefore always runs the default target.
C. `thread-get` / `thread-list` do not expose the conversation's bound target, so the UI cannot show which model a conversation is on.
D. The renderer must never send a path, tool, limit, credential or approval; every Tauri command is in a fixed allowlist (build.rs, permissions/, capabilities/, and a test that lists the commands). A new command or a new field must go through all of those.
E. The broker caches the catalog for 30 s: right after a Registry change a send can be accepted and then fail closed at issuance ("failed before submission") instead of being refused up front. The UI must word this honestly.

Goal: the user can see every Registry target with its status, pick one for a new conversation or for the next message of a conversation, and always see which target each conversation and each run used.

1. Broker (small, read-only): `thread-get` and `thread-list` expose the conversation's bound target as identities only (providerId, remoteModelId, logicalModelId, routeId); no connection reference, no limits beyond the two numbers, no credential material, no path. Optional field; absent for conversations without one. Backward compatible.
2. Tauri: a new read-only command `intent_targets` returning the catalog (RegistryTarget list) through the existing client call; `thread_send` and `intent_submit` accept an optional selection as `{providerId, remoteModelId, logicalModelId?, routeId?}` (identities only) and pass it on; validation of shape/length on the Rust side; nothing else crosses. Register the command everywhere the allowlist requires (generate_handler, build.rs, permissions, capabilities, the authority test) and extend the authority tests so a renderer cannot supply anything but identities.
3. Renderer: a model picker in the composer. It lists issuable targets as choices and non-issuable ones as disabled entries that show the catalog reason in plain words (map the machine reasons: connection-not-connected, route-not-verified, protocol-unsupported, no-billing-tier, no-credential-ref, model-disabled, context-unknown, ...; unknown reasons shown verbatim). Default = "Use the default (as configured)" which sends NO selection (default behaviour must stay byte-for-byte the same request as today). For an existing conversation the picker shows the conversation's target and choosing another one is an explicit switch with a one-line confirmation text ("This conversation will continue on ...; Nexus records the change"). Never silently fall back to the default after a refusal.
4. Status, read-only: a "Models" view (or panel) listing every target with provider, model, route, connection status, protocol, context and output limits, billing tier, data use, and issuable/reason. It shows nothing secret (no credential reference, no path) and is clearly read-only (no edit controls).
5. Per run and per conversation: ThreadView / the run block / History show the model and route the run used (from the run record) and the conversation header shows its bound target; a "model changed" system note is displayed as it is stored.
6. Refusals: map the broker's `model-not-available`, `ambiguous-target`, `model-not-allowed` errors to clear messages that include the reason; for the 30 s cache window, if a run ends "failed before submission" with registry-selection-not-issuable, say that the Registry changed and the choice must be made again. No retry loops.
7. Accessibility and layout: keyboard-operable picker, labelled controls, works at the narrow width the app already supports; follow the existing design system (apps/nexus-desktop/DESIGN-SYSTEM.md).
