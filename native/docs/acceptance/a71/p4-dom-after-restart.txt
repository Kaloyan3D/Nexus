F1 — mortgage bypasses the turn check — free out-of-turn money

Severity: High — exploitable rules violation.

Location:

src/game/engine.ts:967 — if (action.type !== "mortgage" && s.activePlayer !== p.id)
src/game/engine.ts:1070-1082 — case "mortgage" has no phase check and no activePlayer check.

Why it is a problem:
Every other GameAction is gated on s.activePlayer === action.player. mortgage is explicitly exempted, presumably so a company blocked in dividend settlement can raise treasury. But the mortgage handler itself never verifies that the caller is the company that currently owes dividends (s.settlement.cursor / payDividends at src/game/engine.ts:670-687), or even that it is that player's turn. The UI in src/App.tsx:1579-1590 only renders the button for the active player, but the engine is documented as the authoritative, server-ready boundary (ARCHITECTURE.md:2-4), so a direct applyAction({type:"mortgage",player:<not-active>,count:1}) succeeds on any phase and grants floor(stockValue/2) GP. This breaks atomic turn ownership and the mortgage economy.

Fix:
Remove the blanket exemption. Require either action.player === s.activePlayer, or, during dividend settlement, action.player === s.initiative[s.settlement.cursor]. Add an engine test for out-of-turn mortgage rejection.

F2 — Dividend insolvency soft-locks the game

Severity: High — playable game can become unfinishable.

Location:

src/game/engine.ts:624-669 (closePeriod), 670-714 (payDividends), especially 680-687.

Why it is a problem:
If company.cash < total dividends owed, the engine sets activePlayer = id, logs that the rulebook "gives no insolvency procedure", and returns, expecting the player to sellShares/mortgage then re-issue endPeriod. If the company holds no sellable shares (period 5 also freezes sales per 1053), has no mortgage capacity, and has no treasury path, every subsequent endPeriod fails the p.cash < due guard at 635-638 forever. There is no fallback (bank pays, forced sale, elimination). This matches the honest log message but violates ARCHITECTURE.md:5 ("rejected actions preserve the previous state" is fine, but there is no forward progress).

Fix:
Decide and document one rule: e.g. bank covers the shortfall and records it, or presidency is forcibly mortgaged/sold, or shares auto-sell at current value. Add a regression test that drives a broke company through closePeriod.

F3 — Undo-safety logic lives in two places and disagrees

Severity: Medium — privacy/undo invariant is fragile.

Location:

src/game/engine.ts:1183-1184 — canUndo() = !lastActionRevealed && phase !== "finished".
src/store.ts:40-41 — safe = !reveals && rng unchanged && phase unchanged && !["influence","navigation"].includes(current.phase); stored previous/canUndo.

Why it is a problem:
The engine exposes canUndo, but the store does not use it; it re-implements a stricter heuristic. The engine version would permit undo after a phase transition as long as lastActionRevealed is false, while the store correctly blocks undo across phase/RNG changes. Having two definitions invites a future caller to use the permissive one and roll back dice rolls or phase advances. The store check also keys off current.phase (pre-action phase) for the influence/navigation exclusion rather than the resulting phase, which is subtle.

Fix:
Delete one definition. Make the store call engine.canUndo(result.state) plus explicit RNG/phase-equality guards, or move the full safe predicate into the engine and unit-test it (undo blocked after chooseMarket, navigation, dice rolls; allowed after a plain agent placement).

F4 — Neutral-company dock swap in loadShip can break the dock invariant

Severity: Medium — latent invariant violation / dupe-dock risk.

Location:

src/game/engine.ts:774-784 (neutral branch of loadShip), vs. invariant src/game/engine.ts:1250-1253 (fleet size and unique docks).

Why it is a problem:
On a neutral load the ship is returned to "port" and then assigned a dock "free among port ships" (775-780), then swaps with other if one shares that dock (781-783). firstFreeDock (178-182) considers the whole fleet regardless of location, while the neutral search only considers location === "port", so a sea/Indies ship holding that dock is invisible to the search and other (which searches the whole fleet by dock) can then create a duplicate dock, or other.dock = ship.dock can orphan/duplicate. Full-game sims pass, but the code path is only exercised for the 2-player neutral company.

Fix:
Recompute firstFreeDock-style occupancy over the whole fleet (excluding the moving ship) and assign directly without the swap, then assert uniqueness. Add a 2-player test that forces a neutral load while another neutral ship is at sea/in the Indies.

F5 — Final tiebreak uses unfiltered initiative containing the neutral company

Severity: Low-Medium — wrong winner possible on exact ties in 2-player games.

Location:

src/game/engine.ts:109-124 (getScores), tiebreak line 123: s.initiative.indexOf(a) - ....

Why it is a problem:
getScores filters out neutral players (line 111), but the last tiebreaker indexes into the full s.initiative, which in 2-player games contains the neutral id (src/game/engine.ts:350). The neutral's position shifts the relative order of real players versus a "humans-only initiative order" the rules imply. Cash and own-stock tiebreaks run first, so this only bites on full ties, but it decides the winner.

Fix:
Build a filtered order = s.initiative.filter(id => !s.players[id].neutral) and tiebreak on order.indexOf(...). Add a 2-player tie test with the neutral interleaved.

F8 — Seed 0 collides with seed 1; starting-cash table silently depends on shuffle order

Severity: Low — reproducibility wart.

Location: src/game/engine.ts:276 ((options.seed ?? Date.now()) >>> 0 || 1), 346-355.

Why it is a problem:
0 >>> 0 || 1 maps an explicit seed 0 to 1, so two distinct user-supplied seeds produce identical games, contradicting the "seeded RNG, reproducible games" claim (RULES_COVERAGE.md:16). Separately, starting cash [10,10,11,12]/[10,11,12]/[10,11] is dealt by shuffled-initiative position (351-354), which is correct per the cited rule but means the same named player gets different cash across seeds — worth documenting in the setup UI, not just code.

Fix:
Only coerce NaN/negative to a default; preserve 0 as a valid >>>0 seed (xorshift handles 0 poorly — if 0 RNG state is unacceptable, reject 0 with a clear error instead of aliasing it). Document the initiative-based cash deal.

F9 — getScores presidency math and share-ledger edge cases are untested at the boundary

Severity: Low — likely correct, but one boundary is implicit.

Location: src/game/engine.ts:113-115 ((2 - p.presidencyMortgaged) * value), 1052-1068 (sellShares), 1079 (mortgage payout floor(value/2)).

Why it is a problem:
Wealth counts 2 - mortgaged presidency shares at full value while mortgage pays only floor(value/2) and redeem costs full value (1086). Add the mortgage/redeem wealth round-trip test and an invariant p.shares[p.id] + (2 - p.presidencyMortgaged) <= 2 (or whatever the physical limit is).

F2 — Dividend insolvency soft-locks the game: real bug, not intentional design.

Implementation trace (all lines actually read)

Settlement lives in src/game/engine.ts:

closePeriod(s) :624-669 — first call does earnings/growth, moves p.sales into p.cash (661), creates s.settlement={cursor:0} (667), calls payDividends(s) (668).
payDividends(s) :670-715 — iterates s.initiative from s.settlement.cursor (672). Per company id it computes total = Σ p.shares[id]*dividend over non-neutral holders only (676-677), matching the rulebook rule that neutral-company dividends come from the bank (692, 688 skipped for neutral). If a human company is short (680):
tss.activePlayer = id; // 681
note(s, `... needs ${total} GP ... has ${company.cash}. Raise treasury on this turn; the rulebook gives no insolvency procedure.`); // 682-684
return; // 686 — settlement stays open, cursor parked on debtor
Retry path closePeriod :625-641 — if s.settlement exists, recompute only the activePlayer's bill (626-634); if p.cash < due, fail("Need ... Sell shares when permitted or use enabled presidency mortgages.") (635-638); otherwise payDividends(s) resumes the loop (639).

The only treasury-raising moves available while parked in phase="end" with activePlayer=debtor (post-F1 turn check at :967):

sellShares :1051-1068 — allowed in end except s.period===5 && s.phase!=="agents" (1052), i.e. forbidden for the whole of period 5's settlement. Pays price*count at current (pre-drop) getStockValue (1061-1062), then -count stock spaces (1065).
mortgage :1069-1081 — pays count*floor(value/2) (1078), max 2 total (1075). Requires s.options.mortgage, which createGame :283 defaults to false. So in default games this hatch does not even exist.
Re-issuing endPeriod :1157-1162 → closePeriod(s).

Every other action type fails a phase/queue guard (placeAgent, buyShare, navigate, load, unload, etc.), and applyAction returns the unchanged input state on failure (1173-1179).

Why this is a soft-lock

If company.cash < total and the debtor has no sellable p.shares[*]>0, mortgage is disabled/exhausted, or it is period 5 (sales banned), then:

payDividends parks activePlayer=debtor, settlement.cursor on debtor, phase="end".
sellShares/mortgage are either illegal or insufficient.
Every endPeriod re-hits the p.cash < due guard at :635 and is rejected with state preserved.
payDividends never advances cursor, never reaches the delete s.settlement; period++/finished epilogue at :695-714.

The game has no forward move — an unfinishable state. The test helper commercialAction in src/game/engine.test.ts:677-695 tacitly admits this by desperately liquidating any share then mortgaging when due > cash; when both are unavailable it just falls through to autoAction (i.e. endPeriod) which will fail.

Bug vs. intentional?

Real bug (missing-rule fallback), honestly labeled. The log string at :684 ("the rulebook gives no insolvency procedure") is accurate: the authoritative rulebook (reference/rulebook.txt:440-445) says sales move to treasury, then "each player pays dividends... Players must pay this amount to each player, for each Share" with amount dividend × shares, and specifies no shortfall procedure. RULES_COVERAGE.md:86 likewise documents only "treasury-blocked settlement" with no fallback. So the engine faithfully implements the printed rules — but faithfulness here preserves a hole: the physical game would require a table ruling, while the digital game must total-functionally advance.

Reachability is not theoretical: dividends run 0–4/share (src/game/data.ts:42-45), up to 6 shares/company outstanding, so a high-track company can owe up to ~24 GP against treasuries seeded at 10–12 (engine.ts:351-354) plus one period's sales. One bad sales period with heavy outside ownership triggers it.

Fix (not applied per read-only request): choose and document one rule — e.g. bank covers shortfall, partial pro-rata payment, forced auto-sale/mortgage, or debt carried forward — plus a regression test driving a broke debtor (0 cash, no shares, mortgage disabled, period 5) through closePeriod.
