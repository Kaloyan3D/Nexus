# A6.1.3 — Project operations: registry, working-copy lifecycle, limits

Status: implemented and tested **offline**. No provider request was made. Nothing is committed.

## 1. Architecture and exact trust boundaries

```
 operator (OS user that owns the registry dir)
   │  nexus project add|list|show|remove|repin|set-scope        (writes projects.json, atomic)
   │  nexus-broker worktree list|patch|remove                    (needs issuer cap + broker state dir)
   ▼
 <registry dir 0700>/projects.json ──read-only──► nexusd  (authoritative: id → canonical path, pin, write scope)
                                      └─read-only─► nexus-broker (listing, early refusal, passes the id)
                                                         ▲
 Desktop (Tauri backend) ─ broker client verbs only ─────┘   cannot write the registry, cannot name a path
```

| Actor | May | May not |
|---|---|---|
| Registry owner (operator) | create/change/remove projects; re-pin; list/patch/remove inactive copies | approve anything (the approver is separate) |
| `nexusd` | read the registry; make a copy of a *registered* project at its pin; enforce the frozen write scope itself; refuse removal of a leased copy | accept a caller-supplied source path when registry-managed |
| `nexus-broker` | read the registry per listing/run; clamp limits by operator caps; show read-only facts | write the registry; pick a path; raise a limit |
| Desktop / renderer | list project identities (pin + scope, no path); submit by id; read diff/copy facts (ownership-checked); **Copy patch** on explicit click | register, re-pin, remove, delete a copy, approve, send a path |

**Authority to register = the ability to write the registry directory.** `registry::mutate` additionally requires `euid ==` directory owner. Readers (daemon, broker) refuse a registry whose directory or file is: not owned by a trusted uid (`--project-registry-owner-uid`, default: the reader's own euid), group/world-writable, a symlink, hard-linked, larger than 1 MiB, or malformed (strict schema, `deny_unknown_fields`, id/commit/path/scope validation, unique ids). A missing *directory* is an error; a missing file in a trusted directory is an empty registry. Start-up of both processes fails closed on an untrusted registry; at runtime an unreadable registry yields **no** projects and refuses new runs.

**The registry is not signed.** A signing key held by the same OS identity that writes the file would add no independence on a same-UID development instance, so none is claimed. The security of the registry is filesystem ownership and mode. In a multi-UID deployment the registry owner is a distinct operator uid and the daemon/broker run as other uids that can read (set directory ≤ 0750, file ≤ 0640 and share a group) but not write it. **Proven under real, distinct kernel identities** (`multuid_a613_project_registry_owned_by_a_third_identity_is_read_only_for_everyone_else`, userns suite): see §1a.

**Independent validation by the daemon** (`worktree-create`): with a registry configured the request must carry `projectId`; `sourceRoot` is refused (even a valid one). The daemon resolves the id, requires the recorded canonical path to still canonicalize to itself (symlink substitution → `source-moved`), refuses a source overlapping the working-copy root, takes the pin from the registry (a differing `expectedCommit` from the caller is refused), creates the copy, and refuses and removes it if the source is not at the pin. The write scope is **frozen into the copy's identity record** at creation and enforced by the daemon on `approval-request` and `tool-execute` for mutating tools (`path-not-in-scope`), in addition to the broker's earlier refusal.

**Updates without restart; never silent for a started task.** The registry is re-read for every listing and every new run (atomic rename, so no torn read). A run resolves its project once at its start; the daemon freezes pin and scope into the copy record. Removing, re-pinning or re-scoping a project therefore affects **new** runs only: a started run keeps its identity, pin, scope and copy, and its diff stays retrievable. (`a613_registry_changes_reach_new_runs_but_never_change_a_run_that_has_started`.)

**Compatibility.** `--code-source/--code-commit/--code-write-allow` (and `A56_CODE_SOURCE` in the dev script) still work when no registry is configured. A broker with `--project-registry` and `--code-source` refuses to start. `--project-registry` is forbidden by the production-v1 profile like the other pilot flags.

**Residual risks (documented, not hidden).** Same-UID dev: anyone running as that uid can edit the registry and the approver credential. Short window between the daemon's path check and `git` canonicalisation in `gitwt::create` (the pin comparison afterwards still decides). A project's own `build.rs`/test code runs inside the sandbox (network off, read-only source snapshot) and is outside the model write scope; the scope limits model-proposed file writes, not what the project's tests do inside the isolated copy.

**Data-disclosure scope (fixed text, shown by `nexus project show`):** task text, the model's tool calls and every tool result (listings, files the model chooses to read, search hits, bounded command output) go to the model provider; reads cannot be path-scoped, so any non-secret-shaped file at the pinned commit can be read and sent; only writes are scoped.

### 1a. Multi-UID deployment of the registry (tested)

| Identity | Relationship | Needed |
|---|---|---|
| operator (`nexus-operator-test`, third identity) | owns the registry dir and file; the only identity that can change it | directory `0750` owner=operator, group=`registry` group; the CLI keeps the file `0640` in that group when the directory is group-readable, never group-writable |
| daemon, broker (`nexusd-test`, `nexus-issuer-test`) | **readers only**: members of the registry group; started with `--project-registry DIR --project-registry-owner-uid <operator uid>` | no write permission anywhere in the directory |
| Desktop clients, bystander, untrusted, approver | no access at all (not in the group) | — |

The source repository must be readable by the operator and owned by the identity that runs git for the daemon (git's ownership protection stops the operator running git on a daemon-owned repository), so register it with `nexus project add ID PATH --commit <sha40> --defer-verify`: the operator states the pin, only path and `.git` existence are checked by the CLI, and **the daemon verifies cleanliness and the pin on every task** (a wrong pin or a dirty source is refused and nothing is handed out). `repin --defer-verify` works the same way. Per-project client visibility: `--allow-uid U,U` at `add`, or `nexus project set-clients ID (--allow-uid U,U | --all)`; empty = every uid the broker allows (enforced by the broker, like the older `--code-allow`).

What the userns test asserts (all passing): ownership/mode of the directory and file as deployed; daemon and broker can read, nobody else can; **no other identity can change the registry** — each of daemon, broker, both Desktop uids, bystander, untrusted and approver was tried with every CLI mutation (add of a spoofed path, remove, re-pin, scope, clients, also claiming the operator as trusted owner) and with raw `echo >>`, `rm`, `mv`, `cp`, `ln -sf`, `touch` and `rm -rf` — all fail and the file bytes and mode are unchanged; client visibility by uid; spoofed ids (`PROJ`, `proj/../proj`, an unknown id, a filesystem path) refused; an **active** run keeps its project, pin, scope and copy while the operator changes scope/clients and removes the project, the other client cannot see, cancel, diff or inspect the run, and no identity except the daemon can touch the copy; a registry file owned by an untrusted uid or group-writable makes both the daemon (checked directly with the issuer credential) and the broker refuse until it is restored; the original repository is byte-identical afterwards. Ownership checks were not relaxed to make this pass.

## 2. Operator commands (CLI)

Registry directory: `--registry DIR`, else `NEXUS_PROJECT_REGISTRY`, else `~/.nexus/projects` (created 0700). Add `--json` for machine output.

```fish
set -x NEXUS_PROJECT_REGISTRY $HOME/.nexus-a54/projects
nexus project add shop ~/work/shop --write-allow src/,tests/   # clean tree required; pinned to its current HEAD
nexus project add shop2 ~/work/shop2 --commit <sha40>          # --commit must equal the source's HEAD
nexus project add shop3 /srv/shop3 --commit <sha40> --defer-verify   # multi-UID: the daemon verifies the pin on every task
nexus project list
nexus project show shop                                        # path, pin, scope, restrictions, disclosure
nexus project set-scope shop --write-allow src/                # or --all for the whole project
nexus project set-clients shop --allow-uid 1000               # or --all; empty = every uid the broker allows
nexus project repin shop --to <sha40>                          # source must already be clean at that commit
nexus project remove shop --yes                                # new tasks only; copies and history untouched
```

Working copies (operator only; needs the issuer capability, so it is a `nexus-broker` subcommand):

```fish
set -l S --state-dir $A54_HOME/broker --daemon-socket $A54_HOME/daemon/n.sock --cap $A54_HOME/daemon/issuer.cap
nexus-broker worktree list $S                       # id, active|inactive|orphan, project, base commit, KiB, age, run
nexus-broker worktree patch <run-id|copy-id> $S --out ~/fix.patch   # exclusive create, 0600; refuses a truncated diff unless --allow-truncated
nexus-broker worktree remove <run-id|copy-id> $S --yes             # inactive copies only; writes <state>/worktree-ops.jsonl first
```

Multi-project dev instance: `A613_PROJECT_REGISTRY=$A54_HOME/projects sh native/deploy/a54-dev-instance.sh start` (optional `A613_CAP_TURNS|TOOL_CALLS|EDITS|COMMANDS|MINUTES`, `A613_APPROVAL_TTL_SECS`).

## 3. Working-copy lifecycle

* A copy belongs to one run and one project: the daemon records `taskInstanceId`, `projectId`, base commit, creation time and frozen write scope in `<worktree-root>/.meta/<id>.json` (outside the copy).
* **Active/leased** = the run record is non-terminal (broker), **or** the daemon sees a pending/approved approval or an unfinished tool execution for the task. Active copies are never removed: the operator tool refuses, and the daemon refuses a direct `worktree-remove` as well (`a613_an_active_or_leased_copy_is_never_removed…`).
* Only ids that pass `valid_task_id` are targets (never paths); the daemon lists only real directories directly under the managed root (a planted symlink is ignored and, if named, refused); the original repository is never a target. **Orphans** (no run record) need `--orphan` and an age ≥ 10 min.
* Destructive cleanup is an explicit operator action (`--yes`). Audit evidence is independent of the copy: run records, Kernel journals, transcripts and the operator log `worktree-ops.jsonl` (run id, project, base commit, diff digest, bytes, uid) are outside it. After removal the verified outcome and receipts remain; only the diff is no longer retrievable (the Desktop says so).
* The Desktop shows read-only facts (`intent-copy`: retained, in use, base commit, age, approximate size, no path) and **Copy patch** (explicit click, existing ownership-checked diff, disabled for a truncated diff). It cannot remove a copy. Nothing ever commits, merges, pushes or applies the patch.

## 4. Limits and approval lifetime

Operator caps can only **lower** the fixed maximums (12 turns · 30 tool calls · 5 edits · 5 commands · 30 min); a cap above a maximum or 0 makes the broker refuse to start. They are applied by the broker to every run, whatever the client sent, and reported by `intent-code-config` so the composer shows the real numbers and the approval lifetime (shorten-only, default 5 min). Session authorization and exact prompt-byte matching are untouched (the record only has to allow at least what the run uses).

## 5. Language and build-runner support (unchanged by A6.1.3 — the process allowlist was NOT expanded)

| Ecosystem | Works today | Needs / does not work |
|---|---|---|
| Rust | `cargo check/test/build/fmt` offline in the sandbox | dependencies need an operator-admitted offline cache (`--dep-cache`); crates with network build scripts fail by design |
| TypeScript / JavaScript | `npm test`, `npm run build`, `tsc --noEmit` | offline `node_modules` must already exist in the committed tree (not installed by Nexus); no `npx`, `yarn`, `pnpm`, `vitest`/`jest` CLIs directly |
| Python, Go, .NET, Java, C/C++ (make, cmake), others | **not supported** | each needs a dedicated security review (toolchain discovery, offline dependency story, sandbox profile) before implementation |
