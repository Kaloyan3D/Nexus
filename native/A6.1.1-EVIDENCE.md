# A6.1.1 — Outcome integrity: evidence

Base `c85c1cf`. **Uncommitted.** No provider requests (OpenCode Go or otherwise). Scope: the Desktop showed a *completed* coding run whose model claimed success although its edit and test had not run. Nothing in the Kernel, broker trust boundary, approvals, expiry, sealed grants, write scopes or session limits was weakened.

## 1. Root cause (from evidence, not assumption)

The observed run (fixture `a61_gui_fixture_hold`, scripted model, loopback provider): `fs_read` executed; `fs_edit` and `proc_run` ended `approval-expired`; final text "Fixed add (a - b -> a + b); cargo test passes."; lifecycle `Completed`.

| Question | Finding | Evidence |

| Why did both approvals expire? | An approval request lives 300 s (`APPROVAL_TTL_MS`) and then the daemon marks it `expired`. The old fixture approved an operation **only** when the operator created `approve-1` / `approve-2` in the hold directory; absent the file the only possible outcome is expiry. So the run either waited past 5 min per operation or the files were not created in time — by design the fixture never auto-approves. I cannot see what the operator did; the mechanism is certain. | reproduced deterministically with a 2 s lifetime: both approvals `expired`, both activities `refused · approval-expired` (`a611_expired_denied_and_lying_runs…`) |

## 2. What changed

**Backend (derived data only; no state-machine change).** `nexus_client::intent_client::derive_coding_outcome(&IntentRun) -> Option<CodingOutcome>`, returning, for `repo-code` runs only: `verification` (`verified-passed | verified-failed | blocked-by-approval | no-test-executed | not-yet-verified | uncertain`), `change` (`none-proposed | pending-approval | applied | partially-applied | not-applied | uncertain`), counts (edits applied / not applied, commands executed / not executed, blocked by approval), `lastExitCode`, `staleAfterEdit`, `uncertainOperations`. Rules (all from receipts): an edit counts as applied only if it **executed and returned a post-image hash**; a command counts only if it executed **and recorded a verdict**; an executed operation lacking its receipt is *uncertain*, never a pass; `uncertain` activity or run state wins over everything; a passing test that ran **before the last applied edit** is `not-yet-verified`; a blocked command with no executed test is `blocked-by-approval`; a terminal run with no executed test is `no-test-executed`; a live run is `not-yet-verified`. The broker attaches the result in the single `view()` funnel **on read**, so historical records get it too and nothing in storage was rewritten. A successful exit is reported as command evidence ("verifies the command, not that every requirement is met"); it never certifies the whole task. CLI: `intent status/result` lines show it; NDJSON carries `codingOutcome`.

**Lifecycle is untouched** (`completed` still means the model finished). Desktop badges now say "Model completed" for a coding run and show the verified outcome beside it ("Tests passed · exit 0", "Blocked · approval expired · not executed", "Coding outcome uncertain", "Outcome not reported", …).

**Classification.** Recent Tasks groups by the broker's intent type (Code in copy / Inspect / Ask) with `CODE / INSPECT / ASK` badges and a separate `FIXTURE` badge for non-provider origins; the breadcrumb/heading says "Coding run" etc.; the activity table labels every tool `read / write / command`; the proposal counters are renamed "Edit proposals / Command proposals" with a tooltip; a **Verified outcome** panel states that the model's final message is a claim and is never used. The status line is now mode-accurate (`Model proposed N tool call(s); every edit and command still needs an independent approval; validating.`); old transcripts keep their stored text — only the display of a *coding* run's old line is normalised, with the original in the tooltip.

**Fixtures.** `a61_gui_fixture_hold` is now scenario-driven (approved, expired, denied, liar, pending) with an honest reactive model for everything except the deliberate `liar`; expiry uses a new operator-shortenable approval lifetime (`--approval-ttl-secs 1..300` / `BrokerConfig.approval_ttl_ms`, can only *shorten* the 300 s default). Approvals in the fixture are granted only by files the operator creates; no bypass exists in the broker, daemon or Desktop.
