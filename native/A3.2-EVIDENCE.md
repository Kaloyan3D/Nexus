# A3.2 Evidence — Trusted Tool Integration

Branch `feature/rust-native-core`, baseline `c2ca6c4` (A3.1). **Not committed.**

A3.2 makes the A3.1 read-only tools executable through the authenticated
native daemon boundary, resolves the A3.1 residuals, and exposes real tool
records to the Client API, CLI and GUI.

> **Execution mode, stated plainly.** Everything here is **trusted
> operator/test execution**: a Controller-side issuer (holding the daemon's
> ephemeral capability) asks the daemon to run `fs.list`/`fs.read`/
> `fs.search`. **No model, provider or AI-initiated call path exists.** Every
> record carries `aiInitiated: false`, `Kernel::dispatch_enabled()` is still
> `false`, and there are no write, shell or process-execution tools.

---

## 1. Actual authority chain

```
Controller/issuer (cap holder, UID-gated)        operator config
   │ accept (existing)  ─► Kernel receipt (task, attempt, lease, issuance seal)
   │ workspace-bind     ─► Kernel::bind_workspace
   │                        ├ needs accepted receipt, current lease, witness health
   │                        ├ root canonicalized, must be beneath --workspace-bases
   │                        ├ Kernel itself stats the root → (dev, ino)  [never caller-supplied]
   │                        └ HMAC-sealed workspace_bindings row (immutable per command)
   │ tool-execute       ─► daemon: resolve sealed binding (seal re-verified)
   │                        ─► prepare (root only from binding; identity re-checked)
   │                        ─► Kernel::authorize_tool (binding+lease+witness+fence; sealed grant)
   │                        ─► Kernel::begin_tool_execution (seal, args/budget digests,
   │                                                         consistency gate, journal `started`)
   │                        ─► run (descriptor-relative; probe every ≤20 ms)  [no Kernel lock held]
   │                        ─► Kernel::complete_tool_execution (journal `completed`, redacted)
   │ tool-revoke        ─► Kernel::revoke_tools (durable)
reader (peer-UID gated) ─► tool-events (read-only, scoped, paged)
```

No second Controller authority was created: acceptance, leases, witness and
the issuance seal key are the existing Kernel mechanisms; the daemon only
adds three privileged commands to the **existing** issuer-authenticated set.

## 2. Controller workspace-binding guarantees

* The IPC request has **no** root/path field: `workspaceRoot`, `root`, or any
  unknown parameter is rejected (`bad-request`) before authority is looked up.
* A binding exists only if the Controller published it (`workspace-bind`,
  privileged, HMAC-authenticated, replay-protected) for an **accepted
  command in its current lease generation**, **and the Controller intent
  payload sealed at acceptance commits to that exact root**
  (`workspaceRootDigest = sha256(canonical root)`). See §14 for what this
  does and does not establish.
* The root must be beneath an operator-configured `--workspace-bases` entry
  (necessary, **not** sufficient); with none configured nothing can be bound
  (fail closed). `/`, `/proc`,
  relative paths and out-of-base roots are refused.
* `(dev, ino)` and path digest are captured **by the Kernel**, sealed with the
  issuance key, and immutable: a second, different binding for the command is
  `command-conflict`; an edited row fails the seal (`forged-issuer`).
* At execution the root is re-opened and its identity compared with the
  sealed binding; a replaced directory is `workspace-mismatch` with zero reads.
* The bind response never echoes the root path.
* Every grant binds: task, attempt, lease epoch + incarnation, tool id/version,
  args digest, budget digest, workspace digest/dev/ino, cancellation id.

## 3. IPC authentication model

| Command | Class | Gate |
|---|---|---|
| `workspace-bind`, `tool-execute`, `tool-revoke` | privileged | existing issuer capability HMAC (nonce, ts, single-use) + optional `--allowed-uids` SO_PEERCRED gate; `privileged-disabled` in default `readonly` mode |
| `tool-events` | read-only | when `--allowed-uids` is set the peer UID must be listed; scoped to an existing (task, attempt) |

Socket permissions, directory policy and the daemon lock are untouched. No
HTTP endpoint exists. The honest A1.3.3 same-UID limitation still applies
(a hostile same-UID process that can read the capability file can act as
issuer); A3.2 does not claim to fix it.

## 4. Kernel grant and fencing checks

At `authorize` and `begin` (and again at every probe): accepted receipt;
task/attempt match; **current lease epoch + incarnation**; witness present and
not rolled back / not lost; **tool revocation**; **intent fence**;
sealed binding match; journal/witness consistency. At `begin` additionally:
HMAC seal, expiry (120 s), args digest, budget digest, exactly-once start
(`UNIQUE(request, phase)`), and refusal if the request was already
`expired`/`interrupted`.

### Mid-execution fencing (Phase 4)

`ExecCtx::check_cancel` (called per directory, per file, every 512 lines)
runs the **Kernel fence probe** at most every 20 ms in addition to the
caller token. The daemon holds **no** Kernel lock across a scan; the probe
takes it briefly. Verified:

* revocation during a 18k-file recursive search → `revoked`, scan stops
  early, journaled `completed/errorCode=revoked` (status `cancelled`);
* lease supersession (`acquire`) during search → `revoked`;
* revocation persists across daemon restart (durable table);
* library test proves **no file is read** once revoked before the first probe;
* mutation check: disabling the probe fails both the library and daemon tests.

Limit: probe latency is bounded by the 20 ms interval plus one file read.

## 5. Tool execution and recovery semantics

Journal phases per request: `authorized → started → completed`, plus
terminal `expired` and `interrupted` written only by reconciliation.

| State | Meaning | Re-executable? |
|---|---|---|
| authorized (no started) | grant minted, not begun | until expiry |
| expired | grant lapsed unexecuted (reconcile) | **no** |
| started | execution began | **no** |
| completed (ok/truncated/error) | outcome recorded | **no** |
| completed + `cancelled`/`revoked` | stopped by token or authority | **no** |
| interrupted | started, no completion (crash/restart); outcome **uncertain** | **no** |

Reconciliation never invents a completion. At daemon startup (single owner,
nothing in flight) open `started` requests become `interrupted` and stale
`authorized` become `expired`. Verified by SIGKILL of nexusd mid-search:
journal reads `authorized, started, interrupted`; the same request id is
refused; a fresh request runs; no `completed` was fabricated.

Exactly-once durability scope: SQLite `UNIQUE(request, phase)` in WAL/FULL
under the cross-process kernel lock — durable and cross-process (A3.1
6-process race still passes). It covers *authorization to read*, not
external side effects (there are none).

## 6. Journal and witness guarantees

Checkpoint = sealed `(count, tail hash)` stored in the witness DB after each
append. `ensure_journal_consistent` runs before every append, on verify, and at
startup reconcile:

| store vs checkpoint | verdict |
|---|---|
| equal count, equal tail | consistent |
| store exactly 1 ahead and entry `c` == checkpoint tail | **recoverable** (crash between append and checkpoint; documented one-entry window preserved) |
| store behind | fail closed — tail truncation |
| store > 1 ahead, diverged, or checkpoint missing/unsealed with n > 1 | fail closed |

The daemon refuses to **start** on inconsistent evidence (tested).
Chain/seal checks still detect edit, insertion, reorder, mid-chain deletion.

Honest limits: the witness is a same-host, same-user SQLite file — an
attacker who can rewrite both files **and** read the issuance key can forge a
consistent pair, and the newest un-checkpointed entry can be dropped
undetected. **No external tamper resistance is claimed.** The closing of the
one-entry window needs an externally anchored or pre-commit checkpoint
(A3.3 prerequisite).

## 7. A3.1 residuals resolved

* **Hard links:** the dependency-directory exemption was **removed**. Any
  regular file with `nlink > 1` is refused (`hardlink-refused`), including
  under `node_modules`, `target`, `vendor` (tested library- and daemon-level).
  Trade-off: legitimately hard-linked package stores are unreadable.
* **Secrets:** detection is explicitly best-effort (see A3.1 §8.3, limits
  unchanged). New: inline marker `[REDACTED:nexus]`; clipped lines end with
  ` [TRUNCATED:nexus]`; a source line that already contains either marker is
  flagged `marker-collision` so markers are never ambiguous; search matches
  redacted text (no prefix/substring oracle — secret text yields 0 matches,
  stats expose no pre-redaction counts); journals no longer store
  `queryDigest` or `argsDigest` (only query length) so a low-entropy secret
  query cannot be brute-forced from the journal; `tool-events` is an
  allow-listed projection (no payload passthrough, no roots, no content).
* **Sensitive paths** are enforced in `open_path` before any open.

## 8. Client API / CLI / GUI

* `nexus_client::tool_events` (typed page), `tool_events_folded` (bounded,
  folds into `ToolEventV1`), duplicate/out-of-order `seq` ignored.
* CLI: `nexus tools events --task --attempt [--after]` (read-only, real
  daemon). `tools list/inspect/run-offline` unchanged; `run-offline` is still
  double-gated, ephemeral and now binds through the same Kernel binding path.
  The CLI has no way to mint grants or execute against a real store.
* GUI: Tauri command `tool_events(taskInstanceId)` (read-only, allowlisted,
  in build manifest + capability), `NativeApi.toolEvents`, and a **Tool
  activity** section in the task Inspector. The renderer supplies only the
  task instance; the backend takes attempt ids from the **Controller attempt
  journal** (`runs/<TASK>/attempts.jsonl`, via `list_attempts`), queries each
  attempt under its own (task, attempt) scope and returns them grouped.
  Attempt ids are never constructed (the earlier `<TASK>-A<n>` heuristic was
  removed). With no run directory / no attempt record the result is
  `available:false` + reason and the UI shows that. An attempt the kernel does
  not know (stale) is shown as "No kernel record for this attempt" and never
  merged. Each event carries its lease generation. React has no fs access; no
  Tauri fs/shell permission was added; no assistant messages are synthesized
  from tool events. No authoritative tool-call ↔ transcript linkage field
  exists, so no such relationship is drawn.

## 12. Remaining limitations

* Same-UID hostile issuer impersonation (A1.3.3) unchanged; multi-UID
  deployment re-proof is **NOT RUN** (no Docker here).
* Same-host witness is not external tamper resistance; one-entry crash window
  remains.
* `tool-events` read gate is UID-allowlist based; without `--allowed-uids`
  any socket-permitted local process can read (non-sensitive, allow-listed)
  records.
* Redaction is best-effort; hard-link refusal breaks hard-linked stores.
* Probe latency ≤ 20 ms + one file read; in-flight reads of a single huge
  file are bounded by the 8 MiB ceiling.
* Daemon runs tools on the connection thread with a 4-way concurrency cap;
  a disconnect does not cancel the run (it completes and is journaled).
* Linux ≥ 5.8 only.
* GUI draws no link to conversation events (no authoritative linkage field).
* Attempt identity depends on `NEXUS_RUNS_DIR`/`--runs-dir` being
  configured; otherwise the UI honestly reports unavailable.

## 13. Prerequisites for A3.3 (write/edit tools)

1. Externally anchored (or pre-commit) journal checkpoint; close the
   one-entry window.
2. Separate write-intent grants (tool ids, pre-image digest, planned/applied/
   verified phases) and atomic temp-file + `renameat` inside the pinned fd.
3. Controller-published per-task write scope (a second sealed binding kind),
   distinct from the read binding.
4. Undo/rollback and conflict detection.
5. Authoritative tool-call ↔ transcript linkage field so GUI can show the
   relationship without inference.
6. Multi-UID Docker re-proof of the new privileged commands.
7. A decision on output redaction policy beyond pattern matching.
8. Only after the above: any AI-initiated call path.

## 14. Final authority audit (A3.2 close-out)

### 14.1 What authoritatively binds a task instance + attempt to a workspace

Precisely, today:

1. **Controller attempt journal** (`runs/<TASK>/attempts.jsonl`) — the
   upstream authoritative record: each `started` attempt row carries
   `taskInstanceId`, `attemptId` and a `workspace`. **The native daemon does
   not read it** (it has no ledger access by design).
2. **Kernel-sealed accepted command** — the Controller intent
   (`ControllerIntentV1`) is digest-verified and stored at `accept`, bound to
   task, attempt, lease and Registry issuance. Its payload is Controller-
   authored but free-form.

Finding (**confirmed defect in the A3.2 draft**): `workspace-bind` required
only an accepted command and a root beneath `--workspace-bases`; the issuer
chose the root. A valid issuer could therefore bind *any* allowed directory.

Fix (smallest reliable check in the current architecture): `bind_workspace`
now requires the **accepted intent payload to commit** to the root
(`workspaceRootDigest`, sha256 of the canonical path). An intent with no
commitment can never be bound; a different allowed directory is
`binding-mismatch`; the binding stays immutable. Tests: library
`issuer_cannot_choose_a_different_allowed_workspace`,
`forged_binding_cannot_be_published_or_rebound`; daemon
`valid_issuer_cannot_bind_a_different_allowed_workspace_or_an_uncommitted_intent`.

**Honest limit:** the commitment is made by the same capability holder that
issues `accept`, so this is *not* separation of authority between two
parties; it makes the workspace a durable, sealed, pre-execution decision
that cannot be re-pointed at bind or run time, and ties it to the accepted
command. Verifying the commitment against the Controller attempt journal's
`workspace` field is **not implemented** (would require giving the daemon
ledger access); the Controller must write the matching digest into the intent
payload. A compromised issuer that controls `accept` still controls the root.

### 14.2 Tool-event identity

Defect: the GUI built `<TASK>-A<n>`. Replaced as described in §8; regression
tests: `task_events_use_authoritative_attempts_and_never_merge_tasks_or_attempts`
(daemon+client; real attempt, stale attempt, different task instance in the
same runs dir, unavailable states) and four vitest cases (per-attempt
separation, explicit unavailable, stale attempt, backend error).

### 14.3 IPC review

| Property | Verified by |
|---|---|
| issuer HMAC required for `workspace-bind`/`tool-execute`/`tool-revoke` | `unauthenticated_and_readonly_tool_execution_is_refused` |
| replay rejected for all three | `replayed_authenticated_frame_is_rejected`, `bind_and_revoke_are_replay_protected_and_tool_events_cannot_mutate` |
| peer-UID gate on all three **and** on `tool-events` | `peer_uid_gate_covers_privileged_tool_ops_and_tool_events` (allowlist = foreign UID; valid cap still `peer-unauthorized`) |
| `tool-events` has no write/execute semantics; unknown params rejected | same test (5 injected privileged-looking parameters → `bad-request`) |
| scope: exact (task, attempt) that exists as an accepted command | cross-task/attempt tests |
| outputs bounded | page cap 200, output ceiling 1 MiB, truncation flagged |
| credential isolation | bind response returns digest only; capability never in any response/log; events are an allow-listed projection |
| GUI cannot escalate | capability lists only read commands; `tool_events` takes a task instance and is read-only; privileged ops are not in the Tauri manifest |
| trust-threatening store state latches | `journal_corruption_while_running_latches_reconciliation` (status `reconciliationRequired: true`) — **defect fixed**: wrapped kernel refusals from tool ops previously did not latch |

Remaining: without `--allowed-uids`, `tool-events` is readable by any peer
the socket mode admits (same as existing `journal`/`receipt`); the A1.3.3
same-UID impersonation limitation is unchanged.

### 14.4 Fencing and recovery re-verification

Re-run and passing: revocation during recursive search, lease supersession
during search, revocation across restart, SIGKILL mid-execution →
`authorized,started,interrupted`, expiry reconciliation, IPC disconnect.
Documented behavior matches observed behavior. Probe latency is
≤ 20 ms + one file read.

### 14.5 Journal checkpoint — what is and is not guaranteed

Guaranteed: edit / insertion / reorder / mid-chain deletion detected by the
sealed hash chain; tail truncation **back past the last checkpoint** is
detected while the witness file is intact; inconsistent evidence fails
closed (including startup). **Not** guaranteed: detection of loss of the
newest un-checkpointed entry (the one-entry window, recovered as
consistent); resistance to an attacker who can rewrite both SQLite files and
read the issuance key; any external anchoring. This is a same-host
integrity aid, not tamper-proof storage.

## 15. Multi-UID (Docker) status — **NOT RUN**

* `docker info` fails on this host (daemon not accessible to this user);
  `podman` absent; the suite also needs root and four dedicated UIDs.
* The host-capability reporter was executed and reports
  `NOT RUN on this host`; the eight `#[ignore]`d tests were **not** executed.
* The new privileged commands `workspace-bind`, `tool-execute`, `tool-revoke`
  (and the UID-gated `tool-events`) are therefore **not independently
  re-proven under multi-UID deployment**. They are covered only by the
  single-UID peer-allowlist test above. **Production deployment readiness is
  not claimed.**

Operator commands (from `native/deploy/MULTUID-PROCEDURE.md`), on a machine
with Docker:

```bash
docker build -f native/deploy/Dockerfile.multuid -t nexus-multuid .
docker run --rm nexus-multuid
```

or on a prepared host with the four users:

```bash
cd native
cargo test -p nexus-daemon --test multuid multuid_host_capability_reporter -- --nocapture
NEXUS_MULTUID=1 cargo test -p nexus-daemon --test multuid -- --ignored --test-threads=1
```

The multi-UID suite itself does not yet exercise the A3.2 commands; extending
it to cover them is an A3.3 prerequisite.

## 16. Prerequisites for A3.3 (updated)

In addition to §13: (a) extend the multi-UID suite to the three privileged
tool commands and run it; (b) cross-check the intent commitment against the
Controller attempt journal `workspace` field (daemon ledger access or a

are exposed beyond a single-user socket.
