# A3.6 — Multi-UID Security Closure

Branch `feature/rust-native-core`, baseline `1106fd5` (A3.5). **Not committed.**
`Kernel::dispatch_enabled() == false`; no live AI; no unsandboxed fallback — unchanged.

## 1. Environment (Phase 1)

| Option | Result |
|---|---|
| Rootful Docker (`Dockerfile.multuid`) | **Blocked**: `docker` CLI present, daemon inactive (`/var/run/docker.sock` absent), no root/sudo (password required), user not in a docker group, no podman, no rootless-docker tooling. Not worked around. |
| Disposable VM | Not available. |
| **Unprivileged user namespace with a subuid range** (used) | `unshare --user --map-users=0:<me>:1 --map-users=1:<subuid>:65535` + private mount namespace. Inner UIDs 20001–20005 are *distinct kernel UIDs* (host 120000+…); DAC, `SO_PEERCRED`, `chown`, `runuser` and supplementary groups are enforced by the real kernel against them. `/etc/passwd` and `/etc/group` are overlaid (bind) inside the namespace only. Reproducible via `native/deploy/multuid-userns.sh`. |

Caveats of this environment (not a rootful VM): the inner root *is* the invoking
user; the host kernel is shared (as with Docker); the transient systemd user
scope is unavailable to the inner daemon UID, so the process-execution test ran
with the labelled `rlimit-polling` backend — **kernel-enforced memory/pids limits
were not re-verified under multi-UID** (they remain verified by A3.4 single-UID
tests). A rootful Docker/VM sign-off is still recommended before production.

## 2. Topology (Phase 0/2)

| Principal | UID / primary GID | Groups | Role |
|---|---|---|---|
| nexusd-test | 20001/20001 | issuer, approver (SupplementaryGroups equivalent) | daemon; owns DataRoot `0700` |
| nexus-issuer-test | 20002/20002 | — | Controller/issuer; in `--allowed-uids` |
| nexus-bystander-test | 20003/20003 | issuer | same-group, **not** allow-listed |
| nexus-untrusted-test | 20004/20004 | — | adversary; no group access |
| nexus-approver-test | 20005/20005 | approver (own), **issuer (socket access only)** | independent approver; in `--approver-uids`, disjoint from `--allowed-uids` |

Credential delivery: issuer master cap `0600` daemon (DataRoot `0700`); issuer
handoff `0640 daemon:issuer-group` in socket dir `0750`; approver credential
`0640 daemon:approver-group` (see defect D1); dependency cache `0700`, owner
= euid (wrong owner → `cache-root` refusal).

Topology requirement discovered: the approver must be in the socket group to
connect. That makes the issuer handoff readable to the approver; this is safe
only because the daemon's `SO_PEERCRED` allow-list rejects issuer commands from
the approver UID (`peer-unauthorized`, tested). Approver-credential group must
never equal the socket group (enforced, D3).

## 5. Independent approver (Phase 4)

* Disjoint UIDs enforced at the daemon: overlap + `--require-independent-approver`
  → fatal `approver UIDs overlap`, no socket left; overlap without the flag and
  without the test-only flag → fatal `not independent`; the test-only flag
  cannot satisfy `--require-independent-approver`; `--approver-cap-gid` equal to
  the socket group → fatal (all in `multuid_production_configuration_…`).
* Real file permissions: issuer/bystander/untrusted cannot read the approver
  credential, master cap or database; approver cannot read master cap/db
  (`multuid_credential_files_…`).
* Key rotation across restart and allow-list change take effect for the real
  UIDs (`multuid_restart_preserves_…`).
* Process execution requires its own scope; approver key cannot execute.

## 6. Sandbox / filesystem under multi-UID (Phase 5)

`multuid_sandboxed_build_cannot_reach_capability_files_or_daemon_state`: an
approved `cargo check` (real build, exit 0) whose `build.rs`, running inside the
sandbox as the daemon's UID, probes the absolute paths of the master cap,
handoff, approver cap, database, witness, socket, host `/tmp` layouts, PID-1
environment and process table: **no escape**; response contains no capability.
Single-owner cache: only the owning daemon identity can open it; other identities
cannot list it; no shared writable directory was created.

No cross-identity privilege escalation was found: stolen capability on a wrong
UID, issuer↔approver key confusion, same-group bystander, approver with the
readable issuer key, and post-restart/allow-list changes all behaved as
specified.

## 9. Remaining limitations / production blockers

1. Not executed in a rootful Docker/VM; user-namespace run only (§1).
2. Kernel-enforced resource limits not re-verified under multi-UID (polling backend).
3. **Credential-isolation hardening concern (production):** the approver can read
   the issuer handoff credential through socket-group membership. Issuer
   operations remain protected by kernel peer-UID (`SO_PEERCRED`) enforcement
   (tested: `peer-unauthorized`), but the key itself is not isolated from the
   approver. Closing this needs a daemon change (separate socket-access group /
   ACL or per-UID credential delivery); not made here.
4. Same-UID compromise (daemon UID, or approver==issuer in test-only mode) remains
   outside the boundary (unchanged from A3.2–A3.5).
5. Independent approver credential delivery UX/human approval, external journal
   anchoring, seccomp allow-list review, second architecture: unchanged blockers.

## 10. Verdict

**PASS for the tested multi-UID identity and authorization boundaries** (18/18 with real
distinct UIDs; three defects fixed with regression tests), **with the environment
caveat above**. This is **not** a complete production security closure; production enablement still requires blockers 1–3 and 5.
