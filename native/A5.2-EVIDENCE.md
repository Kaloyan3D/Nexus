## 1. Phase 0 — who owns HTTPS connections

* There is no `nexus-model-transport` or `nexus-model-registry` crate in this repository. The component that owns every model
  connection is `nexus-model/src/transport.rs` (`HttpSseTransport`), driven by `nexus-client/src/model_run.rs`
  (`run_model_only`). Registry selection lives in `config/registry/*.cjs` and is sealed into the kernel by digest.
* Before A5.2 the transport used `std::net` only, refused `https`, and resolved names with `ToSocketAddrs` followed by a loopback-only
  check. It *did* support connecting to a resolved address (so IP pinning was feasible) but had no TLS and no per-address policy for
  public destinations.
* TLS choice: **rustls 0.23.45 + `ring` + `webpki-roots` 1.0.9**, all already present in the local cargo cache (offline build
  works; `Cargo.lock` gains rustls, rustls-webpki, rustls-pki-types, ring, untrusted, zeroize, webpki-roots, plus a duplicate
  getrandom/windows-sys set pulled by `ring`). Chosen over `native-tls`/OpenSSL (system trust-store dependence, larger surface) and
  over `reqwest`/`hyper` (would bring a redirect-following, proxy-reading HTTP stack that the earlier A2.2 audit rejected).
  rustls is the smallest verifying client that fits the synchronous, std-only transport.

## 2. TLS design (`nexus-model/src/egress.rs`)

* **Trust store:** compiled-in Mozilla roots (`webpki_roots::TLS_SERVER_ROOTS`). The host trust store and environment
  (`SSL_CERT_FILE`, etc.) are *never* consulted, so ambient configuration cannot change who is trusted. Root updates require a
  dependency bump.
* **Verification:** `ClientConfig::with_root_certificates` → webpki verifies chain, validity window, EKU `serverAuth`, name against
  the **original host name** (also the SNI). No `dangerous()` builder is used anywhere; a test asserts the transport sources contain
  no `dangerous` and no `env::var`.
* **Versions:** TLS 1.3 and 1.2 only (`with_protocol_versions`); 1.3 negotiated in the fixture test. ALPN `http/1.1`; early data off.
* **No bypass option:** `tls_config_with_roots` always verifies. The only way to trust anything else is to add *additional roots*
  (used by tests for a throwaway CA via `HttpSseTransport::with_parts`); production constructors (`HttpSseTransport::new`, the CLI,
  `ModelRunOptions.transport = None`) cannot do it.
* **Failure classification:** new codes `tls-failed` (untrusted issuer / name mismatch / expired / not-yet-valid / revoked /
  incompatible / aborted — message states the class, never peer bytes) and `destination-refused`. Both are raised **before any
  application byte or credential is written**, so the attempt stays `not_sent`.
* **Timeouts & cleanup:** connect ≤ 10 s per address, handshake ≤ 15 s, whole exchange ≤ `total_timeout_ms` (default 120 s);
  100 ms socket slices so cancel/deadline are observed during the handshake; TLS `close_notify` best-effort on drop.
* **Not provided (honest):** certificate revocation checking (no CRL/OCSP), certificate pinning, CT. Mozilla-root webpki trust is
  the same posture as typical clients.

## 3. DNS / egress policy

Per send, in order (`approve_destination_bounded`):

1. Parse origin strictly (scheme, no userinfo, valid port, IPv6 literals).
2. **Syntactic screen before any resolver query:** obfuscated numerics (`2130706433`, `0x7f.0.0.1`), `localhost`, single-label and
   `.local/.internal/...` names are refused with zero DNS traffic.
3. **Resolve once**, on a helper thread bounded by the exchange deadline and observing cancellation (`getaddrinfo` cannot be
   interrupted; the abandoned thread is harmless).
4. **Classify every returned address** (`classify_ip`): loopback, RFC1918, link-local/metadata, CGNAT, ULA, multicast, unspecified,
   benchmarking/documentation/reserved, NAT64, 6to4 (`2002::/16`), Teredo, IPv4-compatible and **IPv4-mapped forms of all of
   these**. One bad address refuses the whole destination (no "pick the good one").
5. **Connect by IP** (`TcpStream::connect_timeout` to an approved `SocketAddr`), verify the socket peer equals the approved
   address, then TLS with the original name. The name is not resolved again, so a rebinding answer cannot move the connection.
6. `http` is accepted only if every resolved address is loopback (the unchanged offline-fixture policy). `https` to loopback is
   possible **only** under `AddressPolicy::PublicOrLoopbackForTests`, which production constructors never use.

Also unchanged/extra layers: kernel scope policy (public https hostname or loopback http), Rust target validation, Registry
probe SSRF checks (JS), exact origin binding.

**Proxy:** the transport never reads `HTTPS_PROXY`/`ALL_PROXY`/`HTTP_PROXY`/`NO_PROXY` (test sets them to a listener and proves 0
connections). **Redirects:** any 3xx → `redirect-refused`, never followed, no `Authorization` forwarding (the redirect target —
including a *trusted* TLS server — saw 0 connections). **Secondary requests:** the response is parsed as SSE data only; no code
path turns provider content into a request.

## 4. Credential isolation

Unchanged owner (issuer-identity executor, protected `0600` file). Additions verified by tests: the authorization header is written
only after TCP + TLS verification; a peer that failed verification receives only handshake bytes (server-side capture is empty);
plaintext-downgrade server receives no `POST` or token; one `Authorization` header per request; no token in request body,
transcript, kernel/witness stores, daemon stdout/stderr, errors or `ModelRunStatus`. Desktop surface unchanged (display + cancel
only). Credentials never enter grants or model-visible context (grant fields are digests/refs only).

## 5. Streaming, timeout, cancellation

Verified over real TLS: incremental delivery; three events in one record; a multibyte character and a frame split across TLS
records (exact text, no U+FFFD, no duplicates); size/frame bounds (`payload-too-large`); malformed frame (`sse-malformed`);
`[DONE]`/`response.completed` semantics unchanged; peer closing without `close_notify` is treated as truncation (missing completion
event), not success; silence after handshake → `timeout` with `bytes_sent=true`, one connection, one resolution (no
retry/re-resolve); cancellation during DNS, during the TLS handshake, and mid-stream; stalled handshake hits the exchange deadline.
Provider failure vs transport failure vs cancellation remain distinct codes (`provider-failed`, `tls-failed`/
`destination-refused`/`disconnected`, `cancelled`).

**Grant semantics on TLS failure:** redemption happens before connect (A5.1 write-ahead design), so a TLS/destination failure
consumes the grant although nothing was sent. The run is `refused` (not `uncertain`) and a new Controller authorization is needed.
This is the safe direction and is pinned by `a52_e2e_untrusted_server_certificate_…`.

## 6. Provider compatibility (Phase 5)

* Wire format: OpenAI **Responses**-style `POST <base>/v1/responses` with `model`, `input`, `reasoning.effort`, `stream:true`,
  SSE `response.output_text.delta` / `response.function_call_arguments.delta` / `response.completed` (+usage, finish) /
  `response.failed`. Dialects supported by the Registry→native mapping: `openai-responses`, `local-openai-compatible`;
  `openai-chat-completions` is refused (`has no Responses path mapping`) — no silent translation.
* **Defects found and fixed (failing-first):**
  1. *Path doubling*: a provider `baseUrl` ending in `/v1` (the OpenAI convention, and what the Registry probe uses) produced the
     executed path `/v1/v1/responses`. `native-target-v2.cjs` now joins so executed path == probed path (JS regression added).
  2. *Unbounded provider output*: the sealed `outputLimitTokens` was validated but **never sent**. Requests now carry
     `max_output_tokens` (E2E asserts the sealed value reaches the provider). This changes request digests; A5.1 tests recompute them.
* Error status mapping (A5.1): 401/403/402/404/408/413/429/4xx/5xx → `provider-failed` with a class string, never retried.
* Provider request IDs: not captured (headers are not surfaced by the transport today) — gap.
* **Compatibility caveat:** the body also carries OpenCode-style extension fields (`session`, `metadata`, `x-opencode-session`
  header). Strict first-party OpenAI endpoints may reject unknown parameters; an OpenCode-Go-style Responses endpoint is the
  intended target. This can only be settled by the live check (BLOCKED). No automatic fallback or alternate provider exists.

## 7. Budgets (Phase 6)

Billable submission requires: explicit operator CLI invocation, `--enable-model-pilot` daemon (not production-v1), a user-explicit
intent, a Controller-minted single-use grant, a protected credential file, prompt ≤ 16 KiB, request ≤ the request cap, **provider
output ≤ sealed `max_output_tokens`**, local response cap 256 KiB, wall-clock ≤ 120 s, at most one submission per grant. Monetary
cost is **not** enforced or computed: no pricing source exists in the Registry; provider-reported token usage is recorded and any
cost figure would be an estimate, not a guarantee.

## 9. Live-provider acceptance (Phase 8)

**BLOCKED.** No operator authorization, no provider credentials and no request budget were supplied; ambient environment

## 10. Remaining production blockers

1. Live provider compatibility unproven (OpenCode-style extension fields; no provider request-id capture).
2. No revocation checking / pinning; trust store updates only with releases.
3. Static credential file: no rotation/revocation runbook, token in executor memory; executor runs as the issuer identity.
4. No monetary budget enforcement; output tokens are bounded, spend is not.
5. DNS resolution is the system resolver (no DoH/DNSSEC); a hostile local resolver can still return public addresses of its choice
   (policy bounds *which class* of address, not *whose*) — certificate verification is the control for identity.
6. Model attempts/redemptions are not externally witnessed; all A4.4 blockers (human presence, external anchor, systemd
   provisioning, rootful suite) still apply.
7. Production-v1 still forbids the pilot; a separate reviewed profile is required before any production inference.
8. GUI-initiated submission, tool-enabled AI and multi-turn grants remain unbuilt (A5.3+).

## 11. Final consistency review and documented limitations (pre-commit)

Re-verified against the final tree (tests in §8 all green): TLS verification is mandatory and has no bypass constructor; no
plaintext fallback (`https` origin never downgrades; `http` only to loopback); connection is made to approved pinned IPs;
redirects and proxy environment variables are not honored; the credential is written only after the handshake; a failed or
uncertain HTTPS exchange is never retried or re-resolved; model-only grants are single-use (durable redemption); production-v1
rejects `--enable-model-pilot`; model output has no tool authority; `nexus-kernel` is **unchanged** in A5.2 and
`Kernel::dispatch_enabled() == false`.

**DNS helper threads.** `resolve_bounded` spawns one short-lived thread per send because `getaddrinfo` cannot be interrupted. On
cancel/deadline the exchange stops waiting at once; the abandoned thread ends when the system resolver returns (bounded by the
resolver's own timeout, typically seconds to tens of seconds) and its answer is discarded. The count is bounded by the pilot
lifecycle: one thread per *send*, a send needs a single-use Controller-minted grant redeemed through the issuer-authenticated
daemon, and the executor is a one-shot CLI process that exits after one run, so threads cannot accumulate across runs and there is
no remote or model-controlled way to trigger sends. Not an exploitable resource-exhaustion path today. **Follow-up (A5.3+):** if
the executor ever becomes long-lived or multi-request, cap in-flight resolver threads (semaphore) or use a resolver with a
native timeout.

**Limitations to carry forward (explicit):**
* Provider compatibility has **not** been verified against any real service. The request uses Responses-style fields plus
  OpenCode-specific extensions (`session`, `metadata`, `x-opencode-session`); strict first-party endpoints may reject them.
* Output tokens are bounded (`max_output_tokens` from the sealed target) but **monetary cost is not enforced**; usage is only
  provider-reported and any cost figure would be an estimate.
* DNS cancellation stops the wait, not the underlying lookup (above).
* Certificate revocation (CRL/OCSP) and pinning are not implemented.
* Provider credentials and live operator authorization were unavailable; **no real billable request was made** and no traffic left
  127.0.0.1.
