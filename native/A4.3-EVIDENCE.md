## 1. Authoritative journals (Phase 0 inventory)

| Journal | Table | Writer | Seal/key | Local checkpoint | A4.3 anchor |
|---|---|---|---|---|---|
| Tool journal (authorized/started/completed, write phases planned→verified, process phases prepared→exited, expired/interrupted) | `tool_journal` | Kernel (daemon UID) | HMAC(issuance key), hash chain | `witness_meta tool_journal_checkpoint/v1` in local witness DB | **yes** `tool-journal` |
| Approval events (requested…consumed, revoked, recovered-*) | `approval_events` | Kernel (daemon UID) | HMAC(issuance key), hash chain | none before A4.3 | **yes** `approval-events` |
| Approval requests (sealed rows) | `approvals` | Kernel | HMAC seal per row | — | covered via events |
| Receipts/events/controller intents | `receipts`, `events`, `controller_intents` | Kernel | seals | witness epoch notes | unchanged (not extended) |

Write lifecycle and process records live inside `tool_journal` as phases; they inherit its anchoring.

Cases where the daemon UID can rewrite BOTH a journal and its witness (pre-A4.3): the local witness DB (`--witness`) and the store share the daemon UID and the issuance key, so a compromised daemon can truncate `tool_journal` and re-seal `tool_journal_checkpoint/v1` (reproduced by `truncate_and_reseal` in the tests), or restore an older (db, witness) pair. Approval events had no checkpoint at all.

## 2. Witness trust model

| Principal | Identity | Holds | Authority |
|---|---|---|---|
| `nexus-witness` | own Linux UID | state dir 0700, sealing key `witness.key` 0600 | remembers commitments; refuses non-continuations |
| `nexusd` | daemon UID (in witness client group) | nothing of the witness's | may commit/query; verifies server uid |
| issuer / approver / GUI / AI | others | none | no access to witness socket or state |

The witness has no authority over grants, approvals or task outcomes; it never signs anything that the Kernel accepts as authority.

Authentication is kernel-attested, not shared-secret: the witness checks the committer's SO_PEERCRED uid; the daemon checks the *server's* uid on the connected socket (`--external-witness-uid`). There is no credential file the daemon must hold, so no new credential-sharing weakness. Acknowledgements carry the request nonce and a witness commit sequence the client requires not to regress.

Boundary statement: protects against the daemon UID, issuer, approver, GUI and AI. It does **not** resist root, a compromised witness UID, kernel compromise, or an attacker who controls the daemon *before first anchoring*. A genuinely external anchor (remote/append-only service) is unavailable here and is a separate deployment blocker.

## 3. Protocol (v1, newline JSON over a Unix socket)

Requests carry `v`, `op`, `nonce`. Journals are domain-separated names (`tool-journal`, `approval-events`); unknown names refused.

- `query {storeId,journal}` → state `{count, tail, seq, adopted}` or null.
- `commit {storeId,journal,count,tail,prevCount,prevTail}` — accepted only as an exact continuation: `prev == witnessed state` and `count > witnessed count`; identical retry is idempotent.
- `adopt {…}` — only for a non-empty, never-witnessed journal (explicit legacy migration).
- `status` — pinned store id, commit seq, chain hash, violations.

Refusals (each counts a persisted violation, state unchanged): `rollback`, `fork`, `out-of-order`, `duplicate-sequence`, `unanchored`, `unknown-journal`, `store-substitution` (witness pins one store id), `adopt-refused`, `peer-unauthorized`.

Witness state: atomic temp+fsync+rename+dir-fsync, HMAC-sealed under the witness key, with a `state.sealed` marker: a tampered or deleted state file makes the witness refuse to serve (no silent reset). Reset is an offline operator action on a fresh directory only.

The client additionally verifies, before every commit, that the local journal still contains the witnessed prefix (`count >= witnessed`, entry hash at the witnessed position equals the witnessed tail).

## 4. Durability contract

1. Append to the local journal (SQLite tx, synchronous=FULL).
2. Commit `(count, tail)` to the witness; witness persists, then acknowledges.
3. Only after the acknowledgement may the transition authorize or be reported: tool grants are minted after `authorized` is witnessed; execution begins after `started` is witnessed; approval decisions are returned after witnessing; **consumption** is witnessed before the grant is minted.

Not atomic across the two stores; ambiguity is handled by an explicit protocol:

| Crash/failure point | Result |
|---|---|
| before append | nothing happened |
| after append, before witness commit | local tail unwitnessed: operation reported **failed**, authorizes nothing; next gate re-commits the continuation or refuses |
| witness persisted, ack lost (`drop-ack`) | caller sees failure; retry is idempotent; no violation |
| witness persisted, witness crashed (`exit-after-persist`) | same; restart + catch-up verifies |
| witness persist failure (`fail-persist`) | state unchanged; operation fails; recovery later |
| witness unavailable | privileged tool/approval authority refused (`witness-required`); reads continue |

An approval decision whose acknowledgement failed still exists as a genuine local decision; it cannot be consumed until witnessed, and becomes usable only after the continuation is committed (never fabricated). A request whose ack failed exists as `pending` and blocks duplicates until decided/revoked/expired.

Residual window (documented, accepted): entries appended but not yet acknowledged can be removed undetectably — they have, by construction, authorized nothing. Read-only list/history calls anchor best-effort and may leave unwitnessed `expired` events that are committed at the next gate.

## 5. Verification states (`integrity-status`, `nexus integrity`, Control Room)

`verified` · `unanchored-legacy` · `witness-unavailable` · `recovery-required` · `integrity-mismatch` · `not-configured`. Every report carries a `scope` string; the UI never shows a bare "secure". Mismatch is never auto-cleared; a verified recheck clears only a recoverable block.

Detected (tests in §7): edited/forked records, tail truncation (also with locally re-sealed checkpoint), rollback to an older self-consistent (db + local witness) pair, swapped store (incarnation), missing witness, replayed/forged acknowledgements, cross-journal and cross-store commitments.

## 6. Recovery and fail-closed behaviour

- Startup (`--external-witness`): verify → catch up unwitnessed continuation → if still not `verified`, reconciliation of interrupted writes/processes and approval recovery are *withheld* (they stay open/uncertain, never replayed) and privileged authority is refused through `require_tool_authority`. Health, status, approval-list and integrity-status remain available.
- Approver restart: approvals reviewed-pending are voided, approved-unconsumed lapse (A4.2), and these recovery events are themselves anchored.
- Interrupted write (real SIGKILL at `after-planned`): restart reconciles as interrupted, file unchanged, witness count == journal count.

## 7. Legacy migration

A store with history and no witness state is `unanchored-legacy` and is **not** trusted: privileged authority is refused. Operator adopts once with `--witness-adopt-legacy`; the witness records the state as `adopted: true`. History before adoption remains unwitnessed (tampering before adoption is not detectable). After first anchoring a persistent latch (`store_meta external_witness`) makes any later start without `--external-witness` refuse writes/process (`witness-downgrade-refused`); read-only start still works. A different DataRoot against the same witness is `store-substitution`.

## 9. Fault injection note

`NEXUS_WITNESS_FAULT=fail-persist|drop-ack|exit-after-persist` exists in the witness binary for tests. It is an environment variable on the witness process, which only the witness's own launcher controls; production units must not set it.

## 11. Remaining blockers / limitations

1. No genuinely external anchor (remote/append-only/hardware): root or the witness UID defeats it.
2. First-anchor trust: history before anchoring/adoption is unwitnessed.
3. The witness proves non-regression of daemon-asserted commitments; it does not validate entry content.
4. Rootful/systemd provisioning, witness key backup/rotation and operator reset procedure unverified.
5. Receipts/controller-intent tables are not yet witnessed.
6. Witness availability is a dependency: outage stops privileged authority (by design).
7. Same-UID hostile module inside issuer/approver (A4.1/A4.2 limit) persists; human presence is still PARTIAL (A4.2).

## 12. Prerequisites for A4.4

Genuinely external or hardware-backed anchor; witness provisioning/rotation/reset runbook verified on systemd; witnessing of receipts/intents; supervised policy that always passes `--external-witness` on production DataRoots; periodic independent verifier.

## 13. Final witness security audit

Confirmed defects fixed (with regression tests):

1. **Adoption laundering** — an anchored store pointed at a fresh witness with `--witness-adopt-legacy` would have adopted (and so accepted a rolled-back) history. Now `adopt-refused` once the store has been anchored; test `anchored_store_cannot_be_laundered_through_a_fresh_witness`.
2. **Latch vs enforcement** — the latch only protects a store *after* first anchoring. Added `--require-external-witness` (refuses to start without the witness even on a fresh store); `nexusd.service` passes it and `Requires=` the witness unit. The latch is now set only when the witness actually holds history (first `verified`), which also preserves the legacy-adoption path. Tests: `enforcement_matrix_*`, `legacy_unanchored_*`.
3. **Detection tests were initially vacuous for the new fault injector** — a replace that silently did not apply left `fail-after:N` inert; found by mutation. Fixed; with the gate/anchor disabled the sweep now fails 6 of 20 witness tests, including the `fail-after` sweep (the `drop-ack-after` sweep persists state, so it asserts non-early-authorization rather than counts and is not expected to fail under this mutation).

Crash-consistency proof (sweep over every commit of approve+write: `fail-after:N` and `drop-ack-after:N`, N=0..13): file never changes unless `planned` and `prepared` are witnessed; a grant is never minted unless the approval `consumed` event is witnessed and `started` never follows an unwitnessed `authorized`; a success response implies local == witness for both journals; every run recovers to `verified`. Additional tests: daemon SIGKILL between append and acknowledgement (witness stalled with `hang`), witness restart during retry, 8 concurrent commits from one prefix (exactly one wins), truncated unwitnessed tail (consistent, authorized nothing, documented), ambiguous continuation whose witnessed prefix no longer matches (not committed, blocks authority), witness exposes no grant/approval/reset operations (`bad-request`, state unchanged).

Witness authority (verified): daemon UID cannot read key/state or write them (multi-UID); cannot rewind/fork accepted state (`rollback`/`fork`, violations persisted); forged/replayed/wrong-identity acknowledgements rejected; commitments bind journal domain and store incarnation (`unknown-journal`, `store-substitution`); adoption is explicit and one-time; the witness binary links no Kernel/grant code and no sealing key of the Kernel.

Precise trust claim: a separate same-host UID provides rollback/truncation resistance against *daemon-only* compromise. It does not protect against host root, a compromised witness UID, or an attacker who controls the daemon before first anchoring.
