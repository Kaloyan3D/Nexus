# A3.4 Evidence — Sandboxed Process Execution

Branch `feature/rust-native-core`, baseline `d98d8c7` (A3.3). **Not committed.**

Adds secure, bounded, native process execution on the Controller → Kernel →
daemon authority chain: a Linux sandbox (bubblewrap + seccomp + cgroup v2),
policy-filtered immutable workspace snapshots, dedicated process grants and
scope, a durable process lifecycle, crash reconciliation, bounded redacted
output, CLI inspection and GUI visibility.

## Verdicts (kept separate)

| Scope | Verdict |
|---|---|
| **Offline sandbox implementation** (library + CLI offline harness, real processes) | **PASS** on this host |
| **Trusted daemon integration** (issuer + approver IPC, real nexusd, real cargo builds, SIGKILL recovery) | **PASS on a single-UID host, test-only approval** |
| **Host isolation tests** (real Linux escape/limit attempts) | **PASS (24 sandbox + 10 daemon + 11 process tests); host-specific, see §9 and §13** |
| **Multi-UID deployment** | **NOT RUN** (no Docker/root/dedicated UIDs) |
| **Production / AI-initiated execution readiness** | **BLOCKED** (§12; kernel-enforced limits now available here, multi-UID still NOT RUN) |

> Everything here is **trusted operator/test execution**. No model, provider
> or AI-initiated path exists. `Kernel::dispatch_enabled()` is `false`.
> Process execution is **disabled by default** in the daemon and, when
> enabled, the daemon refuses to start unless the sandbox preflight actually
> succeeds; there is no unsandboxed fallback anywhere.

## 1. Phase 0 — A3.3 cleanup TOCTOU (confirmed and fixed)

**Finding (reachable, failing-first):** the A3.3 cleanup `unlink_if_identity`
checks a directory entry's identity and then unlinks *by name*. The two
syscalls are not atomic: a party with write access to the **public** parent
directory can rename a foreign file onto the (predictable-once-known) temp
name inside that window, and Nexus deletes it. A deterministic test using a
test-only injection point inside the window (`mutate::set_between_check_and_unlink`,
feature `crash-injection`, compiled out of production) deleted the victim file.

**Fix (protected staging directory):** every write now creates a private
`0700` directory `.nexus-stage-<id>` (`mkdirat` + owner/mode verification);
the temp file and anything Nexus later removes or preserves live **inside**
it, and publication is a cross-directory `renameat2` from the stage into the
target directory. Nothing Nexus unlinks is in the shared directory, so a
directory-writer without access to the stage can no longer substitute a file
under a name Nexus is about to remove. Displaced/foreign files are renamed
aside inside the stage (`displaced`, `conflict`) and reported as
`preservedAs: "<stage>/<name>"`; the stage is removed only when empty.
Recovery (`observe_for_recovery`) understands the stage layout and the legacy
layout.

**Exact threat model / residual limitations:**

* Protected against: other-UID or group-writable-directory adversaries, and
  any writer that does not hold an open descriptor into the stage.
* **Not** protected against: an adversary running as the *same UID* as the
  daemon (it can enter the `0700` stage) — the same-UID boundary was never a
  claim of this system. Linux has no atomic conditional-unlink, so the
  microsecond check-then-unlink window inside the stage still exists; it is
  only exploitable by that same-UID adversary.
* Atomic compare-and-swap is still **not** claimed (A3.3 §5b unchanged).

Tests: `cleanup_cannot_remove_a_foreign_file_renamed_onto_the_temp_name`
(failing before, passes after), `staged_recovery_preserves_displaced_foreign_file_inside_the_stage`.
The A3.3 commit was not modified; this is new work on top of it.

**Additional defect found and fixed while building the stager:**
`Workspace::read_dir_names` duplicated the pinned root descriptor, which
shares its file offset; a *second* listing of the root through one
`Workspace` was silently empty. A3.1–A3.3 never hit it (one call per
`Workspace`). Fixed with `rewinddir`; regression test
`listing_the_same_directory_twice_through_one_workspace_is_complete`.

**Another defect caught by the crash test:** the generic restart
reconciliation (`started` without completion → `interrupted`) would have
closed running process requests *without killing their cgroup*. Process and
write phases are now excluded from the generic pass and reconciled by their
own layer.

## 2. Actual sandbox boundary (all mandatory)

Backend: **bubblewrap 0.13.0** (reviewed, widely deployed) + generated
**seccomp** BPF + **cgroup v2** supervision. Kernel here: Linux 7.2.9.

| Property | Mechanism | Verified by |
|---|---|---|

| No network incl. host loopback | new network namespace (private `lo` only) | `network_including_host_loopback_is_unreachable` (host listener never contacted; raw sockets denied) |
| `/proc` `/sys` | new PID ns + new procfs; no `/sys` | `proc_and_sys_do_not_expose_the_host` |
| No privilege escalation | new user ns, `--cap-drop ALL`, `--disable-userns`, `no_new_privs`, non-root uid | same + `privilege_escalation_primitives_are_denied` (`ptrace`, `mount`, `unshare`, `setns`, `bpf`, `keyctl`, `io_uring_*`, `kexec_load` → EPERM; `clone3` → ENOSYS) |
| Restricted env | `--clearenv` + explicit allow-list | `environment_and_descriptors_do_not_leak` |
| Restricted fds | `close_range(4,~0)` in `pre_exec`; only the seccomp fd survives and is consumed by bwrap | same test (only 0/1/2) |
| No uncontrolled children | PID namespace, per-execution cgroup, `cgroup.kill`, `--die-with-parent`, `PR_SET_PDEATHSIG` | `cancellation_and_revocation_kill_the_whole_tree`, `daemonized_grandchildren_do_not_outlive_the_execution`, daemon SIGKILL test |
| Process count | **kernel:** `TasksMax` on a transient systemd user scope (`pids.max`); always also `prlimit --nproc` (per user namespace) | `kernel_backend_enforces_aggregate_process_count`, `rlimit_nproc_is_scoped_to_the_user_namespace_and_really_applies`, `fork_bomb_is_contained_and_reaped` |

| CPU / runtime | `RLIMIT_CPU` + wall-clock deadline | `cpu_spin_and_wall_clock_are_bounded` |
| Output | bounded reader threads, cap + continued draining, truncation flag | `output_flood_is_bounded_and_flagged` (400 MiB flood → 64 KiB kept) |

in `prepared`.

### Kernel / host requirements and measured host state

Linux ≥ 5.14 (`cgroup.kill`, per-userns `RLIMIT_NPROC` accounting),
unprivileged user namespaces, `/usr/bin/bwrap`, `/usr/bin/prlimit`, a
writable cgroup v2 subtree for the daemon, **x86_64** (the seccomp program is
x86_64 only; other architectures refuse). On this host the **cgroup memory
and pids controllers are NOT delegated** (no `memory.max`/`pids.max` in a
child cgroup — `cgroup.subtree_control` of the scope is empty and cannot be
changed because the scope contains processes). Consequently memory and
process-count enforcement is *rlimit + polling*, not kernel `memory.max` /
`pids.max`. The preflight reports `cgroupMemoryController: false`. Where the
controller is delegated, adding `memory.max` is a drop-in hardening; it is
not implemented because it could not be tested here.

### Honest limits of the boundary

* seccomp is a **deny-list**, weaker than an allow-list; the namespaces and
  dropped capabilities carry most of the weight.
* Memory is **polled** (50 ms) plus a per-process `RLIMIT_AS`: a process can
  momentarily exceed the ceiling, bounded by AS × process count. CPU is not
  throttled (only `RLIMIT_CPU` + wall clock).
* The sandbox shares the host kernel: kernel vulnerabilities are out of
  scope. `/usr` is mounted read-only and is visible (system binaries).
* A signalled program is reported by bwrap's PID-1 as exit `128+signal`;
  the record carries `signalHint` and cannot distinguish a genuine exit 137.
* Toolchain directories (`~/.cargo/bin`, `~/.rustup`) are mounted read-only;
  they must not contain credentials (`credentials.toml` lives in
  `~/.cargo`, not in `bin`).

## 3. Process authority model

* **Command contract** (`proc.run` v1): logical `program` ∈ {`cargo`, `npm`,
  `tsc`} + exact `args` + snapshot-relative `cwd`. No shell strings; unknown
  members are rejected; the policy resolves the program path and the
  environment (allow-list) and validates argv per command
  (cargo: `check|test|build|fmt` with a flag allow-list, `--offline`
  required; npm: `test`, `run build`; tsc: `--noEmit [-p path]`). A
  model-provided command is **never** authority: it must pass the policy
  *before* a grant can exist and is meaningful only under a sealed grant.
* **Dedicated scope**: process grants have sealed `scope: "process"` (tool id
  `proc.run`). A read or write grant can never start a subprocess
  (verified: forged scope fields fail the seal; a read grant paired with a
  process call is refused; a process grant is refused by the read executor).
* **Independent approval**: `process-scope-approve` is authenticated with the
  **approver** capability (never the issuer's), peer-UID gated, replay
  protected, must name the bound workspace digest, and caps wall-clock time.
  Single-UID configurations are labelled `testOnlyApproval: true` /
  `approverIndependent: false` in every response and record.
* Grant binds task, attempt, lease epoch/incarnation, workspace identity,
  tool id/version, **argument digest**, **budget digest** (incl. all process
  budgets), cancellation id; exactly-once start; authoritative fence probed
  at ≤ 50 ms during execution.
* Daemon: `--enable-process` requires shadow-test mode, `--allowed-uids`,
  approver credential/UIDs, workspace bases, and a passing sandbox
  preflight — otherwise it refuses to start (tested: disabled by default,
  misconfiguration fails closed).

## 4. Workspace staging

The sandbox never sees the real workspace. `stage_workspace` copies the
policy-permitted tree (descriptor-relative, A3.1 boundary) into a private
`0700` run directory that is bind-mounted **read-only** at `/work/src`.

* Excluded before copy: hidden/VCS/credential paths, `node_modules`,
  `target`, `vendor`, build dirs, symlinks, hard-linked files, special files,
  other mounts, over-size files (counted per category in `snapshotSkipped`).
* Bounds: files, directories, depth, total bytes, per-file bytes
  (budgeted + ceilinged).
* Consistency: size/inode is compared with the **listing-time** identity; a
  file changed during staging aborts with `snapshot-failed` (tested).
* Digest: sha256 over sorted `(path, content digest)`; stable across runs.
* Artifacts live in tmpfs scratch (`/work/out`) and vanish with the sandbox;
  **nothing is published back** (real project untouched in every test). An
  artifact-export mechanism is deliberately not implemented; it would have to
  go through the write-approval path.
* Honest consequence: the snapshot is immutable, so `cargo` needs an
  existing `Cargo.lock` and `--locked`; dependency crates cannot be fetched
  (no network) and a registry cache is not mounted, so crates with external
  dependencies fail honestly (verified: `serde` dependency → `verification:
  fail`, `network: none`).

## 5. Lifecycle, fencing, recovery

`authorized → started (grant consumed) → prepared → running → exited |
failed | cancelled`, plus `interrupted` (reconciliation) and `expired`.

| Record | Durable before | Contents |
|---|---|---|
| `prepared` | spawn | snapshot digest/counts/skipped, sandbox digest, argv digest, redacted command, limits, cgroup path, run dir |
| `running` | — | pid, cgroup |
| `exited` | — | reason (`exited`/`timeout`/`memory-limit`/`process-limit`/`signaled`), exit code, signal hint, wall/user/sys ms, RSS/process peaks, output byte counts + truncation, redacted bounded tails, output digest |
| `cancelled` | — | `cancelled`/`revoked`, `processStarted` |
| `failed` | — | error code (no process started) |
| `interrupted` | — | `never-started` or `uncertain`, leftover processes killed, run dir removed |

* Mid-execution fencing: lease/generation/witness/revocation probed while the
  process runs; revocation → process-tree kill → `cancelled/revoked`
  (library and daemon tests, incl. revoke while a build sleeps).
* Daemon crash: SIGKILL of nexusd mid-build → sandboxed processes die
  (PDEATHSIG + PID-namespace teardown, asserted within seconds) → restart
  reconciliation records `interrupted` with `outcome: uncertain`, kills any
  leftover cgroup, removes staging, and refuses to run the same request id
  again. Never restarted automatically.
* Exactly-once start and replay refusal are the A3.1–A3.3 mechanisms
  (journal unique `(request, phase)`), tested for processes too.

## 6. Output security

stdout/stderr are read by bounded threads (cap per stream, default 256 KiB,
ceiling 2 MiB), redacted line by line with the A3.1 redactor
(`[REDACTED:nexus]`, `[TRUNCATED:nexus]`), and only an 8 KiB redacted tail
per stream is persisted. Responses and events keep tool results
distinguishable from assistant messages (no synthetic messages). Redaction is
best-effort pattern matching: **persisted tails may contain secrets the
patterns miss** — a documented limitation; raw output is never stored.
The sandbox environment contains no credentials by construction (allow-list),
so env dumps cannot reveal any.

## 13. Final sandbox audit (A3.4 close-out)

### 13.1 Resource enforcement — exact exposure

Before the audit the only aggregate limits were `RLIMIT_AS`/`RLIMIT_NPROC`
plus 50 ms supervisor polling. Measured and reasoned worst case of that
**polling** backend (still available, explicitly `rlimit-polling`):

* A process can allocate and touch memory faster than one poll interval.
  Measured: a single Python process with a 64 MiB budget reached
  **118 MiB (1.8×)** before being killed; native code can touch memory at
  GB/s, so the true exposure is *allocation rate × 50 ms*, further bounded
  only by per-process `RLIMIT_AS` (default 4× budget) × process count —
  i.e. **not a guaranteed aggregate bound**. Process count is bounded by
  `RLIMIT_NPROC`, which is only per user namespace and per process tree.
* `RLIMIT_NPROC` **does** apply inside the configured user namespace
  (verified by `rlimit_nproc_is_scoped_to_the_user_namespace_and_really_applies`:
  forks fail with `EAGAIN` at the configured limit, with the supervisor poll
  disabled, independent of the host's other processes).

**Fix:** a second backend, preferred automatically and *required* by
`--require-kernel-resource-limits`: the sandbox is started under a transient
systemd **user scope** (`systemd-run --user --scope -p MemoryMax=… -p
MemorySwapMax=0 -p TasksMax=…`), giving kernel-enforced aggregate
`memory.max` and `pids.max` even though this host does not delegate the
controllers to the daemon's own cgroup. `MemoryMax` = resident budget +
scratch tmpfs + `/tmp` tmpfs (tmpfs pages are charged to the cgroup).
OOM kills are detected from `memory.events`.

Verified: 8 processes touching ~1 GiB aggregate against a 192 MiB budget are
OOM-killed by the kernel with peak ≤ limit (+small slack); a fork loop is
stopped at `TasksMax`; the preflight and every result/record state which
backend enforced (`resourceEnforcement: kernel-cgroup | rlimit-polling`);
`status` reports `kernelEnforcedLimits`; the daemon refuses to start with
`--require-kernel-resource-limits` when only polling is possible (tested
both branches). **Polling is never presented as equivalent**: the GUI/CLI
record carries the label and production readiness requires the kernel mode.

Residual: CPU is not throttled (no `cpu` controller delegated; `RLIMIT_CPU` +
wall clock only). The kernel backend depends on a running systemd user
manager (`/usr/bin/systemd-run`, `XDG_RUNTIME_DIR`); without it the sandbox
runs in labelled polling mode (offline/test) or the daemon refuses.

### 13.2 Snapshot consistency — exact guarantee

Review confirmed the weakness: the earlier check compared only the
listing-time size and inode with the bytes read, which **cannot** detect a
same-size, same-inode in-place modification (and could not see a torn read).
(The new tests assert detection; the old comparison is incapable of it by
construction — it was not separately executed.)

Now, per file: `(size, inode, dev, mtime_ns, ctime_ns)` must match across
listing → open → after pass 1 → after pass 2, **and** the content is read
twice (second pass by `pread` from offset 0) and compared byte for byte. Tests
(deterministic, same inode and size by construction): a rewrite *after
listing* with `mtime` restored; a rewrite *between the two passes* of one
file with `mtime` restored — both abort with `snapshot-failed`. Because
`ctime` cannot be reset from userspace, a restored `mtime` does not hide a
modification.

**Exact guarantee:** each staged file is consistent (no torn/modified read
is accepted, subject to a writer completing both a modification and its
reversal between the two passes with identical bytes, which is by definition
not a different version). **The snapshot is NOT a point-in-time image of the
workspace**: files are copied sequentially, so a writer can change file A
after it was staged and before B is staged (shown by
`cross_file_snapshot_is_not_atomic_and_is_documented_as_such`). No
whole-workspace consistency is claimed; that would require a
filesystem-level snapshot (btrfs/ZFS/LVM), which is not used. The snapshot
digest identifies what was staged, nothing more.

### 13.4 Dependency-cache architecture (recommendation only; not implemented)

Goal: compile real Rust/Node projects with dependencies without giving the
sandbox network or the user's package homes.

1. **Content-addressed, read-only cache owned by a separate fetcher identity.**
   A privileged-but-networked *fetcher* (not the sandbox, not the daemon's
   issuer path) resolves a project's `Cargo.lock`/`package-lock.json`
   offline-verified against recorded checksums and downloads artifacts into
   `/var/lib/nexus/depcache/<sha256>/…`, root- or service-owned, read-only to
   everyone else. Every artifact is verified against the lockfile checksum
   before it is admitted; the cache index is itself sealed (HMAC) by the
   Kernel key so tampering is detectable.
2. **Per-execution materialization, not mounting a home.** For each run the
   daemon materializes *only the packages named in that lockfile* into a
   read-only vendor directory (`cargo vendor`-style layout / npm
   `node_modules` from verified tarballs) and bind-mounts that directory
   read-only; cargo is pointed at it via a generated `source.replace-with =
   "vendored-sources"` config living outside the snapshot.
3. **No install scripts from the network, ever.** npm `--ignore-scripts` for
   materialization; lifecycle scripts of *project* packages still run, but
   only inside the sandbox.
4. **Approval:** populating the cache is its own privileged, approver-gated
   operation (new package set = new approval), and is recorded in the same
   journal; sandbox runs only *consume* the cache.
5. **Not recommended:** mounting `~/.cargo`/`~/.npm` (credentials, mutable,
   cross-project poisoning), proxying a registry into the netns (re-opens the
   network surface), or a writable shared cache.

**What works today (offline, no cache):**

| Project shape | Result |
|---|---|
| Rust crate with **no** dependencies + `Cargo.lock` + `--locked` | works (`cargo check`, tested) |
| Rust crate with registry dependencies (e.g. `serde`, or this repo's `native/` workspace: `no matching package named hex found`) | fails honestly, `network: none` |
| Rust crate with path dependencies fully inside the snapshot | expected to work (not separately tested) |
| Rust project without a committed `Cargo.lock` | fails (`--locked` cannot create it; snapshot is read-only) |
| Vendored deps under `vendor/` | **excluded** by the staging policy today (treated as an ignored tree) → fails |
| `npm test` / `npm run build` | only for projects whose dependencies are already in the snapshot — but `node_modules` is excluded, so effectively dependency-free packages only |
| `tsc --noEmit` | requires a global `tsc`; project-local `node_modules/.bin/tsc` is excluded |

### 13.5 Recovery and output — re-verified

SIGKILL of the daemon mid-build: sandbox processes gone within seconds in
**both** backends (the scope/cgroup is checked in the user-manager slice as
well as the daemon cgroup); restart records `interrupted`
(`outcome: uncertain`, `processStarted: true`), kills leftovers, removes
staging, never restarts, and the same request id is refused. Oversized
stdout/stderr bounded (400 MiB flood → 64 KiB kept; 20 000-line stderr flood
through the daemon stays under 300 KiB in the response and 200 KiB in
persisted events). Persisted tails are built only from the already-redacted
bounded buffer; the redaction limitation (best-effort patterns) is stated in
§6/§11 and not weakened. Events remain scoped by the authoritative
(task, attempt); no assistant messages are synthesized from process events.

### 13.7 Updated production blockers

1. Multi-UID suite NOT RUN; independent approval unproven under real UIDs.
2. Production profile must run with `--require-kernel-resource-limits`; hosts

3. CPU throttling absent; seccomp deny-list, x86_64 only.
