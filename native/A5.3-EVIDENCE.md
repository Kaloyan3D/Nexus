## 2. Shared versioned intent API (`nexus-contracts/src/intent.rs`)

`NexusIntentV1 { schemaVersion, requestId, idempotencyKey, intentType, content, model?, limits{maxOutputTokens?}, responseMode, clientLabel? }`.

* Only `intentType = "model-only"`; anything else → `unsupported-intent-type` (`project-design`, `tool-run`, `shell`, `write`, "").
* `deny_unknown_fields`: `grant`, `cap`, `apiKey`, `providerUrl`, `endpoint`, `tools`, `workspace`, `approval`, `writeScope`,
  `processScope`, `command`, `clientId`, `leaseEpoch`, `extension`, `resolution` all → `bad-intent` (tested at contract level and over
  the real socket).
* Bounds: content ≤ 16 KiB (no NUL), ids/keys charset-restricted and length-bounded, `maxOutputTokens` ≤ 1,000,000 (the sealed
  Registry limit still applies; a request can only **lower** it — `ModelRequest.max_output_tokens`, `wrong-target` if higher).
* **Client identity is not a field**: it is `uid:<n>` taken from `SO_PEERCRED`. `clientLabel` is display-only.
* Verbs: submit, status, result, follow (offset long-poll ≤ 2 s, ≤ 32 KiB per reply), cancel, list (own runs only), models
  (Registry-issued, optionally narrowed by `--allow-model`).
* Replies carry authoritative `runId`, `taskId`, `taskInstanceId`, `attemptId`, `commandId`, `conversationId`, provider/model/logical
  target, endpoint kind, request digest, HTTP status, provider-reported usage, finish reason, latency, `errorCode/errorMessage`.

## 3. Broker security model

```
client (unprivileged)  ──unix socket, SO_PEERCRED──▶  nexus-broker (issuer identity)
                                                       │  Controller bridge (node, fixed args, env cleared)
                                                       │  daemon IPC signed with the issuer capability (this process only)
                                                       └─ run_model_only  → HTTPS provider (credential read by this process only)
```

* **Closed command set.** `intent-*` and `broker-health` only. `acquire`, `seal`, `accept`, `dispatch-authorize`, `model-redeem`,
  `tool-execute`, `workspace-bind`, `approval-request`, `intent-publish`, `status`, `shutdown`, `exec`, `read-file` all →
  `unknown-command` (tested). No path, URL, daemon command or shell is forwarded.
* **No authority in requests; no grant minting client-side.** The bridge fixes `scope=model-only` and `initiator=user-explicit`
  itself (a request cannot choose another scope — JS test); the kernel still requires the pilot flag and the sealed initiator.
* **AuthN/Z:** connection UID must be in `--allowed-uids` (default: the broker's own euid). Runs are owned by `uid:<n>`;
  status/result/follow/cancel on another client's run answer `not-found` (no existence leak); list shows only own runs; the
  idempotency index is keyed by (client, key). Run ids are validated (`run_<32 hex>`), so path traversal is impossible.
* **Bounds:** frame ≤ 80 KiB, ≤ 16 connections, 10 s socket timeouts, `max-active` concurrent runs (default 2 → `busy`),
  `rate-per-minute` per client (default 10 → `rate-limited`), prompt ≤ 16 KiB, sealed output limit, per-exchange wall clock.
* **Secrets:** the broker alone reads the issuer capability (hex, in memory) and the credential file; no verb returns either.
  Verified absent from every client-visible payload, the broker state dir, transcripts, ledger, kernel/witness stores
  (byte scan). The node bridge is spawned with a **cleared environment** (only `PATH`). Socket 0600 (0660 + chown only when a group
  is configured); state dir 0700; run records are written atomically (tmp + fsync + rename + dir fsync).
* **Single instance:** `flock` on `broker.lock`; a live socket at the path refuses start.
* **Startup preconditions (fail closed):** daemon reachable, `modelPilotEnabled=true`, `dispatchEnabled=false`,
  `trustMode=shadow-test`. A daemon without the pilot (which is what production-v1 forces — it forbids `--enable-model-pilot`)
  makes the broker refuse to start.

### Authentication limits (stated, not hidden)

* `SO_PEERCRED` proves the **UID** of the connecting process, nothing more. If Nexus Desktop, Arthur's backend, a terminal and a
  hostile local program all run as the same user, they all appear as the same client id and can see, cancel and replay each other's
  runs. This milestone provides **no** isolation between same-UID processes and does not claim any.
* Meaningful separation needs distinct UIDs per client (or per-client credentials delivered out of band): e.g. daemon UID, broker/
  issuer UID, desktop-user UID with the socket shared via `--socket-group`. The multi-UID harness in this repo already models that
  topology for the daemon, and the broker **is** now exercised in it (§12): daemon, issuer/broker, two Desktop-client UIDs,
  independent approver, external witness, bystander and untrusted UIDs.
* If the broker runs as the same UID as the Desktop user (a lab setup), any same-UID process could read the issuer capability file
  directly — in that topology the broker adds convenience, not security.
* **Residual:** the frontend parser and the issuer authority live in one process. Mitigation: strict, bounded, `deny_unknown_fields`
  parsing and a closed verb set. A stronger design (follow-up, not built) is an unprivileged intake process that only appends
  validated intents to a spool directory consumed by a separate privileged executor.

## 4. CLI (`nexus intent …`) and machine contract

Unprivileged: the CLI reads **no** capability or credential file; it needs only the broker socket
(`--broker-socket` / `NEXUS_BROKER_SOCKET`, default `~/.nexus/broker.sock`). Existing administrator/developer commands
(`nexus model …`, `nexus tools …`) are unchanged and separate.

```
nexus intent submit (--input FILE|- | --intent FILE|-) [--model p/m] [--idempotency-key K] [--request-id R]
                    [--max-output-tokens N] [--follow | --wait]
nexus intent status|result|cancel <runId>     nexus intent follow <runId> [--from-offset N]
nexus intent list [--limit N]                 nexus intent models
```

Envelope (`--json`): success `{"schema":"nexus.intent.cli/v1","ok":true,"run":{…},"text"?,"replay"?}`; failure
`{"schema":…,"ok":false,"error":{"code","message","class"}}` with `class ∈ usage|auth|rejected|transport|internal`.
`follow --json` emits NDJSON events `submitted|state|text|end` (each with the schema tag; `text` carries `delta`, `offset`,
`nextOffset`). Exit codes: 0 ok/completed, 2 usage/rejected, 3 broker unreachable, 4 unauthorized, 6 run ended without completing
(cancelled/uncertain/…). A simulated external consumer (test) depends only on this envelope and classifies errors from
`error.class`; it is **not** an Arthur integration.

Retry safety: the CLI generates a fresh key per invocation unless `--idempotency-key` is given — callers that may retry must pass a
stable key.

## 6. Controller → Registry → Kernel → executor path (per run)

`task-create` (intent ledger) → `issue` (Registry V1+V2) → `shadow` intent → daemon `acquire` + `seal` + `seal-extension` →
`kernel-intent` → `prepare_model_run` (expected-model check, output cap) → `publish` (model-only, user-explicit) → daemon
`intent-publish` + `accept` + `dispatch-authorize` → `run_model_only` (credential validated **before** redemption; redemption
write-ahead; verified TLS; streamed transcript). Model selection: `intent.model` must equal the Registry-issued target
(`model-not-available`, **before any run exists**); `--allow-model` can only narrow. No fallback/substitution exists.

## 7. Streaming, cancellation, recovery

* Follow is offset-based and resumable: reconnecting clients pass the stored byte offset (char-boundary validated, `bad-offset`
  otherwise); each reply ≤ 32 KiB; long-poll ≤ 2 s. Test streams ~110 KiB and reassembles it exactly.
* Cancel reaches the executor through the transcript stop marker (A5.1) in every phase: before submission (`cancelled`, nothing
  sent), during the TLS handshake (stalled peer, cancelled < 4 s, no application data), during streaming (< 5 s). Repeated cancel is
  idempotent (`requested` → `already-terminal`). A cancelled run is never `completed`; output shown is the real partial text.
* Client disconnect: runs are independent of connections. Desktop restart: runs/results are reread from the broker and transcripts.
* **Broker crash:** the broker was run as a child process and `SIGKILL`ed mid-stream together with a daemon restart. The new broker's
  recovery closes the run as `uncertain` (`send-uncertain`) through the executor's own recovery, replays of the idempotency key
  return the same run, the provider saw exactly **one** connection, and the daemon refuses re-authorization (`command-conflict`).
  A run that had not reached the executor becomes `abandoned` ("nothing was sent"). **Nothing is ever resumed or resubmitted.**
* Shutdown (SIGTERM): stops accepting, cancels running executors through the normal path, joins workers (≤ 20 s) — no orphans.
* Uncertain provider submission: `uncertain`; same key → same run; only a **new** key (an explicit client decision) creates a new
  attempt.

## 8. Duplicate/billable protection

Idempotency key + payload digest → one run (6 concurrent identical submits → one run, exactly one provider connection); same key
with a different payload → `idempotency-conflict`; durable key index created `O_EXCL`; Desktop key per click + disabled button;
grants are single-use (A5.1) so even a bug upstream cannot send twice. Limits as in §3. **Cost:** output tokens are bounded;
monetary cost is not computed or enforced (no pricing source) — any figure would be an estimate.

### 12.3 Privileged-broker audit
Examined: request parsing and framing, node bridge invocation and path resolution, environment, filesystem modes, client fields that
reach the bridge, socket ownership/group, command forwarding, credential disclosure, resource exhaustion.

* **No exploitable client-reachable privilege escalation was found.** The only client input accepted is `NexusIntentV1`
  (`deny_unknown_fields`, bounded); client text reaches the model prompt only — test with shell/JSON metacharacters shows it
  is absent from the ledger, broker state and bridge arguments; bridge/daemon parameters come from Controller/Registry outputs.
  No verb forwards a daemon command (tested for 25 names across the E2E/multi-UID suites).
* **Hardening defects fixed (operator/deployment boundary or availability, each with a regression test):**
  1. *Stale-socket handling could delete or follow anything at the configured path* → only a real socket is ever replaced; regular
     files and symlinks are refused and left intact (**failing-first confirmed by mutation**).
  2. *Socket created under the process umask before chmod* → bound under a restrictive umask (0177 / 0117).
  3. *`node` resolved through `PATH`, bridge code trusted implicitly* → `node` is resolved to an absolute path whose whole chain is
     owned by root or the broker uid and not group/world-writable (sticky ancestors tolerated); the bridge script and every module
     in its directory must be non-writable by others (tests: node in a 0777 directory, 0666 bridge module, unresolvable name).
  4. *Infrastructure detail (paths, interpreter messages) shown to clients* → `bridge-error`/`ledger-*`/`daemon-*`/panic failures
     show only a code; detail goes to the operator log; the Registry-target lookup likewise (**failing-first confirmed by mutation**).
  5. *A worker panic would strand a run non-terminal* → `catch_unwind` ends it as `rejected` (nothing sent).
  6. *Unauthorized peers could hold connection slots for 10 s each* → peer UID is checked before the read, unauthorized peers get a
     0.4 s fuse and a separate pool of 4 slots (the rest are shed with `busy`); authorized clients are never starved.
  7. *Unusable ledger/transcript directories only failed later* → the broker fails to start; the ledger dir is forced to `0700`.
  8. Observed during testing: Node's `mkdirSync({recursive:true})` on a path under `/proc` spins at 100 % CPU; the broker's 60 s
     bridge timeout bounded it and the new fail-early directory check prevents reaching it.
* **Residual same-process trust risk (kept, documented):** the request parser and the issuer capability/credential live in one
  process. The attack surface is a small, `deny_unknown_fields`, bounded parser behind a UID-gated socket; a memory-safety or
  logic bug there would be exploitable by an *authorized* UID. An unprivileged intake + separate privileged executor is the
  recommended follow-up; it was deliberately not built here (no redesign). Authorized UIDs can still consume the global
  `max-active`/rate budget (coarse limits). Crashes print no credential (the token lives in a `Credential` with a redacted `Debug`,
  panics print locations only).

### 12.4 Controller authority (dedicated native intent ledger)
* **Single authoritative record for this workflow:** `<ledger>/.ai-harness/state/tasks.json` + `runs/<INTENT-n>/attempts.jsonl`,
  written only by the broker's bridge (private `0700`, atomic writes, attempt evidence before the task record). Controller identities
  (task, taskInstance, attempt, session, command) come **only** from that ledger and the Registry/Kernel; nothing is taken from
  Desktop state or from the request.
* **Immutability:** `targetDigest`, `extensionDigest`, `requestDigest`, lease epoch/incarnation and task/attempt ids are sealed into
  the kernel intent and the HMAC-sealed grant; changing any of them breaks verification (A5.1 kernel tests), and the run record's
  terminal state is sticky.
* **No collision with legacy Controller ledgers (new regressions, JS):** the bridge refuses to write into a `tasks.json` that holds
  any non-`model-only-intent` record (`ledger-foreign`, file left byte-identical, no `runs/` created), refuses a task id that already
  exists (`ledger-collision`), and skips past (never reuses) an orphan attempt directory left by a crash. The `INTENT-nnnnn` namespace
  and a separate directory keep it apart from PowerShell TaskController ids.
* **DSH retirement:** the ledger is plain JSON read by `native-shadow-intent.cjs`; it needs neither DSH, the PowerShell
  TaskController nor `pwsh`, so retiring DSH does not affect it. The Desktop's historical DSH views are unrelated.
* **Limitations (explicit):** it is a native-shaped ledger, not the PowerShell Controller; no cross-ledger id uniqueness
  (namespacing only); no task lifecycle beyond the started attempt (terminal outcomes live in broker run records and the transcript,
  not back in the ledger); no compaction/retention; a crash between attempt write and task write leaves a harmless orphan directory;
  Controller "decisions" here are the Registry's issuance and the Kernel's sealed grant — there is no scheduler or multi-attempt
  policy. A broad Controller rewrite was explicitly not attempted.
