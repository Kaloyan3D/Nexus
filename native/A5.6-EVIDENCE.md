# A5.6 — Controlled Autonomous Coding: evidence

Branch `feature/rust-native-core`, base HEAD `81c30e192cd1283fa87e182abc1b7c6825e11466` (A5.5 evidence). **Uncommitted** working tree; nothing pushed. **No live provider call was made by A5.6**; the only network peers in any test are local fixtures.

Scope delivered: a new versioned `repo-code` intent in which the model may *propose* `fs_write`, `fs_edit` and `proc_run` inside an **isolated Git working copy**, each requiring its own independent, single-use approval, executed only through the existing Rust A3 tools and Kernel authorization. `model-only` stays tool-free and `repo-inspect` stays read-only. Nothing is ever committed, pushed or merged by the agent.

## 1. Intent contract

* `repo-code` is a distinct intent type in `nexus-contracts::intent` with its own limit set (`maxTurns` default 12, `maxToolCalls` 30, `maxEdits` 5, `maxTests` 5, runtime/result-byte budgets) and hard ceilings; unknown fields (paths, tools, commands, roots, approvals) are rejected. Test: `repo_code_is_a_distinct_intent_with_its_own_limits_and_no_smuggled_authority`.
* Tool catalog (`nexus-model::repo_tools`): `repo-inspect` offers exactly `fs_list fs_read fs_search`; `repo-code` adds exactly `fs_write fs_edit proc_run`; the provider adapter builds tools only from the catalog and records its digest. Verified on the wire: `a56_repo_inspect_and_model_only_stay_read_only_and_tool_free_beside_a_repo_code_daemon` (first provider body of each mode).
* Kernel: `SCOPE_REPO_CODE` + `enable_repo_code_pilot` (daemon `--enable-repo-code`); `check_ai_proposal` admits write/process only under a sealed `repo-code` intent with a user-explicit initiator and a dispatched turn, **and** they still pass the unchanged scope-binding + consumed-approval gates. Refused under `production-v1` (daemon test `repo_code_pilot_cannot_be_activated_under_production_v1`, integration `a56_production_v1_refuses_to_start_with_repo_code`).
* Daemon preconditions (each a separate lock, fail closed): model pilot, writes **and** process enabled, `--require-human-approval` (mandatory per-operation approval; never the coarse scope), a `--worktree-root` beneath an allowed workspace base.

## 2. Worktree isolation (`nexus-tools::gitwt`, 5 tests + 6 broker tests)

* The copy is a **local clone** (`clone --local --no-hardlinks --no-checkout`, detached checkout at the recorded commit), not `git worktree add`: the source repository's `.git` is never written, nothing writable is shared. Destination `<root>/<taskInstanceId>`; the model never supplies a path. Metadata lives outside the tool-reachable tree. Creation is atomic (`.creating-*` → rename) and stale half-built directories are swept at daemon start.
* Hardened Git runner: argv vector (no shell), cleared env, system/global config off, hooks and fsmonitor disabled, no prompts, timeouts, bounded output.
* Source acceptance: clean tracked tree, no untracked non-ignored files, born HEAD, no alternates/submodules, **no config key that can execute a program** (filters, fsmonitor, hooksPath, drivers, credential helpers, includes). Dirty/ambiguous/hostile sources are refused *before any authorization is spent*: `a56_a_dirty_or_unsafe_source_repository_is_refused_before_anything_is_sent` (tracked edit, untracked file, `core.fsmonitor`; provider accepted 0 requests; the fsmonitor payload never ran).
* Evidence the original is unchanged: after the full E2E, `git status --porcelain --ignored` of the source is byte-identical, HEAD unchanged, one commit; the copy has the edit, **no commit**, HEAD equals the recorded base commit.
* A committed symlink out of the project is never followed by an approved write (`a56_a_committed_symlink_…`; outside directory stays empty).
* Concurrent runs get separate copies and independent diffs (`a56_two_concurrent_runs_…`).
* Copies are **retained** for review after any outcome; no automatic deletion except half-built ones. There is a daemon `worktree-remove` verb but no client route; discarding a copy is an operator action.

### Clone vs `git worktree` (security closure audit)

A linked worktree writes `worktrees/<id>` administrative entries *into the source's `.git`*, keeps a live path link back to it, and shares the object store and refs — any process that can write the copy's `.git` can corrupt the source. The requested property is "original repository unchanged", so a clone was chosen: it shares nothing writable. Verified by `clone_isolation_audit_…` (real `git`, and the same properties again end to end in the broker tests):

* source working tree **and every `.git` file** byte-identical (sha256 + mode) after create, after an edit inside the copy, after diff, after removal, after a refused (dirty) create and after a stale-copy sweep; and after cancelled / timed-out / crashed runs (`src_fp` assertions);
* no shared inodes and every copied file `nlink == 1` (`--no-hardlinks`); no `objects/info/alternates`; no remote (`origin` removed — the copy has no path back to the source, so no fetch/push); `--template=` (no hook templates), `.git/hooks` empty, `core.hooksPath=/dev/null`, `core.fsmonitor=false`; a hostile source hook (`post-checkout`) never copied and never run;
* a source with config keys that can execute programs, alternates, submodules, linked-worktree/symlinked/bare layouts, unborn HEAD, dirty or untracked content is refused explicitly;
* committed symlinks stay symlinks (never followed), executable bit preserved; ignored files (`.env`, a FIFO) are not copied; the tools additionally refuse links/special files;
* the copy and its `.git` are owned by the daemon UID with no group/world write; destination derived from the task id (traversal ids refused by `remove`); creation atomic (`.creating-*` → rename), stale ones swept at start;
* retained-copy policy: copies are kept after any outcome for review (including failed/cancelled/uncertain runs); removal is an explicit operator action (daemon `worktree-remove`, task-id scoped).

No isolation defect was found; the mechanism was not redesigned.

## 3. Kernel write/edit authorization

* Model proposals pass (1) broker validation (`code::validate_code_proposal`: strict per-tool key allowlist, size/count caps, protected write names — `build.rs`, lock files, toolchain files, CI/Docker/Make files, hidden/sensitive/ignored dirs, `.git`; pre-image pinning to `fileSha256` the model actually read), then (2) `approval-request`, (3) `tool-execute` through the existing A3 prepare → consume approval → authorize → begin → execute → finish pipeline, journalled with `aiInitiated`.
* `a56_a_prompt_injected_model_…`: a model that obeys instructions from a hostile `docs/NOTES.md` (curl pipe, `sh -c`, `build.rs`, `.env`, `.git/hooks`, `../..` escape, `git push`, `cwd ../..`, reading `.env`, writing `Cargo.lock`, an invented `git_commit` tool) executes **none** of them; **zero approvals were even requested**; diff empty; nothing outside the copy changed; the repo secret appears in no log/body.
* `a56_the_kernel_independently_refuses_unapproved_or_out_of_scope_model_writes_and_processes`: an issuer-authenticated caller replaying `tool-execute` with `aiOrigin` and `fs.write`/`proc.run` (no approval, or a fabricated approval id) is refused by the Kernel with `scope-refused` in both an inspect and a code command; no approval is created or consumed. Read controls still work.

## 4. Independent approval enforcement

Reuses A4 unchanged (no new approval authority was added to the broker, CLI or Desktop).

* The broker only **requests** (issuer `approval-request`; the daemon authors preview, args/budget/path/task/attempt/workspace digests and `proposedBy`) and **polls** (issuer read-only `approval-list`). Review (`approval-get`) and `approval-decide` are approver-credential-only.
* E2E shows the approver saw the exact daemon-derived unified diff (`+    a * b`), `proposedBy.origin == "model"`, preview bound to the args digest, and four distinct request digests for four operations.
* Single use: every approval ends `consumed`; multi-UID test asserts all approvals `consumed` after the run.
* Denied → nothing executes, run continues (`…denied_approval…`). Unanswered → the run's own time budget ends it and the approval is not decidable afterwards (`revoked`/`expired`). Cancel while pending → approval `revoked`, a late approver's decision is refused (`…cancelling_while_an_approval_is_pending…`). Restart while pending → no `pending`/`approved` approval remains.
* Budget exhaustion (`maxEdits`/`maxTests`) refuses further proposals *before* an approver is asked even if the approver would approve everything.
* **Not proven / out of scope:** that a *human* is present. The single-UID test harness approves from a thread using the approver credential with `--allow-nonindependent-approver-test-only`; the daemon flags this as non-independent. The independence of the approver is proven only by the multi-UID run (§11). Patch-substitution/replay at the Kernel level is covered by the existing A4 suites (`approvals_a42`, multi-UID `stolen_credentials_cannot_forge_human_approval`), which A5.6 does not modify.

## 5. Process sandbox

* Policy is the A3.4/A3.5 `CommandPolicy`: `cargo check|test|build|fmt --check` with `--offline`, `npm test|run build`, `tsc --noEmit`; read-only snapshot, scratch discarded, no network, no ambient credentials, resource limits, fail closed without sandbox (`sandbox_ready()` gates the tests; the suite *ran* here with bwrap).
* `a56_a_hostile_build_script_in_the_repo_…`: a **committed** `build.rs` (the model can't write one, but a repo can contain one) that tries a loopback TCP connect, reading a host file, writing a host path, reading an ambient env secret and leaving background children. The script demonstrably ran (its output reached the model) and reported `NET=blocked READ=blocked WRITE=blocked ENV=none`; the host listener saw no connection; the outside directory is empty; the ambient secret and the host marker appear in no body/log; no orphan `sleep` survived.
* Ordinary model-visible results are bounded tails of redacted stdout/stderr plus `verification: pass|fail`, exit code/signal, wall time.
* Unconfirmed here: `npm`/`tsc` were not executed end-to-end (policy-level tests from A3.4 only); dependency crates need the A3.5 `--dep-cache`, which the dev script does not wire.

## 6. Coding loop

* Loop = one Controller attempt/command/single-use grant per model turn (Kernel intents are single-dispatch), reusing the A5.5 loop with a mode parameter. Defaults: 12 turns, 30 tool calls, 5 edits, 5 commands, one mutation at a time, run-time and result-byte budgets.
* Headline: `a56_e2e_edit_test_fail_diagnose_fix_pass_…` with the **real** Registry/Controller bridge, Kernel, Rust tools, bwrap sandbox, approvals, worktree and broker; only the model is simulated and is *reactive* (it asserts on the actual tool results it receives): list → read → fs_edit (plausible but wrong) → approval → write → `cargo test` **fails** (exit≠0, failure text reaches the model) → diagnosis → corrective `fs_edit` pinned to the first edit's post-image hash → approval → `cargo test` **passes** → final answer. 6 tool calls, 2 edits, 2 commands, 4 approvals, final diff = one file `src/lib.rs` showing only the net change.

## 7. Durable state and recovery

* Per-run durable record: tool activity with approval id/outcome, pre/post SHA-256 of each write, exit code and `pass|fail` of each command, `editsUsed/testsUsed`, last test verdict, worktree base commit, changed files and diff digest.
* Restart never resumes, re-executes or re-sends: `a56_restarting_the_broker_mid_approval_…` (provider request count unchanged; no usable approval left). Recovery of a repo-code run additionally revokes its open approvals and scans the journal: a write/process with a `started` phase and no end becomes `uncertain` / `tool-outcome-uncertain` (unit-tested fold `a_started_write_or_process_without_an_end_is_uncertain_never_assumed`); a lost daemon answer during a write/process also ends the run `uncertain` rather than a guessed failure. Provider-call uncertainty keeps the A5.4 `send-uncertain` semantics (never auto-resubmitted).
* **Crash-boundary fault injection (deterministic, real daemon):** `NEXUS_TEST_WRITE_CRASH_AT` makes the daemon SIGKILL itself inside an approved, Kernel-authorized operation. Two cases, each with the broker/provider/Controller chain live:
  * `after-applied` — an `fs_edit` whose post-image is on disk but whose verification was never recorded; journal `authorized, started, planned, prepared, applied` then, after restart, the daemon's explicit `interrupted`.
  * `proc-after-exit` — the sandboxed `cargo test` exited but its receipt was never written; journal `authorized, started, prepared, running, interrupted`.
  For both: the daemon died; the run ended `uncertain` / `tool-outcome-uncertain` (activity status `uncertain`, not failed, not completed); no further model turn; after restarting daemon **and** broker the run stays `uncertain` and nothing is re-sent; no success phase (`verified`/`exited`/`completed`) was invented; exactly one execution id exists; the single approval is `consumed` and none is `pending`/`approved`; replaying the same request and a fresh request for the same exact operation are both refused (`scope-refused: no approved human approval matches this exact operation`) and add no execution; the retained copy and `intent diff` remain readable (partial state inspectable); the source is byte-identical. Limits: the broker-process-crash variant (broker killed mid-operation) is covered by the restart test and the unit-tested journal fold, not by a killed broker process; the crash-injection feature is a dev-dependency feature of `nexus-daemon`, compiled only into test builds.
* Defects found while closing this and fixed: the recovery fold treated `completed` as the only clean end, so a *finished* write (`verified`) or command (`exited`) would have been reported uncertain on a later restart, and it ignored the daemon's `interrupted` marker — it now classifies by the full phase vocabulary and is unit-tested against real phase sequences; the cancel watcher made a single `tool-revoke` attempt (a lost attempt would leave a cancelled command running) — it now retries until accepted.
* Cancel during a running command: revokes the command, the sandboxed process tree is gone in milliseconds, run `cancelled` (`a56_cancelling_during_a_running_command_…`).

## 8. Diff / change management

* `worktree-diff` (daemon) runs `git add -A` in the copy's index only and returns a bounded unified diff + file list + digest; `intent diff <runId>` and the Desktop viewer show it. The diff is client-scoped by run ownership (second UID gets `not-found`). Nothing applies, commits, pushes or merges; applying the patch to the real repository is a manual step.

## 9. CLI and Desktop

* CLI: `intent submit --type repo-code --workspace <source-id> [--max-edits N] [--max-tests N] --follow --json` emits NDJSON `submitted / state / tool / approval-pending / text / end` (stable `nexus.intent.cli/v1`); `intent code-sources`, `intent diff <runId>`, `status/result/cancel` unchanged. Test `a56_cli_submits_code_runs_…` (rejects a path as source and an inspect-only workspace as source).
* Desktop (reuses the A5.5 UI): "Code in copy" mode only when the operator approved a source; explicit write/execute/provider disclosure; proposed edits table with approval outcome and pre→post hash; test results; pending-approval banner explaining *Desktop cannot approve*; classified diff viewer; uncertain-outcome and limit alerts; cancel. Tauri backend gained three commands (`intent_code_sources`, `intent_code_submit`, `intent_diff`) that only speak the unprivileged broker protocol; a source-pin test forbids any approval verb, tool name, `Command::new` or `std::process` in the production backend. Vitest: `code.test.tsx` (5), asserts there is no apply/commit/push/merge/approve/deny control.
* Not done: an in-app approve button (deliberately; the approver is a separate tool).

## 10. Adversarial results (all against real Kernel paths)

Prompt injection; protected/hidden/credential write paths; path traversal; `.git` hooks; symlink escape; non-allowlisted programs/`cwd`/extra keys/file mode; invented tools; forged/fabricated approvals; denied, unanswered, cancelled and restarted approvals; edit/command budgets; dirty/hostile source; malicious `build.rs` (network, host read/write, ambient env, orphan processes); cancel during a running command; concurrent runs; production-v1 refusal; repo-inspect and model-only staying read-only/tool-free beside a repo-code daemon. All 18 tests in `nexus-broker/tests/code_a56.rs` pass, including 4 consecutive full runs under 6 busy-loop CPU hogs (an earlier 4 s run budget in the timeout test was load-sensitive and was widened; the tool is refused fail-closed either way). Defects found and fixed *by* these tests: unknown model argument keys (`fileMode`) were accepted; `model-only` session records were writable; process calls timed out at the 15 s IPC read; `--code-allow` was silently ignored in the CLI parser; the approval wait read the wrong response shape.

## 11. Multi-UID (real distinct kernel UIDs, userns harness)

`multuid_a56_repo_code_write_and_process_authority_across_distinct_identities` (nexusd, issuer/broker, approver, two Desktop UIDs, bystander, untrusted): neither Desktop UID can read or write the source, the working copies, or reach `tool-execute / approval-* / worktree-*` (socket permission denied, and `unknown-command` through the broker); the run **stops at `fs_edit` approval** with the real approver idle (source unchanged, nobody decided); the **issuer credential (the broker's) can neither review nor decide**; the approver UID then approves each operation; the daemon-journal shows scopes `read, write, process`, all `aiInitiated`; all approvals `consumed`; the source repository is unchanged; the diff is readable only by the owning Desktop UID (second UID: `not-found`); the provider saw neither the credential nor unrelated source. Full suite: **39 passed** (baseline 37, +2), 1 filtered, 0 failed.

**Positive path** — `multuid_a56_positive_independent_approval_executes_edit_and_sandboxed_test_via_the_real_approver_cli`: real kernel UIDs for daemon, issuer/broker, approver, two Desktop clients, plus the external witness; **no raw `approval-decide`, no `confirmation: {tty:false}`, no test-only approver flag** (the daemon runs `--require-independent-approver` with role-separated credential groups). Sequence demonstrated: Desktop UID submits `repo-code` → daemon creates the isolated copy → run blocks on a pending `fs_edit` approval with the copy still containing `a - b`, forged decisions by the issuer/broker credential refused, Desktop UIDs denied at the socket → the approver UID runs the real `nexus-approver review` on a **pty**, sees the exact diff (`+    a + b`, `src/lib.rs`), types the displayed review code, `recorded: approved` → the Kernel executes the edit (journal: authorized[model-initiated, write, `approverIndependent`], planned, applied, **verified** with pre/post SHA-256; post hash equals the bytes on disk) → second pending approval for `cargo test --offline`, reviewed and approved the same way → sandboxed execution (journal: prepared with `network: none` and the exact argv, running, **exited** `exitCode 0`) → `lastTestVerification: pass`, file contents correct. Both approvals end `consumed` with `approverId` = the approver UID; a second `approval-decide` on a consumed approval is refused; the source repository (tree and `.git`) is byte-identical before/after; the external witness journal counts equal the daemon DB counts and `integrity-status` is `verified`. What this does **not** show: that a human typed the code — the harness drives the pty. Physical human presence remains unproven (A4 limit).

## 14. Production blockers

1. Human-presence of the approver is not cryptographically proven (A4 limitation, unchanged).
2. Broker-process crash mid-operation is not simulated by killing the broker (daemon crash and broker restart are; §7).
3. npm/tsc paths, dependency caches and multi-crate/workspace repos not exercised end to end.
4. Working copies are retained with no retention/GC policy or client discard route.
5. `--enable-repo-code` is forbidden under `production-v1` by design; there is no production profile for it.
6. Live provider behaviour is unmeasured; cost/abuse budgets rely on per-run limits and the single-use session record only.
7. Desktop cannot approve; usable operation requires the separate approver tool.

## 15. Self-hosting limitations

Not suitable for modifying Nexus itself yet: copies exclude ignored/untracked content and need a clean, hook-free, config-clean source; protected-file rules deliberately forbid editing lock files, `build.rs`, CI and toolchain files, which a real Rust workspace change often needs; large repos exceed the 32 KiB write / 256 KiB diff bounds; no dependency cache is wired; sending Nexus source to a provider is excluded by the A5.6 rules. A6.1 was not started.
