## 1. Architecture review (ten questions, A2.1 deltas only)

1. **Source of truth.** Unchanged: Controller ledger (attempts), JS Registry
   (model resolution), kernel SQLite receipts + witness reservations. New derived
   state only: `--allowed-uids` list (operator configuration, echoed in
   status/readiness, never persisted) and the transport posture report.
2. **Ownership.** Unchanged: only `nexusd` writes its DataRoot while live (CLI
   mutations refuse with `daemon-owns-store`). New: the daemon refuses to *start*
   on a DataRoot it does not exclusively own in the DAC sense (euid-owned,
   `0700`), so a permissive directory can never host kernel persistence.
3. **Dependency direction.** Unchanged: JS transport -> daemon IPC -> kernel ->
   store. The UID gate lives in the daemon transport layer; the kernel never
   learns peer credentials and its seal/binding checks are unchanged.
4. **Service boundaries.** IPC v1 unchanged; one additive refusal code
   (`peer-unauthorized`) and two additive observational fields (`peerUidEnforced`,
   `allowedUids`, plus the readiness `transport` object). No existing field moved.
5. **Failure semantics.** New refusals fail closed with named codes, never fallback:
   non-allowlisted peer -> `peer-unauthorized`; missing peer credentials with a
   configured allowlist -> `peer-unauthorized`; permissive hosting dir ->
   `insecure-dataroot` at startup with no socket bound; unknown `--allowed-uids`
   syntax -> exit 2 before any state opens. In-process frames without a socket
   peer are refused exactly like credential-less connections when a gate is set.
6. **State lifecycle.** Unchanged daemon lifecycle. The allowlist is parse-once at
   startup (immutable for the incarnation); the cap key still rotates every start,
   so pre-restart tags fail HMAC post-restart and there is no cross-restart replay
   window.
7. **Test seams.** Real-subprocess harness extended (`spawn_daemon_opts` with extra
   argv, owner-only `0700` temp DataRoots); real `SO_PEERCRED` on every connection
   (never injected). No sleeps for synchronization; readiness is polled.
8. **Migration/compatibility.** Additive only: no schema/version moves; default
   behavior (no `--allowed-uids`) is byte-identical to A2.0. Rollback = delete the
   new tests/deploy docs and revert the gate to `None` (single commit, no data
   migration). The strict `0700` startup check may refuse previously permissive
   dev directories — that is the intended fail-closed behavior, documented here.
9. **Observability.** `status` and `readiness` now report the transport posture
   (`peerUidEnforced`, `allowedUids`, `capAuth`, `limitation`); every refusal is
   logged as bounded JSON with ids/codes only (no keys/tags/nonces).
10. **Security implications.** See sections 2–6. The gate authenticates the
    connecting *process* (UID), never the calling *JS module*: same-UID module
    confusion is explicitly out of scope and stated in every surface that reports
    the gate. No new privilege is granted in any mode; production stays BLOCKED.

## 2. What was built (and what was deliberately NOT built)

Implemented:

- `server.rs`: `allowed_uids: Option<Vec<u32>>` on `Daemon`; `parse_allowed_uids()`
  (strict comma-decimal syntax, duplicates removed, empty entries rejected);
  `authorize()` enforces **cap-HMAC first, UID-allowlist second** — a stolen
  capability alone is insufficient when the gate is set; `dispatch()`/`serve_frame`
  thread the real per-connection `SO_PEERCRED` peer (captured once, never
  self-asserted); `verify_protected_dir()` (euid-owned + `0700`, else
  `insecure-dataroot`); transport posture in `status`/`readiness`; `peer-unauthorized`
  code in `protocol.rs`.
- `main.rs` (daemon + kernel CLI): `umask 0077` first, so store/WAL/cap/socket are
  owner-only even if a later chmod is missed; `--allowed-uids` flag;
  fail-closed DataRoot + external socket-parent checks before the lock, the store
  open, or the socket bind.
- `tests/isolation.rs` (7 tests, all real binary + real socket + real peer creds):
  non-allowlisted UID refused despite a VALID cap; allowlisted shadow flow works
  with cap/store/witness `0600` + DataRoot `0700`; unauthenticated + forged-tag
  seals refused; replay rejected with gate enforcing; CLI mutation refused while
  live; permissive DataRoot refuses startup with no socket bound; readiness stays
  `NOT_READY` with `dispatch_enabled=false` and reports the transport posture.
- `native/deploy/SETUP.md` + `nexusd.service`: the production identity/directory/
  invocation design (`nexusd` vs `nexus-issuer` vs untrusted UIDs) as configuration
  and documentation. Host accounts, services, and privileged paths were NOT
  touched (no authorization); the unit is not enabled here.

Deliberately NOT built (would be scope expansion or false security):

- No new shared capability file, no static token, no "second cap" as a same-UID
  fix — the task forbids it and it would not survive same-UID theft either.
- No kernel issuer-allowlist constant: the kernel already binds the issuer string
  inside the HMAC-sealed issuance bytes (tampering breaks the seal into
  `forged-issuer`) and checks issuance/target/snapshot digests plus
  generation/role/mode binding (`accept.rs`). Origin trust remains channel
  authentication at the daemon transport; duplicating it in the kernel would add
  a second source of truth without new evidence.
- No socket-dir group-sharing relaxation: with the strict `0700` check, a distinct
  issuer UID cannot traverse a DataRoot-hosted socket. The production socket-dir
  design (group-accessible socket dir outside the DataRoot, gated check
  relaxation) is specified in `SETUP.md` as remaining work, not half-enabled.
- No execution enablement of any kind (see section 7).

## 5. Unsupported guarantees (read before any wider use)

- **Same-UID hostile peers are NOT stopped without the gate, and same-UID module
  confusion is NEVER stopped by it.** `SO_PEERCRED` proves which UID/PID
  connected, not which JavaScript module produced a request. A hostile thread or
  module inside the allowlisted issuer process can still use the process's
  capability. Issuer-process hardening is separate future work.
- **File-mode bits are necessary, not sufficient.** `0600`/`0700` deny distinct
  UIDs only when the OS identities actually differ and no broader access (ACLs,
  mounts, backups, container volume sharing, root-equivalent peers) re-exposes
  the files. Deployment must audit those out of band.
- **Witness separation assumes separate failure domains.** Same-disk witness +
  store restored together remains undetected by construction (retained A2.0 limit).
- **No power-loss, no cross-file atomicity claims** (retained A1.1/A2.0 limits).
- **Readiness is observational.** The `transport` object (including
  `peerUidEnforced: true`) is posture reporting, never an authorization token.

## 6. Why production is BLOCKED (evidence, not belief)

Genuinely distinct OS identities are unavailable to this runner. Attempted and
observed in this task:

- `setpriv --reuid=65534 … id` -> `setresuid failed: Invalid argument` (exit 127).
- `python3 -c "os.setuid(65534)"` -> `OSError: [Errno 22] Invalid argument`.
- `sudo -n -u nobody id` -> `sudo: /etc/sudo.conf is owned by uid 65534, should
  be 0` + `The "no new privileges" flag is set` (exit 1).
- `runuser -u nobody -- id` -> `may not be used by non-root users` (exit 1).
- `unshare --user --map-root-user id` succeeds but maps only the caller's own UID
  (single-self-map for unprivileged users): the namespaced child is the *same*
  host kuid, so DAC and `SO_PEERCRED`-as-seen-by-the-daemon cannot distinguish it.
  A fabricated distinct host kuid requires privileges this runner does not have.
- NoNewPrivs=1, empty capability sets (`CapEff: 0`), `/tmp` unrelated.
- Host account/service modification was explicitly out of scope and not attempted.

Therefore: the enforcement logic is proven against real peer credentials with a
non-matching allowlist value, the DAC bits are proven, the refusal paths are
proven — but **independent evidence of the operating-system security boundary
with two live distinct UIDs does not exist**, and per the task it is required
before any execution-readiness claim. The isolated test harness
(`spawn_daemon_opts` + `isolation.rs`) and the deployment configuration
(`native/deploy/`) are implemented so the target host can supply that evidence;
until it does, production readiness is BLOCKED.
