## 1. Desktop data path — before and after

**Before (A5.3).** Send went through the broker (`intent-submit`), but every *read* of a model run bypassed it:

| Desktop need | Tauri command | What it did |
|---|---|---|
| conversation page (streaming, resume) | `conversation_read` | `nexus_client::conversation()` → opened `<transcript_dir>/model_….jsonl` **directly** |
| run status/provenance | `model_run_status` | `nexus_client::model_run_status()` → direct transcript read |
| run list | `list_model_conversations` | direct scan of the transcript directory |
| cancel | `cancel_model_run` | broker (`intent-cancel`), else local marker |

Under distinct UIDs the transcript directory is issuer-private (`0700`), so the Desktop UID got `EACCES`: the conversation view was empty/broken (the A5.3 evidence recorded this as a deployment gap).

**After (A5.3.1).**

```
React ConversationPanel / ModelRunPanel / RecentTasks     (unchanged rendering code)
   │  conversationRead / modelRunStatus / listModelConversations / cancelModelRun   (same NativeApi)
   ▼
Tauri commands ──▶ nexus_client::desktop_contract   ◀── `nexus intent desktop …` (CLI view of the SAME functions)
                      │
                      ├─ model_… ids: broker verbs  intent-conversation | intent-list | intent-cancel   (unprivileged socket, peer-UID authn)
                      └─ fallback ONLY on `not-found` / broker unreachable: the caller's OWN local transcript dir
                              (operator-started single-user CLI runs; under distinct UIDs it contains nothing of the broker's)
```

* New broker verb **`intent-conversation {conversationId, afterSeq?, beforeSeq?, limit≤200}`**: read-only, served **only if a run owned by the connection's client id points at that conversation** (same `not-found` for absent and foreign — no existence leak); returns the same `ConversationView` JSON the Desktop already renders, produced by the broker from its private transcript. No path, no file handle, no other primitive. Cursor paging (`afterSeq`) preserves incremental streaming, reconnection and partial (`partial`/`interrupted`) messages; `beforeSeq` preserves "load earlier".
* `IntentRun.promptPreview` (first 160 chars of the owner's own prompt) lets the Desktop list show titles without a transcript read.
* `model_run_status` is built from the broker's `IntentRun` (provider/model/endpoint kind/state/usage/errors/cancel flag); `text` is empty there because the UI takes text from the conversation view.
* `list_model_conversations` merges broker runs with the caller's local runs (dedup by conversation id). Runs that have no conversation yet are surfaced by the composer's pending-run state instead.
* The historical (non-intent) viewer — DSH logs, `task_…`/`mock_…` conversations — is unchanged and still reads the user's own sources.
* Filesystem isolation is **not weakened**: no ACL, no group access, no new readable path. The transcript directory stays `0700` issuer-owned.
* Frontend change: only labels for broker states (`preparing`, `executing`, `rejected`, `abandoned`).

## 3. Security regression

* **No issuer credential or provider secret reaches Tauri:** the Tauri backend still references no `issuer::`, `signed_frame`, `read_capability`, `credentials`, `run_model_only`, daemon verbs (source-pinned test, extended with a second pin that every model-run read/cancel routes through `desktop_contract` and none reads transcripts directly). `desktop_contract` itself only calls `intent_client`.
* **Broker protocol remains model-only:** still a closed verb set; `intent-conversation` is a read of the caller's own run, not a path/file API; the 25 privileged names still → `unknown-command` (tests unchanged and green).
* **Per-client isolation intact:** now also covers conversation reads.
* **Production-v1 still forbids the pilot** (`development_model_pilot_cannot_be_activated_under_production_v1`, broker refuses without the pilot).
* **Fixture-only TLS/resolver cannot be enabled in production builds:** the `test-fixtures` feature is off by default; test `a53_audit_default_broker_binary_carries_no_fixture_trust_injection` verifies the default workspace binary contains none of the fixture strings.
* **No live provider requests:** all traffic is the loopback TLS fixture.

## 4. Intermittent broker test failures — investigation

Observation recorded in the A5.3 audit: one `cargo test --workspace` run (immediately after a failed clippy invocation, while the machine's 1-minute load average was ~19) had 11 broker tests fail at the Registry-fixture `node` driver step.

Hypotheses checked:

| Hypothesis | Result |
|---|---|
| Parallel test collisions / shared temp dirs | Every test uses its own `tempfile` directory, socket, state dir and ports; no shared path found. Not supported. |
| Registry state initialization race | The driver is single-process and writes only into its own data root. **40 concurrent `driver registry` invocations under 24 busy loops on 8 cores: 0 failures.** Not reproduced. |
| Node subprocess startup | Same experiment: no start-up failures. |
| Environment isolation | The broker clears the child environment; tests inherit a normal one. No dependence found. |
| Build-artifact races | The failing run followed a failed compile; test binaries/`nexus`/`nexusd` come from earlier builds and the tests never rebuild. Plausible only for tests needing the CLI binary, not for the driver step. Not demonstrated. |
| Stale sockets / child processes | Each broker uses a fresh socket path; no stale process was present in later runs. |
| **CPU starvation** | **Reproduced** as a distinct failure class: with 24 busy loops on 8 cores, 4 of 7 full broker runs failed 1–5 tests (e.g. `bridge-timeout` at the broker's 60 s node-call bound, "executor never reached the provider", "child broker never came up", "run never finished" at 20–30 s waits). Without induced load every broker run in this task and the previous audit passed (well over a dozen runs). |

Conclusion (stated accurately): **the original 11-failure incident was not reproduced and its exact cause is not isolated.** The only failures reproducible are load-induced timeouts of bounded waits; they are not data races or logic errors (the failing runs end in honest `rejected`/timeout states and never produce a second submission). I did **not** raise timeouts or disable tests. One diagnostic improvement was made so any recurrence is attributable: the fixture's `node_json` now includes the driver's exit code, stdout and stderr tail in the assertion message (previously only the subcommand name). Guidance: do not run the broker suite on a saturated host; the documented configuration (default parallelism on 8 idle cores) passed repeatedly.

## 6. Residual limitations

* The Desktop still polls (≈1.5 s); each poll is a broker connection and the broker re-reads and re-verifies the whole transcript chain per `intent-conversation`/`status`/`list` call (O(transcript) per call; list reads up to 100 transcripts for previews). Fine for the pilot; a cache or push channel is future work.
* `intent-conversation` returns the run's full event set for the owner (user prompt, assistant text, status/error events). It never exposes another client's data or arbitrary files.
* Under distinct UIDs the fail-safe local stop marker is unusable; cancel *requires* the broker (by design). If the broker is down the Desktop can neither read broker-run conversations nor cancel them.
* `model_run_status.text` is empty for broker runs (text comes from the conversation view).
* Same-UID applications remain indistinguishable (A5.3); the single-process broker residual risk, provider-compatibility, spend-enforcement, systemd hardening and external-witness gaps from A5.3 still stand. Live-provider acceptance remains BLOCKED; production readiness NOT READY.
