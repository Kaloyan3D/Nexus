# A3.3 Evidence — Secure Write/Edit Tools

Branch `feature/rust-native-core`, baseline `61932d5` (A3.2). **Not committed.**

Adds `fs.write` and `fs.edit` on top of the A3.1/A3.2 trusted read-only
architecture: an independent write-approval authority, a dedicated write
scope, descriptor-relative atomic publication, a durable write lifecycle,
deterministic crash reconciliation and SIGKILL-tested recovery.

## Verdicts (kept separate)

| Scope | Verdict |
|---|---|
| **Offline write-tool implementation** (library + CLI offline harness) | **PASS** |
| **Trusted daemon integration** (issuer + approver IPC, real nexusd, SIGKILL recovery) | **PASS on a single-UID host, test-only approval; multi-UID NOT RUN** |
| **Production / AI-initiated write readiness** | **BLOCKED** (see §12) |

> Everything executed here is **trusted operator/test execution**. No model,
> provider or AI-initiated call path exists. `Kernel::dispatch_enabled()` is
> `false`; there is no shell/process execution; write tools are **disabled by
> default** in the daemon (`--enable-writes` + approver configuration).

## 1. Phase 0 — prerequisites assessed and resolved

### 0.1 Independent workspace/write authority

Assessment of what exists:

* The A3.2 `workspaceRootDigest` commitment is made by the same capability
  holder that issues `accept` → **not independent** (confirmed).
* The Controller attempt journal's `workspace` field is an unprotected file
  writable by the same UID → **not accepted as authority** (per task rules).
* No second principal existed in the architecture.

**Remediation (smallest real one):** a second, separately generated
**approver capability**. `write-scope-approve` is authenticated with a key
the issuer does not hold, is peer-UID-gated by `--approver-uids`, is
replay-protected, and must *name the workspace root digest it approves*.
The Kernel seals the resulting `WriteScopeBinding` (HMAC under the issuance
key, domain `nexus-write-scope/v1`) bound to command, task, attempt, lease
epoch + incarnation, workspace digest, byte budget and approver id. A
write grant cannot be minted without it:

* the issuer key cannot satisfy `write-scope-approve`, and the approver key
  cannot satisfy any issuer command (both tested);
* a valid issuer who accepts a self-consistent command still gets
  `scope-refused` for writes;
* approving a different digest than the bound workspace is `binding-mismatch`;
* a scope for command A cannot be used by command B (cross-task test).

**Honest limit.** Independence is only as strong as key/identity separation.
The daemon computes `independent = approver UIDs ∩ issuer UIDs = ∅` and
seals that fact into the binding (and into every approval response); it is
never self-asserted by a caller. In single-UID development/test setups it is
**`false`** and reported as such; `--require-independent-approver` refuses to
start in that case. Real independence therefore **requires the multi-UID
deployment, whose tests were NOT RUN** (§8). Until then production writes
stay blocked, as the task requires.

### 0.3 Tool-event visibility

`--enable-writes` refuses to start without `--allowed-uids` (so
`tool-events` and every privileged command are peer-gated), without an
approver credential and UIDs, without `--workspace-bases`, and outside
`shadow-test` mode (all tested). `tool-events` was already scoped to an
existing (task, attempt) and is an allow-listed projection; it now also
carries write change metadata (digests, sizes, mutation state — never
content).

### 0.4 Journal crash safety

Design and durability points are in §4. Local crash consistency is provided
by "journal intent first" ordering plus restart observation; this is
**not** tamper resistance: the witness checkpoint remains a same-host,
same-user file, so a privileged same-host attacker is **not** defended
against, and the A3.2 one-entry checkpoint window is unchanged.

## 2. Write authority model

```
Controller accept (issuer cap) ─► workspace-bind (issuer, intent-committed root)
Approver (separate cap, UID-gated) ─► write-scope-approve {commandId, rootDigest, maxWriteBytes}
        └► Kernel: WriteScopeBinding (sealed; independent flag from daemon)
tool-execute fs.write|fs.edit (issuer cap) ─► prepare_write (budget ≤ approved max)
        ─► Kernel::authorize_tool  (scope=write: needs binding + write scope; sealed grant)
        ─► Kernel::begin_tool_execution (re-checks write scope; journals `started`)
        ─► write lifecycle (hooks: journal + authoritative fence)
```

* The grant carries a sealed `scope` (`read`/`write`) derived from the tool id
  (`tool_scope`) and re-derived at every verification. A read grant can never
  authorize mutation: forged scope/tool fields fail the seal; a genuine read
  grant paired with a write-prepared call is refused; the read executor
  refuses to run write grants; write phases cannot be recorded on read
  grants; `complete_tool_execution` refuses write grants.
* Grant binds task, attempt, lease epoch/incarnation, workspace digest +
  dev/ino, args digest (path, mode, content, expected pre-image, edits),
  budget digest (incl. `maxWriteBytes`, capped by the approved scope),
  cancellation id, expiry (120 s), unique request id, approver id (via the
  write scope).
* Model/renderer JSON never creates authority: arguments are typed
  (`deny_unknown_fields`), digested, and only meaningful under a grant the
  Kernel sealed.

## 3. Filesystem mutation security

* Targets: UTF-8 text only; parent directory must already exist (no implicit
  `mkdir`); no deletion, rename, chmod, shell.
* Write policy is **stricter than read**: any dot-prefixed component (incl.
  `.git`, `.env*`, `.gitignore`, `.github`, Nexus temp names), any sensitive
  name, and dependency/build directories (`node_modules`, `target`, `vendor`,
  …) are refused for writes. Traversal/absolute/encoded paths are refused
  lexically.
* Descriptor-relative throughout: parent opened via the A3.1 `openat2`
  (`NO_SYMLINKS|NO_XDEV|BENEATH`) walk with mount-ID and identity checks;
  target opened with `open_file_in_dir` (symlink, special-file, hard-link
  and mount-crossing refusal, identity re-check). Symlinked, hard-linked,
  FIFO and cross-mount targets are refused with zero mutation (tested).
* Temporary file: `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600, same directory,
  name `.nexus-tmp-<execution id>` (unguessable, hidden, unwritable via
  tools), `fchmod` to the final mode, `fsync` before publication.
* Metadata semantics: `create` → mode `fileMode` (≤0777, default 0644);
  `replace`/`edit` **preserve permission bits**. Owner, group, ACLs,
  xattrs, mtime and birth time are **not** preserved (the file becomes a new
  inode owned by the daemon user).
* Unsupported filesystems (no `renameat2` flags): refused with
  `unsupported-filesystem` — no non-atomic fallback.

## 4. Durable lifecycle and crash recovery

```
authorized ─ started ─ planned ─ prepared ─ applied ─ verified
                 └──────────────┴──────────┴─────────► failed | conflict | interrupted
```

| Record | Written | Durability point (SQLite `synchronous=FULL`, then witness checkpoint) | State the backend can claim |
|---|---|---|---|
| `authorized` | grant minted | before the grant is returned | no mutation |
| `started` | grant verified | before any workspace byte is touched | no mutation |
| `planned` | pre-image read, post-image computed | **before the temp file exists**; carries path, op, pre/post sha256, sizes, mode, temp name | no mutation |
| `prepared` | temp written + fchmod + fsync | before the final fence and publication | no mutation (temp only) |
| *(rename + dir fsync)* | — | — | **mutation may have occurred** |
| `applied` | after rename and parent-directory fsync | before verification | published; unverified |
| `verified` | target re-read, hash == planned post | final | **mutation verified** |
| `conflict` | expectation not met | final | mutation `none` (restored if it raced) |
| `failed` | error | final | `mutation`: `none` / `published-unverified` / `uncertain` |
| `interrupted` | restart reconciliation only | final | observed: `pre-image-intact`/`post-image-present`/`diverged`/`unobservable` |

* The state machine is enforced in the Kernel (`record_write_phase`):
  each phase exactly once, in order, no phase after a terminal one.
* **Restart reconciliation** (`nexus_tools::reconcile_writes`, run at daemon
  startup before serving): for every request with `planned` and no terminal
  record the target is *observed* (never modified), an abandoned temp is
  removed, and `interrupted` is recorded with `observed` + `mutation`. It
  never replays, never invents `applied`/`verified`, and the same request id
  can never run again (SIGKILL tests assert this).
* A journal failure after publication surfaces as an error with
  `outcome: uncertain` — a write is never marked successful merely because
  the process returned.
* SIGKILL tests (real nexusd, feature-gated crash points, restart):
  after `planned`, after `prepared`, after rename (before `applied`), after
  `applied` — for both replace and create. Observed/mutation values asserted
  exactly; temp artifacts removed; replay refused.

## 5. Conflict detection and atomicity

* Pre-image: `replace`/`edit` require the exact sha256 of the current bytes
  (create requires absence). Mismatch, absent target, existing create target,
  ambiguous/missing edit text, no-op edit → `conflict`, **never** an
  overwrite, journaled `mutation: none`.
* **Publication is detect-and-undo, not atomic compare-and-swap.**
  `replace` uses `renameat2(RENAME_EXCHANGE)` so that *the exact inode that
  was replaced* lands on the temp name atomically with publication and can
  be hashed. The kernel cannot make the replacement conditional on content,
  so a pre-image mismatch is only detected **after** our file is visible at
  the target name, and is then undone non-destructively (see §5a). `create`
  uses `RENAME_NOREPLACE` (a genuine atomic create-if-absent).
* Edits apply in declared order on the progressively edited text; each
  `oldText` must match exactly once; 1–16 edits, 64 KiB each.
* Fencing: authoritative fence checked before `planned` and again immediately
  before publication; the cancellation token likewise. After publication
  nothing aborts: a revocation/cancel arriving after the rename is recorded
  as the truthful `applied`/`verified` outcome (tested) — never "no changes".

### 5a. Final-audit findings on the exchange protocol (A3.3 close-out)

Confirmed by deterministic fault injection (`WriteHooks::at` sync points and
the `after-exchange` SIGKILL point), **failing first** against the earlier
implementation:

| # | Finding | Fix |
|---|---|---|
| C1 (P0) | **Reversal destroyed a newer external replacement.** Exchange → another writer atomically replaced the target with E → reversal exchanged D back in and then `unlink`ed the temp name, which now held E. The newest data was deleted and the name ended with the *older* file. | Reversal is identity-checked and non-destructive: after exchanging back, the temp name is inspected; if it is not our own inode, the exchange is repeated (their file is restored to the target) and the displaced earlier file is renamed aside (`.nexus-displaced-<id>`), never deleted. |
| C2 (P0) | **Reversal discarded an in-place write** made into our briefly-published inode (a writer opening the name after the exchange). | The inode is deleted only if it still hashes to the post-image; otherwise it is kept as `.nexus-conflict-<id>` and reported (`preservedAs`). |
| C3 (P0) | **Crash recovery deleted the displaced file.** After SIGKILL right after the exchange the temp name holds the file that was displaced; recovery unlinked it by name, which could destroy an externally modified file. | `prepared` records the temp inode `(dev, ino)`. Recovery removes only (a) its own never-published temp, or (b) a displaced file whose hash equals the expected pre-image; any other file is preserved (`displacedPreserved`, `publishedOverUnexpectedPreImage: true`) and nothing is rolled back automatically. |
| C4 | Cleanup paths unlinked temp files by name. | All own-temp removals go through `unlink_if_identity`. |
| M1 | Replacing a setuid/setgid/sticky file silently kept (or would have changed) privilege bits. | Refused (`conflict: special-mode-bits`). |
| M2 | A file owned by another user would silently change owner on replacement. | Refused (`conflict: owner-differs`). |
| M3 | `user.*`, POSIX ACL and `trusted.*` xattrs were silently dropped. | Refused (`conflict: xattr-present`). |
| P1 | A daemon could enable writes with a non-independent approver in a "production-looking" configuration. | Refused at startup unless `--allow-nonindependent-approver-test-only` is given; every write response/record then carries `approverIndependent:false` / `testOnlyApproval:true`, and the GUI labels it. |

### 5b. Exact supported concurrency model

**Guaranteed (and tested):**

1. *Between Nexus writers:* exactly one of N concurrent `replace`s of the
   same expected pre-image succeeds; the rest report `conflict` with no
   mutation (8-writer test).
2. *Create:* atomic create-if-absent; a concurrent creator always wins
   cleanly or loses cleanly.
3. *Non-destruction invariant:* Nexus never unlinks an inode other than
   (i) its own temp whose identity it recorded, or (ii) the displaced file
   it just hashed and verified to equal the expected pre-image. Every other
   file it displaces is renamed aside, and that includes foreign
   replacements, in-place appends into the published file and
   crash-displaced files. A matrix test (replace / in-place append / delete
   / rename-away by an external party at the exchange window) asserts that
   every distinct external byte string remains on disk.
4. *No false success:* a write is reported `verified` only after re-reading
   the target and matching the planned post-image hash; a late in-place
   writer turns the result into `published-unverified`, not success.
5. *Crash truthfulness:* after any SIGKILL point restart reconciliation
   records `interrupted` with the observed state; it never replays, never
   claims `verified`, and never deletes a file it cannot prove is its own or
   the expected pre-image.

**Not guaranteed (documented limits; no claim of full CAS):**

* The target name briefly points at the new file before a mismatch is
  detected; concurrent *readers* can observe content that is later undone.
  During a reversal the name may transiently hold the earlier external file.
* An external **in-place writer** that already holds an open descriptor to
  the pre-image can write into the inode after our hash and before/after we
  remove it; that write is lost (indistinguishable from "replaced by
  rename"), and cannot be prevented without cooperative locking, which is
  not provided. Such writers are *not excluded* — only rename-style
  publishers and Nexus itself are coordinated.
* `check-then-unlink` of files Nexus itself created has a microsecond window
  (identity is verified immediately before the unlink).
* When the reversal itself cannot complete (e.g. an external party moved our
  published file away) the outcome is `published-unverified` and a temp or
  displaced file named in the journal may remain; it is never deleted
  automatically.
* Power-loss durability beyond the filesystem's fsync semantics is not
  claimed.
* If the filesystem lacks `renameat2` flags the write is refused
  (`unsupported-filesystem`); there is no non-atomic fallback.

### 5c. Metadata contract (actual behavior)

| Attribute | `create` | `replace` / `edit` |
|---|---|---|
| Permission bits | `fileMode` (≤0777, default 0644), exact (fchmod; umask-independent) | **preserved** (executables stay executable; tested) |
| setuid/setgid/sticky | cannot be set (≤0777) | target with them is **refused** |
| Owner | daemon euid | target owned by another uid is **refused** (owner would change) |
| Group | daemon egid (or setgid directory's group) | **not preserved**; follows creation rules (disclosed) |
| `user.*` xattrs, POSIX ACLs, `trusted.*` | none | target carrying them is **refused** |
| `security.*` (SELinux/IMA labels) | applied by kernel/LSM defaults | **not preserved** (disclosed; not detected) |
| Timestamps (mtime/atime/ctime/btime) | new | **not preserved**; new inode, new mtime (disclosed) |
| Inode number / open descriptors | new inode | **new inode**: processes holding the old file keep the old content; hard links are refused, so no alias drifts |

Operational note for source files: scripts keep their executable bit, but a
running interpreter or editor that keeps the old inode open will not see the
new content, and tools that watch by inode will see a replacement.
Ownership/ACL refusal was verified for mode bits and xattrs; the
owner-differs branch could not be exercised without a second UID and is
covered only by code review.

## 6. Undo semantics

**No automatic rollback exists.** The pre-image hash is journaled; a future
undo may restore content only if the file still hashes to the recorded
`postSha256`, using the same compare-and-swap path and requiring the old
bytes to be supplied by the operator (the journal intentionally does not
store content). A changed target is never touched. This is a documented
design constraint, not an implemented feature.

## 7. Client / CLI / GUI

* Client API `ToolEventV1` gained `scope` and `change`; statuses cover
  `planned/prepared/applied/verified/conflict/interrupted`. One shared
  allow-listed projection (`record_from_entry`) serves daemon, client and
  tests (no raw payload passthrough; only digests/sizes/paths).
* CLI: `tools inspect fs.write|fs.edit` (shows "MUTATING: requires
  independent write scope"); `tools list` includes them. **There is no
  `nexus write` command** (tested exit 2). Offline mutation requires all of
  `--offline-test`, `--allow-write-test`, `NEXUS_TOOLS_OFFLINE_TEST=1`,
  `NEXUS_TOOLS_OFFLINE_WRITE_TEST=1`, a workspace beneath the system temp
  directory, and a `.nexus-offline-write-test` marker in its root. The
  throwaway Kernel self-approves and the report says "write scope
  SELF-approved, NOT independent". CLI users can never mint write grants
  (no approver key, no daemon execute path).
* GUI (Inspector → Tool activity): shows operation, path, pre→post hash,
  size, mutation claim ("no file was changed" only when the backend recorded
  `mutation: none`; uncertain/unverified states are worded as such), conflict
  reasons, and a "write (independent approval required)" marker. It only
  displays records; the renderer has no fs access, no Tauri fs/shell
  permission was added, and no assistant messages are synthesized.
  Diff review is not implemented (the journal deliberately stores no
  content); the data model is ready for a Controller-mediated review.

## 9. Findings during implementation (see also §5a for the final-audit findings)

* The A3.2 `workspace-bind` commitment is not independent authority
  (documented in A3.2, now addressed by the approver channel).
* The A3.1 read policy allow-listed some hidden files (`.gitignore`,
  `.github`); applying that list to *writes* would have permitted mutation of
  VCS/CI control files, so write policy was made stricter.
* `tools list`/`inspect` and two A3.1 tests asserted a three-tool, all
  read-only surface; they were updated to the five-tool surface with an
  explicit `requiresWriteScope` flag (no behavior regression).

## 11. Remaining limitations

* Independent approval is unproven under real multi-UID deployment (NOT RUN).
* Same-host attacker with write access to both SQLite files and the issuance
  key can forge a consistent journal/witness pair; the one-entry checkpoint
  window remains; no external anchoring.
* Same-UID hostile processes can read both capability files (A1.3.3
  limitation) — in that configuration `independent` is `false`.
* Linux ≥ 5.8 and a filesystem supporting `renameat2` flags only.
* Exchange-check window visible to concurrent readers; in-place writers are
  not excluded (see §5).
* Owner/ACL/xattr/mtime not preserved; text files only; no mkdir/delete.
* No undo implementation; no diff-review UI; attempt identity for the GUI
  still depends on the configured run directory.

## 12. Production blockers (must clear before any production or AI-initiated write)

1. **Run and pass the multi-UID suite** (11 tests) on a prepared host;
   require `--require-independent-approver` in the production unit.
2. **Human/Controller approval UX** that holds the approver credential
   outside the renderer and outside the AI-execution path.
3. **External anchoring** of the journal checkpoint (or pre-commit
   checkpoint) so a same-host privileged attacker is detectable.
4. A Controller-signed (or journal-verified) workspace commitment that does
   not rely on the issuer for the root.
5. Per-path/prefix write allowlists in the approval (today: whole workspace
   minus the policy denylist, bounded by bytes).
6. An implemented, tested undo/restore using compare-and-swap.
7. Review of AI-path integration: nothing AI-initiated is wired; adding it is
   a separate milestone and must go through the approver channel.
