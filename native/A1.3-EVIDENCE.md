## 0.1 Implementation plan (executed as written)

- **Process ownership.** One `nexusd` owns one DataRoot via an exclusive
  `daemon.lock` held for its whole lifetime. The daemon reuses the existing
  `nexus-kernel` crate (no competing Kernel): a single persistent `Kernel`
  behind one `Mutex`, with the kernel's own `flock` + IMMEDIATE-transaction
  layer as the cross-process backstop. Legacy CLI mutations check the same
  lock (non-blocking) and refuse with `daemon-owns-store` while a daemon
  is live; reads stay available.
- **IPC trust boundaries.** Unix Domain Socket, newline-delimited JSON,
  IPC protocol v1 (exact-match, never negotiated down). Read-only commands
  (`health/status/receipt/journal/digest`) need no authorization.
  Privileged commands (`acquire/seal/accept`) are refused in the default
  `readonly` trust mode (`privileged-disabled`) and require per-request
  HMAC authentication in the explicit `shadow-test` mode. `SO_PEERCRED`/socket
  permissions are NOT treated as JS-module authentication (see section 6).
- **Durable state.** Unchanged A1.1 layout (main SQLite store + independent
  witness SQLite). Daemon adds only `daemon.lock`, the socket file, and
  `issuer.cap` (shadow-test only, 0600, rotated every start). No schema change.
- **Failure modes.** Crash mid-request -> receipt durable, client re-reads
  by commandId and converges (created-or-replayed, never conflict, never
  two receipts). Corrupt/incompatible store -> startup refusal (never serve
  untrusted persistence). Witness loss -> `reconciliation-required` + latched
  status. Stale socket -> reclaimed after a failed connect probe. Second
  daemon -> `daemon-already-running`. Oversize/malformed/unknown -> versioned
  refusal, connection hygiene preserved, daemon survives.
- **Compatibility.** A1.2 CLI contract preserved byte-for-byte for reads and
  for mutations whenever no daemon owns the store (A1.2 suite re-proven
  87/87). Daemon transport presents the same `invokeBridge` shape so A1.2
  reconciliation logic is reused without duplication; delivery `await`s the
  invoke so sync (CLI) and async (daemon) transports both work. No silent
  fallback from a refused daemon request to a CLI mutation (forbidden path,
  tested).
- **Test strategy.** Real-subprocess tests only for lifecycle/IPC/auth
  (actual `nexusd` binary, real sockets, real SIGTERM/SIGKILL via `kill`);
  real Registry + real Controller shapes (+ one real pwsh TaskController
  section) for JS integration; temporary DataRoots/sockets everywhere.

## 1. Architecture review (ten questions, deltas from A1.2)

1. **Source of truth.** Unchanged: Controller ledger (attempts), JS Registry
   (model resolution), kernel SQLite receipts (shadow durability). Daemon
   adds no new truth: `issuer.cap` is an ephemeral authenticator (rotated
   per incarnation), pins/diagnostics remain derived.
2. **Ownership.** Only `nexusd` writes its DataRoot while live (CLI
   mutations refuse). Only the Controller creates attempts; only the kernel
   writes receipts. The daemon never writes the Controller ledger.
3. **Dependency direction.** Volatile -> stable: JS transport -> daemon IPC
   -> kernel -> store. No cycles; Rust never imports JS.
4. **Service boundaries.** IPC v1 envelope `{protocol,id,cmd,params,auth?}`
   with strict field validation; unknown commands fail closed. Forbidden from
   crossing: shell text, paths, executables, secrets (vocabulary cannot name
   them; cap keys/tags/never logged).
5. **Failure semantics.** Timeouts (30 s per request), client cap (32,
   backpressure refusal), frame caps (1 MiB in / 4 MiB out), bounded nonce
   cache (10k), bounded drain on shutdown (5 s). Every dependency failure
   (store/witness/socket/cap/entropy) fails closed with a named code.
6. **State lifecycle.** `starting -> ready -> stopping -> stopped(exited)`;
   SIGTERM/SIGINT -> drain -> unlink socket -> release lock -> exit 0.
   SIGKILL -> OS releases flock; next start reclaims the stale socket.
7. **Test seams.** Real-subprocess harness (`tests/common/mod.rs`) with
   temp dirs, polled readiness, real signals; JS suite injects readers and
   services exactly like A1.2. No sleeps for synchronization except bounded
   post-crash settling before restart probing (readiness itself is polled).
8. **Migration/compatibility.** No contract/schema version moves; rollback =
   delete the new crate + JS module + revert the two small edits (CLI guard,
   transport selection). CLI works exactly as A1.2 when no daemon runs.
9. **Observability.** `health` (state/incarnation/version/dispatch) +
   `status` (trust mode, accepted commands, event count, journal head,
   witness configured+present, latched reconciliation state, active clients,
   request/refusal/error counters). Bounded JSON logs on stderr.
10. **Security implications.** See section 6 (critical). No new privilege in
    the default mode; shadow-test mode is an explicit, documented, limited
    trust configuration — never production authentication.

## 3. Daemon lifecycle (A1.3.1, proven)

- Persistent `Kernel` instance (one process serves arbitrarily many
  requests; epochs advance 1,2,... across calls on one connection set).
- Explicit states `starting/ready/stopping/stopped`; one JSON `ready` line
  on stdout gates supervisors/tests; one `stopped` line reports the latched
  reconciliation flag at exit.
- SIGTERM/SIGINT: stop accepting, bounded drain (5 s), unlink socket,
  release `daemon.lock`, exit 0 (proven: socket gone, restart clean).
- Single ownership: second daemon on the same DataRoot/socket fails fast
  with `daemon-owns-store`/`daemon-already-running`; first daemon unaffected
  (proven).
- SIGKILL recovery: lock released by the OS, stale socket reclaimed after a
  failed connect probe, receipts byte-identical after restart (proven).
- Corrupt DB / incompatible schema (forged `schema_version=99`) refuse
  startup naming `store-corrupt` / `store-incompatible` (proven).
- Bounded: 1 MiB frames, 4 MiB responses, 32 clients, 30 s I/O deadlines,
  10k nonces, 5 s drain. Panics contained per connection (`catch_unwind`).
- Foreground-only: no service manager, suitable for supervision (stated).

## 4. IPC protocol (A1.3.2, proven)

- Unix socket, one JSON object per line; exact `protocol: 1` match else
  `version-mismatch` with id echo (proven, incl. post-abuse serving).
- Request IDs required; every response echoes `{protocol,id,ok}` (proven).
- Strict validation: non-object/unknown fields/missing ids/empty cmd/
  non-object params all refused as `bad-request` (proven, 9-shape battery).
- Unknown commands fail closed as `unknown-command` (proven, incl. case
  variants and `shutdown`/`exec` bait).
- Oversize frames rejected pre-parse as `too-large`; daemon survives
  (proven with a 1 MiB+ frame).
- 16 concurrent clients served; 8-way concurrent identical accepts yield
  exactly one created receipt + 7 replays with one digest (proven).
- Disconnects (no-data, half-frame) never disturb the daemon (proven).
- No shell/paths/executables in the vocabulary by construction; malformed
  input yields refusals, never crashes or state corruption (proven battery).
- A1.2 CLI contract preserved: reads unchanged; mutations behave exactly as
  A1.2 whenever no daemon owns the store (A1.2 suite 87/87 re-proven).

## 6. Issuer authorization boundary (A1.3.3, CRITICAL — proven + limited)

What the daemon enforces (proven by Rust + JS tests):

1. Issuer strings / caller hashes / well-formed resolutions are NEVER
   authorization: every privileged command first passes mode + per-request
   authentication before any kernel semantics run.
2. The real JS Registry remains the sole model-resolution authority: no
   resolver exists in Rust (unchanged, no new resolution code).
3. Readonly (default): privileged commands unconditionally refused with
   `privileged-disabled`; no credential can enable them (proven, incl. with
   a well-formed dummy cap). No cap file is created in this mode.
4. Shadow-test (explicit opt-in): per-request `auth {nonce,ts,tag}`,
   `tag = HMAC-SHA256(capkey, canonical({protocol,id,cmd,params,nonce,
   ts}))`, fresh 128-bit nonce, +/-5 min window, bounded replay cache,
   constant-time compare. Missing/wrong/stale auth -> `issuer-untrusted`;
   reused nonce -> `replay-rejected` (proven). The key is random per
   incarnation, rotated each start, 0600, never logged/returned.
5. Forged resolutions on the protected path: unauthenticated seal of a
   self-consistent forgery -> `issuer-untrusted` (auth gates first);
   authenticated tampered bytes -> `delivery-invalid`/`forged-issuer` from
   the kernel seal check (proven). H-02 is retained and restated: `seal`
   proves well-formedness, NOT Registry origin; origin trust = channel auth.
6. Legacy CLI bypass closed: `acquire/seal/accept` via CLI while a daemon
   owns the store -> `daemon-owns-store`, exit 2 (proven live); reads still
   work; after daemon exit the CLI path works again (liveness, not file
   existence). This is NOT a static shared string or a world-readable token:
   the capability is per-incarnation random with replay protection.

VULNERABLE boundary (proven, pinned, must be read before any wider use):

- **Same-UID hostile processes are NOT stopped.** The cap file is 0600, but
  any process running as the daemon's UID can read it and impersonate the
  trusted issuer over the socket. `SO_PEERCRED` was deliberately NOT used as
  authentication: it proves UID/PID, not which JS module produced a request.
  Socket permissions do not fix same-UID access either.
- Proven by `same_uid_cap_theft_is_possible_and_documented` (Rust) and the
  A4 JS check: the test process reads the cap as the same user and its
  forged authenticated request is ACCEPTED. If that test ever fails, the
  boundary got stronger and this section must be rewritten.
- Supported deployment boundary: single-tenant development/test machines
  with no hostile same-UID peer. Production use requires separate service
  identities (distinct UIDs + protected store or external trust anchor) and
  is explicitly NOT claimed. Until then, privileged operations stay either
  disabled (readonly default) or confined to the explicit shadow-test
  configuration. No validation was weakened to make tests pass.

## 7. Lifecycle, recovery, observability (A1.3.5–A1.3.6, proven)

- Fresh DataRoot starts clean (0 commands/events, witness unconfigured).
- Restart preserves receipts byte-identically (graceful and SIGKILL paths).
- Termination after accept, before the response: the client reconnects,
  re-accepts the same envelope, and converges to exactly one receipt
  (created-or-replayed, never conflict) — proven by the fire-and-SIGKILL test.
- Concurrent identical commands -> one winner + replays, one digest.
- Conflicting commands -> `command-conflict`, prior receipt byte-identical.
- Witness deleted after protection -> next generation op fails closed with
  `reconciliation-required`/`witness-required`, and `status` latches
  `reconciliationRequired: true` with detail (never auto-cleared).
- Ambiguous/malformed Controller history -> `ambiguous-attempt` / explicit
  refusal, never inference (proven through the daemon path).
- **Retained A1.1 limitation:** main-store receipt and witness note are not
  atomically committed; reconciliation stays conservative and external
  dispatch stays disabled (see section 8).
- `status` exposes: state, incarnation, IPC version, trust mode, shadow mode,
  accepted/total commands, event count, journal head, witness
  configured+present, reconciliation latch, active clients, request/refusal/
  error counters, `dispatchEnabled: false`. Logs are bounded single-line
  JSON with ids/codes only (no keys/tags/nonces/prompts/credentials).

## 10. Known limitations (NOT claimed)

- Same-UID hostile peer breaks the shadow-test trust boundary (section 6).
- Witness must live in an independent failure domain (inherited A1.1).
- Main-store + witness commits are not atomic (retained A1.1 window).
- Nonce cache (10k) bounds replay memory, not replay time beyond the ts
  window; ts window requires roughly synchronized clocks.
- Proven on Linux + SQLite WAL + Unix sockets only. No Windows/macOS, no
  NFS, no power-loss, no performance/SLO claims.
- Recovery attestation stays operator-asserted (inherited A1.1).

## 11. Blockers before A2 (unchanged + one added)

- Independent-failure-domain witness deployment proof; IPC peer
  authentication replacing the cap file (separate service identities);
  verified attestation source for recovery; atomic commit across store +
  witness (2PC or witness-acknowledged protocol).
- Only then any external-effect authorization. A shadow receipt is not
  execution evidence and never becomes completion evidence.

## Verdict

- **A1.3 SHADOW READY** — persistent daemon, versioned IPC, trusted-issuer
  boundary with a proven and documented same-UID limitation, crash-safe
  lifecycle, and full shadow integration, all within shadow-only operation.
- **A2 DISPATCH NOT AUTHORIZED** — a working daemon does not imply a
  trustworthy execution runtime; dispatch stays disabled.
