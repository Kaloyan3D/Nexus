## 1. Implemented guarantees

- **Versioned contracts.** `ControllerIntentV1`, `RegistryResolutionV1`,
  `ExecutionTargetCoreV1`, `ExecutionPinV1`, `GenerationLeaseV1`,
  `KernelCommandV1` (as `AcceptRequest`), `CommandReceiptV1`, `KernelEventV1`,
  `KernelErrorCode` with wire-stable kebab-case strings shared with the JS
  prototype vocabulary. Target carries ONLY real resolver binding fields;
  invented endpoint/billing/session metadata is impossible by construction
  (the struct has no such fields). Missing mandatory target fields fail
  closed with `target-incomplete`; unknown schema versions fail with
  `unsupported-schema`. No second model resolver exists in Rust: the JS
  Registry remains authoritative and the kernel only verifies sealed bytes.
- **Sealed issuance.** The kernel honors only bridge-sealed resolutions:
  HMAC-SHA256 over the canonical issued bytes with a per-store random 256-bit
  key, verified with constant-time equality against the sealed record.
  Swapped target bytes fail (`delivery-invalid` on identity mismatch);
  re-digested but never-sealed forgeries fail (`forged-issuer`).
- **Kernel-owned fencing.** `AcquireGeneration` advances one generation
  epoch transactionally. Concurrent acquires issue unique epochs (proven
  8-way threaded and 4-process xproc). Old epochs cannot authorize new
  commands (`stale-lease`). Acceptance verifies the current generation and
  lease inside the same transaction that writes the receipt (no TOCTOU).
- **Idempotent replay, conflict rejection.** Identical envelope replay
  returns the original receipt (one receipt row, ever). Same commandId with
  any differing immutable field fails with `command-conflict`; prior
  authority is never overwritten (8-way concurrent acceptance: exactly one
  winner, one authoritative digest).
- **Durable receipts and ordered journal.** Command row + journal event +
  receipt row commit in ONE SQLite transaction. Events are monotonic
  (`AUTOINCREMENT seq`), per-generation ordered, typed, and restart-stable
  (byte-identical journal across reopen). Reconstruction validates ordering,
  receipt presence, and digest agreement, failing closed otherwise.
- **Independent rollback witness.** Separate SQLite file in a separate
  failure domain tracks monotonic maxEpoch plus accepted-receipt progress.
  Cross-epoch restore fails with `rollback-detected`; same-epoch receipt
  loss fails with `reconciliation-required` (never silently re-accepted);
  missing/corrupt witness after protection fails closed; downgrade (omitted
  witness) fails with `witness-required`. Recovery is explicit only via
  `fence_for_recovery` with recorded operator attestation; fenced epochs
  are never re-issued and old leases stay dead.
- **Dispatch-disabled boundary.** Every receipt carries status
  `accepted-reserved-dispatch-disabled`. The sole dispatch authorization
  path always returns `dispatch-disabled`; the binary contains no exec,
  network, spawn, or dynamic-load capability (asserted by test on the
  actual `main.rs` source plus `init`/`status` smoke runs). No exactly-once
  external execution is claimed.

## 2. Transaction boundaries

- SQLite pragmas: `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`,
  `busy_timeout=5000`. WAL gives atomic multi-statement commits with readers
  never seeing torn state; FULL scores durability across OS crashes once
  commit returns.
- All mutating transactions use `BEGIN IMMEDIATE`: the write lock is taken
  up front so contenders receive retryable `SQLITE_BUSY` (handled by the
  busy timeout) instead of the immediate `SQLITE_BUSY_SNAPSHOT` upgrade
  failure that DEFERRED transactions hit under write contention.
- `accept_command` (store): seal-exists check, lease-currency check,
  existing-command classify, command INSERT, `command-accepted` event INSERT,
  receipt INSERT — one transaction.
- `acquire_generation` (store): generation upsert + `generation-acquired`
  event — one transaction.
- Cross-process serialization (NOT cross-file atomicity): an in-process mutex
  plus an `flock(2)` exclusive lock on `<dbdir>/kernel.lock` serializes every
  check-act-note sequence (acquire, accept, fenced recovery) across threads
  AND processes, so no two writers can interleave their store and witness
  updates. This is mutual exclusion only. The main store and the independent
  witness are two separate SQLite files with two separate commits; no atomic
  commit across both failure domains is claimed or possible here (that would
  require 2PC or a witness-acknowledged protocol). Lock failure fails closed.
- RETAINED receipt/witness crash window: receipt-then-witness ordering means a
  crash (or a backup restored) between the store commit and the witness note
  leaves a committed receipt without witness coverage. The next identical
  replay heals the witness when the receipt survived, and fails closed with
  `reconciliation-required` when the receipt was lost — never silent
  re-acceptance. Because the kernel cannot prove exactly-once external effects
  across this window, external dispatch stays disabled; closing the window is
  an explicit A2 blocker (see section 7).
- Schema versioning: `schema_version` table, current version 1; anything
  else fails closed with `store-incompatible`. `PRAGMA integrity_check` runs
  on every open; failure maps to `store-corrupt`.

## 3. Crash behavior

- SIGKILL mid-loop over 2000 acquire/seal/accept iterations (real `Child::kill`,
  i.e. SIGKILL, not an injected exception): store reopens cleanly,
  `commands == receipts`, events strictly ordered, every receipt
  reconstructable, replays idempotent. Only complete records survive;
  incomplete transactions never appear committed.
- Refused commands journal nothing (only `generation-acquired` events exist
  for bare acquisitions).
- The residual crash window (receipt committed, witness note lost) resolves
  to `reconciliation-required` on replay, never to silent re-acceptance.
  This window is RETAINED as a blocker for external dispatch (see section 2).
  No power-loss testing beyond process termination is claimed.

## 5. Cross-language identity

- Rust `canonical_json` replicates JS `resolver.canonicalize` (sorted keys,
  `JSON.stringify` scalar encoding). `scripts/gen-canonical-vectors.cjs`
  generates 8 vectors from the REAL resolver (empty object, key sorting,
  scalars, unicode escapes, intent/command digest field sets, a realistic
  target binding, nested arrays); the Rust `cross_language_canonical_vectors`
  test asserts byte-identical canonical form and sha256 for every vector.
- Digest layering matches SPIKE-02 `envelope.cjs`: payloadDigest,
  intentDigest (lease/timestamps excluded), commandDigest. Issuance identity
  covers the complete immutable issuance incl. task binding, mirroring
  `trust.sealContentOf`; `targetDigest` remains model-target identity only.

## 6. Known limitations (NOT claimed)

- Witness MUST live in an independent failure domain. Same-disk witness
  restored together with the DB is undetected by construction (inherited
  from SPIKE-02 F-02 LIMIT).
- Seal is a store-held HMAC key, not IPC peer authentication; same-UID
  readers/writers of the store break the boundary (needs service identity /
  SCM_CREDENTIALS-class proof in A2).
- Accepted-map growth in the witness is unbounded; A1 needs pruning keyed
  to Controller retention.
- Recovery attestation is operator-asserted, not independently verified; a
  wrong attestedMaxEpoch below a forgotten issuance could re-enable an old
  epoch. The audit baseline records the assertion explicitly.
- Proven on Linux + SQLite WAL semantics only. No Windows/macOS, NFS flock,
  power-loss, or performance/SLO claims.
- `flock` mutex serializes kernel writers; readers never block. First-init
  races between two concurrent openers fail closed (locked schema setup),
  not queued — operators start one writer set.

## 7. Gates remaining before A1.2 and A2

- A1.2: trusted bridge wiring (JS Registry snapshot + mode config into Rust
  `RegistryResolutionV1` via the sealed path — no hand-built resolutions in
  production flow), witness pruning policy, operator runbook for
  `fence_for_recovery`, multi-generation retention tests.
- A2: independent-failure-domain witness deployment proof, IPC peer
  authentication replacing the store-held seal key, verified attestation
  source for recovery, and only then any external-effect authorization.
  External dispatch stays disabled until every A2 gate passes; A2/A4 gates
  stay closed.

## 8. Architectural deviations from SPIKE-02 (deliberate)

- File-store link-publish replaced by SQLite WAL + IMMEDIATE transactions;
  mkdir mutex replaced by `flock` + in-process mutex (same semantics, real
  cross-process proof included).
- Issuance identity keyed by content hash carried in
  `provenance.issuanceId` (G-03/G-04 design, unchanged).
- Sealed-issuance records live in the store (table) instead of
  `trusted-issuances/` files; the HMAC verification is identical.
- No `controller-intent-store` equivalent: the Controller journal is out of
  A1.1 scope; the kernel is authoritative for commands, receipts, and events.
- Error-code vocabulary preserved (`forged-issuer`, `stale-lease`,
  `command-conflict`, `rollback-detected`, `reconciliation-required`,
  `witness-required`, `binding-mismatch`, `payload-tamper`,
  `issuance-conflict`, `target-incomplete`, `unsupported-schema`,
  `dispatch-disabled`, `store-corrupt`, `store-incompatible`) so JS-side
  operators keep the same contract language.
