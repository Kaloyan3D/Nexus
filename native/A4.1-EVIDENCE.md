## 1. Before / after credential topology

**Before (A3.6).** Issuer handoff `issuer.handoff` (0640 `daemon:socket-group`) sat in the
shared socket directory. The approver must be in the socket group to `connect(2)`, so the
approver identity could read the issuer credential through ordinary file permissions.
Only the SO_PEERCRED allow-list stopped it from being used.

**After (A4.1).**

| Path | Owner:Group | Mode | Readers |
|---|---|---|---|
| DataRoot (`k.db`, `issuer.cap`) | daemon:daemon | 0700 / 0600 | daemon |
| socket dir | daemon:socket-group | 0750 | traverse: issuer, approver, bystander |
| `n.sock` | daemon:socket-group | 0660 | connect: socket group only |
| issuer credential dir | daemon:issuercred | 0750 | daemon, issuer |
| `issuer.handoff` | daemon:issuercred | 0640 | daemon, issuer |
| approver credential dir | daemon:approver | 0750 | daemon, approver |
| `approver.cap` | daemon:approver | 0640 | daemon, approver |

Group membership: `issuercred` = {daemon, issuer}; `approver` = {daemon, approver};
socket group = {daemon, issuer, approver, bystander}. The three groups are enforced disjoint
in role by startup checks (see 4).

## 2. Authentication / role boundaries (unchanged, verified independent of file access)

- Connect: kernel (socket 0660 group). Untrusted UID gets EACCES.
- Issuer commands: valid issuer HMAC **and** SO_PEERCRED UID in `--allowed-uids`.
- `write-scope-approve` / `process-scope-approve`: valid approver HMAC **and** UID in `--approver-uids`.
- Issuer key never satisfies approver commands (`issuer-untrusted`); approver key never satisfies issuer commands.
- A stolen valid key used from the wrong UID gets `peer-unauthorized`.
- Replay protection and Kernel authorization untouched. `dispatch_enabled() == false`.

## 3. Code changes

- `nexusd`: new `--cap-handoff-gid GID|NAME`. Handoff goes in a dedicated exact-0750
  `daemon:gid` directory, symlink-leaf refused, distinct from socket dir and DataRoot.
- Startup refuses (fail-closed): handoff gid == socket group; approver gid == issuer credential
  group; approver credential configured with a handoff but no `--cap-handoff-gid`; approver
  credential dir not exactly 0750 `daemon:approver-gid`; any credential dir equal to / nested
  with socket dir, other credential dir or DataRoot.
- `CredGuard`: if startup fails after publication, only the exact regular files this process
  published are removed (symlinks/dirs never followed or removed). Clean shutdown does the same.
- Publication unchanged and reused: O_EXCL temp inode, validated, atomic rename, O_NOFOLLOW.
- Deploy: `nexusd.service` (second RuntimeDirectory, group), `SETUP.md`, `Dockerfile.multuid`,
  `MULTUID-PROCEDURE.md`, `multuid-userns.sh` updated.
- No new Tauri permissions, daemon commands, tool invocation or provider access.

## 4. Threat model

| Threat | Control |
|---|---|
| Approver reads issuer cap via socket group | separate credential group/dir (test: socket_membership) |
| Issuer reads approver cap | approver-only group/dir (credential_files) |
| Untrusted reads either / connects | dir 0750 + socket 0660 (EACCES) |
| Stolen key used from other UID | SO_PEERCRED allow-lists (each_role, stolen tests) |
| Credential dir swapped for symlink | symlink leaf refused (a41_misconfiguration #5) |
| Loosened/wrong-group dir | exact 0750 + gid check (#6, #7) |
| Pre-planted symlink/hardlink at handoff | refuse symlink; rename replaces inode, hardlink keeps stale bytes (#8, #9) |
| Crash/partial publish leaves key | CredGuard + stale temp scrub; startup rotation |
| Key in responses/diagnostics | test credentials_never_appear (responses, refusals, stdout/stderr) |

## 6. Security findings and fixes

1. **F1 (fixed):** approver could read issuer handoff via socket-group membership. Fixed with
   dedicated credential group/dir, and startup now refuses the coupled configuration.
2. **F2 (fixed):** failed startup after publication could leave a published credential. Fixed by CredGuard (exact paths, regular files only).
3. **F3 (noted):** the test-harness group file previously encoded the coupling; corrected.

Caveat: `--cap-handoff-gid` is opt-in for the legacy issuer-only (no approver) topology,
which keeps the old socket-dir handoff. Any configuration with an approver credential is forced onto the new layout.

## 7. Same-UID limitation

If the daemon and a hostile process share a UID, Linux file modes cannot separate them: the
process can read DataRoot and every credential. Likewise a hostile module inside the issuer
or approver process shares that UID's credential. SO_PEERCRED authenticates processes, not
modules. Separation here is only real across distinct UIDs.

## 8. Remaining deployment blockers

- Production provisioning of `nexus-issuercred` and the second RuntimeDirectory is documented
  but not exercised on a real systemd host.
- Rootful Docker suite not run here.
- Issuer/approver are still separate processes only by convention; the approver identity has
  no UI/human channel yet.
- Same-UID module confusion inside the issuer process (see 7).
- Credentials rotate per start but there is no online rotation or revocation.

## 9. Prerequisites for A4.2 (Human Approval System)

- Approver identity runs as its own UID with its own credential dir (provided by A4.1).
- Define an authenticated human-to-approver channel that does not traverse the issuer UID.
- Decide approver-process hardening (no shared UID with GUI/renderer).
- Online credential rotation/revocation, and audit events for approvals.
- Run the rootful Docker suite on a host with a daemon.
